# PC-1360K 漢字ROM吸い出しツール

PC-1360K実機の漢字ROMを、ページ（`0x3600`の選択値）0〜3ごとに64KiBずつ回収する。
吸い出し用BASICは1本で、実行時にページを指定する。同じプログラムを4回実行し、録音WAVを4本作る。
専用デコーダーで検証・復元した4ファイルを、そのままStudioのROMセット作成画面へ指定できる。
ROM本体や実機録音は同梱しない。ページとSC6976S／SC6976Tの物理チップとの対応は未確定。

## はじめに：短いプログラムで往復を確認する

**本番の約33分の録音を始める前に、次の一連の作業を最後まで確認する。**

```basic
10 PRINT "TEST OK"
```

1. 付属の[transfer-test.bas](transfer-test.bas)をWAV化する。
2. WAVを再生し、PC-1360Kで`CLOAD`する。
3. `RUN`し、`TEST OK`と表示されることを確認する。
4. PCで録音を開始してから、実機で`CSAVE`する（この確認はBASIC保存なので`CSAVE M`ではない）。
5. 保存終了後に録音を止め、WAVとして書き出す。
6. 録音WAVをBASICソースへデコードし、行番号・`PRINT`・文字列が元のソースと一致することを確認する。
   デコード後の空白や改行などの整形差は問題ない。

再生・実機ロード・実機実行・実機保存・PC録音・デコードのいずれかができない状態では、
先に接続や音量、録音設定を調整する。本番の長時間録音で初めて接続を試さない。

## 必要なもの

- PC-1360K実機と、カセットインターフェース等の再生／録音接続環境。
- BASICのWAV化と上記のBASIC復元には、Pokecom GO作者提供の[pcwav](https://github.com/digihori/pcwav)を推奨する。
  実行にはPerlが必要。pcwav本体はこのツールセットには含めない。
- 録音には[Audacity](https://www.audacityteam.org/)を推奨する。
- 本番のROM録音の復元にはPython 3.10以降と付属の[decode.py](decode.py)を使う。追加パッケージやpcwavは不要。

| ファイル | 用途 |
| --- | --- |
| [transfer-test.bas](transfer-test.bas) | 事前の転送・録音確認 |
| [pc1360k-kanji-dump.bas](pc1360k-kanji-dump.bas) | ページ指定式の漢字ROM吸い出し |

### pcwavの準備と事前確認用コマンド

以下は`pcwav`と`pokecom-go-plus`を同じ親ディレクトリに置く例。
既存のpcwavがある場合は、コマンドのパスをその配置に合わせる。

```text
work/
  pcwav/
  pokecom-go-plus/
```

pcwavのリポジトリ直下で以下を実行すると、`dist/pcwav-encode.pl`と`dist/pcwav-decode.pl`が生成される。

```sh
perl build.pl
```

以降のコマンドは、すべて`pokecom-go-plus`のリポジトリ直下で実行する。

```sh
perl ../pcwav/dist/pcwav-encode.pl s1basic tools/pc1360k-rom-dump/transfer-test.bas transfer-test.wav
```

このWAVで`CLOAD`・`RUN`を確認し、実機の`CSAVE`を録音したファイルを`transfer-test-recorded.wav`として、次を実行する。

```sh
perl ../pcwav/dist/pcwav-decode.pl s1basic transfer-test-recorded.wav transfer-test-decoded.bas
```

WindowsでもPython／Perlの実行方法とパスを環境に合わせる。`python3`がない環境では`py -3`などを使う。

### 録音・WAVの設定

- **モノラル、16000Hz、符号付き16bit PCM WAV**を推奨する。既存の16000Hz・8bit PCM実機録音でも検証済み。
- Audacityの録音デバイスを実機の接続先に合わせる。入力レベルが振り切れないように調整する。
- 無音による自動停止・一時停止は使わない。ブロック間の無音も含めて録音する。
- ノイズ除去や音量の自動調整などの加工を避ける。最後の保存音が終わるまで録音を止めない。
- 録音元が44100Hz／48000Hzや浮動小数点の場合は、WAV書き出し時に16000Hz・16bit PCMを選ぶ。
  ファイル名の拡張子だけを変えても変換にはならない。AudacityのプロジェクトファイルではなくWAVを渡す。
- デコーダーは4000〜32000Hzの8bit／16bit整数PCM、モノラル／ステレオに対応する。
  ステレオは既定で左のみを使う。信号が右にある場合は`--channel 1`を指定する。左右は混合しない。

## 吸い出し前のRAM確認

対象はPC-1360K。以下のRAMを使用するため、必要なプログラムやデータを退避してから実行する。
BASIC自身の領域とも重ならないことを確認する。

| 使用範囲 | 用途 |
| --- | --- |
| `0xC000〜0xC11B` | DATA行から書き込む機械語 |
| `0xC200〜0xC21B` | パラメーター・比較結果等 |
| `0xC220` | 実行状態 |
| `0xCFF0〜0xCFFF` | 保存用識別ヘッダー |
| `0xD000〜0xDFFF` | 読出しデータ4096バイト |

READ(LDPC)を使う機械語をDATA行から配置するので、別途アセンブルする必要はない。
通常ROMバンクやFポートを機械語から切り替えず、`0x3600`へ選択値を書き込んで読む。
機械語から戻る際の選択値は1となる。

## 吸い出し用BASICの転送と実行

```sh
perl ../pcwav/dist/pcwav-encode.pl s1basic tools/pc1360k-rom-dump/pc1360k-kanji-dump.bas pc1360k-kanji-dump.wav
```

1. 吸い出し用WAVを再生し、実機で新しいプログラムとして`CLOAD`する。
2. PC側で録音を開始する。
3. 実機で`RUN`し、`PAGE(0-3)`に対して`0`を入力してENTERを押す。
4. 同じページの4KiB読出し・再読比較・`CSAVE M`を16回繰り返す。途中のENTER待ちや手動保存操作はない。
5. 最後の保存音が終わり、`DONE`が表示されたら録音を止め、`kanji-page-0.wav`として書き出す。
6. プログラムを入れ替えず、録音を新たに開始して`RUN`し、ページ`1`、`2`、`3`も同様に回収する。

0〜3以外や小数を入力するとページ入力へ戻る。4回とも同じページを指定しないように注意する。
途中で停止した場合は、そのページを最初から録り直す。元の録音は調査用に残す。

1ページ64KiBの所要時間は**約33分の見込み**。このページ指定プログラムでの実機所要時間は未計測。
電源管理RAMを書き換える処理は入れていない。

再読不一致数`D`が0以外なら、そのブロックを保存する前に`ERROR BLOCK:`と`D:`を表示して停止する。
番号はページ全体で通したブロック番号（0〜63）。その場合は正常完了として扱わない。

## WAVからROMファイルを復元する

4本のWAVをまとめて指定する。入力の順番ではなく、録音中の識別ヘッダーからページとアドレスを判断する。

```sh
python3 tools/pc1360k-rom-dump/decode.py kanji-page-0.wav kanji-page-1.wav kanji-page-2.wav kanji-page-3.wav --output kanji-roms
```

長時間音声は小分けに読み込み、処理中は録音ごとの進捗を表示する。

ページごとに早めに録音の成否を確認したい場合は、期待するページを明示する。

```sh
python3 tools/pc1360k-rom-dump/decode.py kanji-page-0.wav --pages 0 --output kanji-roms
python3 tools/pc1360k-rom-dump/decode.py kanji-page-1.wav --pages 1 --output kanji-roms
python3 tools/pc1360k-rom-dump/decode.py kanji-page-2.wav --pages 2 --output kanji-roms
python3 tools/pc1360k-rom-dump/decode.py kanji-page-3.wav --pages 3 --output kanji-roms
```

| 出力ファイル（各65536バイト） | Studioの指定先 |
| --- | --- |
| `kanji-selector-0.bin` | 漢字ROMの選択値0の欄 |
| `kanji-selector-1.bin` | 漢字ROMの選択値1の欄 |
| `kanji-selector-2.bin` | 漢字ROMの選択値2の欄 |
| `kanji-selector-3.bin` | 漢字ROMの選択値3の欄 |

各`.bin`に対応する`.json`には、ページ・サイズ・合計値・SHA-256・各ブロックの検証情報を保存する。
StudioのPC-1360K ROMセット作成ダイアログには4つの`.bin`を指定する。WAVやJSONは指定しない。
通常ROMなど他の必要ファイルも従来どおり指定する。4ページを1ファイルにまとめる必要はない。

### 検証とエラー

デコーダーは次を検証してから出力する。

- S1の名前・メタ情報・120バイトごとの転送チェックサムと終端。
- 末尾の端数データと最初の`0xFF`を含める、PC-1360K実機方式の末尾チェックサム。
- 識別ヘッダーの形式、ページ、アドレス、4096バイトの長さ、ブロック番号の整合性。
- 実機での再読比較が`D=0`であること、データ合計と保存ヘッダーのSUMが一致すること。
- 指定した各ページの16ブロックがすべてあり、重複や想定外のページがないこと。

検証失敗時は終了コード1、成功時は0。検証不合格の入力からはROMを生成しない。
別内容の既存ファイルは上書きしない。同じ内容なら再実行できる。
検証が失敗しても、過去の実行で出力したファイルは削除されないので、古い成功結果と取り違えないこと。
出力中のディスク容量不足等では途中ファイルが残る場合があるため、エラー時は完了表示も確認する。

`missing blocks`は欠落、`duplicate block`は同じブロックの重複、`checksum mismatch`は転送データ不整合を示す。
録音の切り詰め、無音停止、音量、選択チャンネル、ページの指定を確認し、必要なら該当ページを録り直す。
通常のpcwavの`s1bin`復元は一括録音をすべて取り出すための手順ではないので、本番にはこの専用デコーダーを使う。
確認したpcwav S1 Binaryエンコーダーの末尾SUM計算の修正は別件で、このツールではチェックを省略して受け入れない。

## 検証範囲と詳細資料

- 実機録音から全64ブロックを復元し、4つの64KiB ROMと全バイト一致を確認。
- 付属テストは合成データのみを使い、ROMや実機録音は不要。
- BASICの入力・ループは実ROMを使ったエミュレータで全4ページ、範囲外・小数入力、比較エラー時の停止を検証済み。
  この試験では音声保存を代替処理に置き換えている。
- ページ0は本ツールを使った実機での吸い出し・録音・デコードを確認済み。生成した65536バイトは検証済みのページ0と全バイト一致した。

## 補足：吸い出し用BASICが行っていること

BASICは、漢字ROMを読み出す機械語の準備と、4KiBごとの保存を担当する。
漢字ROMを読む部分はDATA行に入っている機械語で、BASICの`READ`はその機械語データを取り出すために使う。
CPU命令のREAD(LDPC)とは役割が異なる。

### 1. 機械語をRAMへ配置する（行10〜40、1000〜1230）

DATA行に並んだ284バイトを、`READ B`で1バイトずつ取り出し、
`POKE &C000+I,B`で`0xC000〜0xC11B`へ書き込む。
これで、後から`CALL &C000`で呼び出せる読出し処理が準備できる。

### 2. ページを選び、16個のブロックを順番に処理する（行45〜90）

入力したページ番号を変数`P`に保持する。0〜3の整数以外は再入力へ戻る。
1ページは64KiBなので、4KiBずつ16回に分けて扱う。

| 変数 | 意味 |
| --- | --- |
| `P` | 入力したページ番号（0〜3） |
| `K` | 4ページ全体で通したブロック番号（0〜63） |
| `S` | 今回読み出すページ番号。`K`から計算し、`P`と同じ値になる |
| `A` | ページ内の読出し開始アドレス。`0x0000`、`0x1000`、…、`0xF000` |
| `Z` | 機械語へ渡す、開始アドレスの1つ手前の値 |
| `H` | `Z`の上位1バイト |
| `D` | 再読比較で一致しなかったバイト数 |

例えばページ2なら、`K`を`0x20〜0x2F`まで進め、ページ2の全16ブロックを読む。
`Z=A-1`とするのは、機械語がアドレスを1つ進めてから読むため。
先頭`0x0000`を読む場合は`Z=0xFFFF`とし、次に進めたときに`0x0000`へ折り返すようにしている。

### 3. 漢字ROMを4KiB読み出し、もう一度読んで比較する（行100〜150）

`0xC200`にページ番号、`0xC201〜0xC202`に`Z`の下位・上位バイトを渡し、`CALL &C000`で機械語を呼ぶ。
機械語は`0x3600`へページ番号を書き込み、DPで示す漢字ROMのデータをREAD(LDPC)で読み出して、
4096バイトをRAMの`0xD000〜0xDFFF`へ格納する。同時に、各バイトの値を足したSUMも計算する。

さらに同じ範囲をもう一度読み、RAMに保存した内容と1バイトずつ比較する。
不一致数を`0xC210〜0xC211`、SUMを`0xC212〜0xC214`へ書き戻す。
BASICは不一致数を`D`として取り出し、0以外なら録音へ出力せずエラー処理へ進む。
機械語は呼出し時のレジスターを退避・復元し、終了時には`0x3600`の選択値を1へ戻す。

### 4. 識別ヘッダーを付ける（行200〜280）

読み出した4096バイトの直前、`0xCFF0〜0xCFFF`に16バイトのヘッダーを置く。
この情報があるので、PC側はファイル名や録音の指定順に頼らずデータを組み立てられる。

| ヘッダー内の位置 | 内容 |
| --- | --- |
| 0〜3 | 識別文字列`K136` |
| 4 | 保存形式のバージョン（1） |
| 5 | ページ番号 |
| 6〜7 | ページ内の開始アドレス |
| 8〜9 | データ長（4096バイト） |
| 10〜12 | データ4096バイトのSUM |
| 13〜14 | 再読不一致数（正常時は0） |
| 15 | 全体のブロック番号`K` |

複数バイトの数値は、下位バイトから順に格納する。
ここでのSUMはROMデータの単純な合計で、カセット転送形式のチェックサムとは別の検査値。

### 5. ヘッダーとデータを音声として保存する（行400〜440）

`CSAVE M &CFF0,&DFFF`で、ヘッダー16バイトとROMデータ4096バイト、計4112バイトを出力する。
実機の保存処理が、このRAMの内容をカセット用の信号に変換する。
BASICがWAVファイルを作るわけではなく、その音声をPC側で録音してWAVとして保存する。

保存が終わると`NEXT K`で次の4KiBへ進み、同じRAM領域を再利用する。
16回が終わると状態欄`0xC220`へ`0x5A`を書き、`DONE`を表示して終了する。
デコーダーは各保存データからヘッダーを除き、16ブロックをアドレス順に結合して64KiBのROMにする。

### 6. 読出しが一致しなければ停止する（行700〜730）

再読比較の不一致を検出した場合は、状態欄へ`0xEE`を書き、
`ERROR BLOCK:`にブロック番号、`D:`に不一致数を表示して終了する。
一致しなかったブロックは`CSAVE M`へ渡さない。

### シリアル通信による吸い出し：低優先度・保留

実機検証に利用できるケーブルとして、高松製作所製のD-Sub9ピン接続ケーブルがある。
[製品ページ](https://tmfg.jp/products/detail/80)には、15ピンシリアルポート用で、
レベル変換回路とハードウェアフロー制御の信号線を備えると記載されている。
PCへの接続にはUSB–RS-232C変換アダプターを介する想定。
同ページの対応機種一覧にはPC-1360Kが含まれないため、所持ケーブルの仕様と
PC-1360Kでの接続・通信可否は別途確認が必要。

1200bps、8ビット、パリティなし、ストップ1ビットでバイナリを連続転送できる場合、
理論上は4KiBで約34秒、256KiBで約36分となる。
ROM読み出し、送信処理、フロー制御などの時間は含まず、実測値ではない。
将来着手する場合は、短いデータの送受信、既知の4KiBとの一致確認、
全領域の転送時間測定の順で検証する。
この案は優先度を下げて保留し、次回リリースの対応範囲には含めない。
