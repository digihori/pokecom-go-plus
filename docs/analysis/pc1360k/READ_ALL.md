# PC-1360K 自動一括回収

> この文書は個別実験の経過記録です。「未取得」「未実装」等は各記述時点の状態を示します。
> 現在のまとめは[PC-1360K 漢字ROM解析とStudio対応](../../machines/PC-1360K.md)、
> 吸い出し用BASICの使い方は[配布用手順書](../../../tools/pc1360k-rom-dump/README.md)を参照してください。

選択値2・3の追加回収は[専用手順](READ_ALL_23.md)を参照。

2026-10-18。アドレス・機械語DATA・桁数の基準値などは`&`付き16進表記。
行番号とGOTO先の行番号は通常の10進表記で残す。
対象は現在指定方法が分かっているselector 0/1の各64KiB、計128KiB。
物理ROMの全容量、S/T対応、256KiB構成や追加の選択条件は未確定。

## 操作

以下は旧版（`read-all.bas`／後の`pc1360k-kanji-dump-01.bas`）での実行記録。
現在の配布ソースは[ページ指定版](../../../tools/pc1360k-rom-dump/pc1360k-kanji-dump.bas)に統合している。

1. 当時の選択値0・1用BASICを新しいプログラムとして実機へ転送する。
2. PC側で録音を開始する。長い録音なので、無音での自動停止は無効にする。
3. 実機でRUNする。
4. 以後は読み出し→再読比較→CSAVE Mを32回、自動で繰り返す。
   途中にPRINTによるENTER待ちはない。手動のCSAVE M操作も不要。
5. 最後にDONEが出たら録音を止め、WAVをそのまま解析用に渡す。

既存4KiBリーダーの機械語は変更していない。
実機の連続録音を受領し、32回の保存データをすべて抽出・検証できた（下記の結果参照）。
プログラム全周回と保存前の内容は、下記の代替保存テストで確認している。

標準S1の参照pcwav波形では1ブロック約137秒、32ブロックで約73分に相当する。
これに実機の読出し・準備時間が加わる。実際の所要時間は転送速度・機器で変わる。

### 不一致の場合

読み直しでDが0以外なら、そのブロックを保存する前に停止し、
ERROR BLOCKとブロック番号、Dを表示する。値と録音済みWAVを残す。
録音が途中で止まった場合も、それまでに完了したブロックは回収できる。

行60は`60 FOR K=0 TO &1F`。再開するときは、回収済み一覧を照合してから
開始番号だけを変更できる。K=0..15はselector 0、16..31はselector 1。
開始DPは`(K MOD 16)*4096`。不足分の穴をゼロで埋めたROMは作らない。

## 保存形式

各CSAVE Mの範囲はCFF0..DFFF（53232..57343）、4112バイト。
先頭16バイトに識別情報を付け、その後にROM読出しデータ4096バイトを置く。
各ブロックを匿名で保存しても、番号・範囲・合計値から識別できる。
読み出し・再読比較中は音声が出ないため、ブロック間に無音区間がある。
録音はその間も止めず、全32回を1本のWAVとして残す。
既存のread-fast-4k.basの結果表示と手動保存とは異なる形式。

| ヘッダー位置 | 内容 |
| --- | --- |
| 0..3 | ASCII K136 |
| 4 | 形式バージョン1 |
| 5 | selector 0/1 |
| 6..7 | 読出し開始DP（下位/上位） |
| 8..9 | データ長4096（下位/上位） |
| 10..12 | データ合計値（下位から3バイト） |
| 13..14 | 再読不一致数。正常保存時は0 |
| 15 | ブロック番号0..31（2・3版では32..63） |

使用領域は機械語C000..C11B、パラメーターと結果C200..C21B、
状態C220、保存ヘッダーCFF0..CFFF、データD000..DFFF。
これらの既存データを上書きする。C220は実行中0、全保存後90、不一致停止238。
保存中のCPU内部レジスタ・F出力等の扱いは[4KiBリーダー](READ_FAST_4K.md)を参照。

## 録音の分割・復元

通常のpcwav s1binデコードは最初のファイルを返すため、一括録音はrawとして
デコードし、追加した[extract-batch.py](extract-batch.py)で全ファイルを抽出する。
ユーザーが手動で分割する必要はなく、WAVのまま渡してよい。

実行例（pcwav側のスクリプトパスは各環境の配置に合わせる）：

```sh
perl /path/to/pcwav-decode.pl raw all.wav all.raw
python3 docs/analysis/pc1360k/extract-batch.py --raw-s1 all.raw \
  --output local-data/analysis/pc-1360k/batch
```

また、別ツールで各CSAVE Mの4112バイトのペイロードを取り出せた場合は、
複数ファイル、またはその連結ファイルを`--raw-s1`なしで渡せる。

各S1ヘッダー・完全な120バイト単位のチェックサム・端数データと最初のFFのチェックサム・
終端、識別情報、データ合計、不一致数を検証する。端数のチェックサムは実機録音で
確認した方式を既定とする。旧pcwav encoderの端数を除外する方式は
`--allow-legacy-tail`を明示した場合だけ受け付ける。合計値だけであらゆる転送破損を検出できるわけではない。
異なる内容の同一番号があればエラー。欠番は一覧として報告する（終了コード2）。
既存の異なるファイルを上書きしない。

正常な4KiBファイルを取り出し、16ブロックそろったselectorについてのみ
`read-s0-0000-ffff.bin` / `read-s1-0000-ffff.bin`を生成する（各65536バイト）。
これらはselector別の論理イメージであり、S/Tの物理チップ名はまだ付けない。
manifest.jsonに合計・範囲・SHA-256・不足番号を記録する。
取得済みの4KiB・256バイト・「あ」の字形とも照合する。

## 検証と限界

- ローカル実ROMのBASICで全32回の周回・範囲・selector・保存データを検証。
  この試験に限りCSAVE Mを保存内容を記録するCALLへ置き換え、実音声転送は実行しない。
- 2番目のブロックの再読を1バイト変更する試験では、最初の1ブロックだけを保存し、
  不良ブロックを保存する前にERRORへ進むことを確認。
- 既存pcwav S1 encoderの独立した実装で合成した32フレームを全件抽出し、
  2つの64KiBファイルの生成を確認。テストデータは人工パターンでROMを含まない。
- 同encoderで間に無音を置いた2フレームのWAVを作り、既存pcwav raw decoderと
  追加スクリプトで両方を回収できることを確認。
- Pythonの自動テストで参照フレーム、32番号、破損・切断・矛盾する重複の拒否を確認。

```sh
python3 docs/analysis/pc1360k/test_extract_batch.py
PGP_ANALYZE_PC1360K_FAST=1 ./gradlew --gradle-user-home .gradle-local build
```

ローカル解析試験を環境変数を変えて再実行するときは、Gradleキャッシュにより
省略されないよう`:core:desktopTest --tests com.digihori.pgp.core.integration.Pc1360kFastReadTest --rerun-tasks`を使う。
実機回収・録音の連続動作と128KiBの全32ブロックは、受領した録音で検証済み（下記参照）。
ROM由来の録音と出力ファイルはlocal-data以下に保存し、共有ソースへ追加しない。

## 自動電源OFFについて

PC-1360 Operation Manualの印刷ページ20（PDFページ28）「Auto Off」に、
無操作約11分で電源OFFとなる一方、プログラム実行中はAUTO OFFしないと明記されている。
[取扱説明書の該当ページ](https://minuszerodegrees.net/manuals/Sharp/Sharp%20PC-1360%20-%20Operation%20manual.pdf#page=28)
を画像として確認した。サービスマニュアルの15分は自動電源OFF試験で放置する時間であり、
取扱説明書の公称待機時間とは区別する。

今回の一括処理はBASICプログラムを実行したまま読出し・比較・CSAVE Mを繰り返すため、
標準動作では自動電源OFFの対象外と考えられる。PC-1360K実機での長時間一括実行を
確認したという意味ではない。電源OFF防止の未確認RAM書換え等は追加しない。

## 一括録音の回収結果（2026-10-18）

ユーザー提供のkanji-all.wavは16kHz/8bit/モノラル、約64分39秒。
全32ブロックを取得でき、欠番なし、全D=0、各4096バイトの合計と
保存ヘッダーのSUMがすべて一致した。S1の名前・メタ情報・120バイト単位・
端数を含む末尾のチェックサムも全件一致。
以前の3つの4KiB、3つの256バイト、一覧表・READ比較・「あ」の30バイト等、
全既知観測値とも一致した。

選択値ごとに65536バイトへ結合した。生データ・録音・詳細manifest・由来情報は
local-data/analysis/pc-1360k以下にのみ保存。

| selector | 合計 | SHA-256 |
| --- | ---: | --- |
| 0 | 6079681 | `3be0d1efefb08f25f05c7d8725d866b0ac9160566dd53acc53cec63377ed9275` |
| 1 | 7017286 | `fad0c644adbc4cf2f1177c5760d83c4a25cec899d742f0822ed9fa35d06dedd1` |

S/Tとの物理対応や、さらに別の領域へ切り替わる条件は引き続き未確定。
今回の結果は、現在の手順で指定できる2×64KiBの取得を完了したという意味。

### 末尾チェックサムの実機差分

実機のS1 Binary末尾は、最後の端数データ32バイト（rawのニブル交換済み表現）と
最初のFFを累積したチェックサム。次のFFは計算へ含めない。
全32件でこの計算に一致した。参照pcwav encoderは最後のFF単独のチェックサムを
付けるため、旧版の抽出スクリプトが最初の末尾で拒否した。
抽出側を実機方式へ修正し、旧encoder方式は明示的な互換オプションだけに分離した。
検証を省略して受け入れたわけではなく、全件の実機チェックサムを検証した。
参照pcwavのソースは変更していない。

長時間WAVに対しては、参照pcwavのraw decoderと、同じアルゴリズムを
定数メモリで処理する解析専用C++版の出力133409バイトが完全一致した。
C++版のソースはlocal-data以下に保存した（Studio/coreへは追加していない）。
