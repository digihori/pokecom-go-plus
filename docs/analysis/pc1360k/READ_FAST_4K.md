# PC-1360K 4KiB機械語リーダー

> この文書は個別実験の経過記録です。「未取得」「未実装」等は各記述時点の状態を示します。
> 現在のまとめは[PC-1360K 漢字ROM解析とStudio対応](../../machines/PC-1360K.md)、
> 吸い出し用BASICの使い方は[配布用手順書](../../../tools/pc1360k-rom-dump/README.md)を参照してください。

2026-10-18。Studioでの検証と初回4KiBの実機回収・照合を確認。

## 初回の操作

1. [read-fast-4k.bas](read-fast-4k.bas) を**新しいBASICプログラム**として実機へ転送する。
   従来のread-block.basの行60だけを変更する手順ではない。
2. 初期設定のままRUNする。selector 0、DP 0000..0FFFの4096バイトを回収する。
3. SUMとDを控え、各表示でENTERを押して最後まで進める。
4. D=0であることを確認し、録音を開始して次を実行する。

```basic
CSAVE M 53248,57343
```

保存範囲はD000..DFFF、4096バイト。コマンド構文の根拠は
[256バイト版の手順](READ_BLOCK.md)と同じPC-1360取扱説明書。

5. WAV原本またはpcwavでデコードした4096バイトのペイロードと、SUM・Dを渡す。
   ファイル名の例は`read-s0-0000-0fff.bin`。

ファイルのサイズ・合計を確認し、ファイルの0100..01FFが以前の
selector 0の256バイトと完全一致するか照合する。実機でのSUMは現段階では不明。
D=0以外の場合はそのまま報告し、ファイルを正常とみなして合成しない。

## 変更点

従来はBASICから1バイトごとにCALLしていた。今回はCALL 1回で機械語が
4096バイトを保存し、さらに4096バイトを読み直してその場で比較する。
不一致時も最初の取得データは上書きしない。
合計は24ビット、不一致数は16ビットで計算する。
4096バイトすべてが255ならSUM=1044480、全不一致ならD=4096を扱える。
BASICはパラメーター設定と結果表示のみを行う。

## メモリとパラメーター

- 機械語：C000..C11B、284バイト。
- パラメーター：C200=selector、C201/C202=開始アドレスから1を引いた値（下位/上位）。
- 保存先：D000..DFFF、4096バイト。
- 結果：C210/C211=不一致数（下位/上位）、C212..C214=合計（下位から3バイト）。
- C215=機械語完了165、C216=BASIC表示完了90。
- C217..C219=BASICで復元した合計、C21A/C21B=同じく不一致数（検証用）。

上記領域の既存データを上書きする。実機で利用できるRAMであることを確認する。
CPU内部の00..0C、P/Q、スタック位置を保存・復元する。
DPとフラグは保存しない。F出力と通常ROMバンク3400への書込みは含めない。
3600は最後に1となる。

IXでXを1増やしてDPへ設定し、READ（56）で読み、IYSでYを1増やしてRAMへ書く。
検証側は同じDPを再読し、RAM側の値と比較する。
両方のREADの直後をLIB 6Dにそろえている。
A=0の場合はXをFFFFから始め、最初のIXで0000になる。
この連続方式の実機での挙動は、受領するファイルと既知データで確認する。

後続の取得は行60を変更する。Sは0/1、Aは0,4096,...,61440のいずれか。
4096バイト固定であり、A+4095がFFFFを超える設定は使用しない。

```basic
60 S=0:A=0
```

両selectorの各64KiBを4KiBずつ取得する場合は合計32ファイル。
これは論理的な取得範囲であり、全128KiBが物理的に独立した領域と確定したわけではない。
まず初回ファイルを照合し、その後に残りの回収手順を整える。

## 検証

通常の自動テストでは、合成ROM上で以下を確認する。

- 8192回のREADのDP・selector順序、4096バイト保存と再読比較。
- 開始0000とF000、selector 0/1、保存範囲の直前・直後を上書きしないこと。
- レジスタ・P/Q・スタックの復元、完了マーカー。
- 合計の桁上がり（最大1044480）、不一致1件と4096件の検出。

明示的なローカル解析モードでは、実ROMのBASICからロード、CALL、復帰、
SUM/Dの計算とPRINT、表示終了を確認した。
取得済みの0100..01FFを検証時だけREAD結果へ注入する試験でも、
その256バイトが出力の対応位置に保存され、SUM=496980、D=0となることを確認。
それ以外の領域は検証用パターンであり、実機ROMの内容ではない。
この試験はCPUの製品実装や物理マッピングを変更しない。

JDK 21での再現用：

```sh
PGP_ANALYZE_PC1360K_FAST=1 ./gradlew --gradle-user-home .gradle-local build
PGP_ANALYZE_PC1360K_FAST=1 ./gradlew --gradle-user-home .gradle-local :core:desktopTest --tests com.digihori.pgp.core.integration.Pc1360kFastReadTest --rerun-tasks
PGP_ANALYZE_PC1360K_FAST=1 PGP_PC1360K_FAST_FIXTURES=1 ./gradlew --gradle-user-home .gradle-local :core:desktopTest --tests com.digihori.pgp.core.integration.Pc1360kFastReadTest --rerun-tasks
```

現行の一般READ実装ではデータがすべて3、SUM=12288、D=0となる。
これはエミュレータ検証の基準であって、実機に対する期待値ではない。
実機ROM、回収データと生成バイナリはlocal-data以下にのみ保存する。

## 初回4KiBの実機結果（2026-10-18）

selector 0、0000..0FFFのfast4k.binを受領。4096バイト、
実機SUM=255966、D=0。ファイル合計も255966で一致。
0100..01FFは以前の256バイトと全バイト一致し、範囲内のその他の既知値とも矛盾なし。
連続IX/READ/IYS方式の初回回収が、既存の明示DP方式の結果と整合する。
全範囲・selector 1・物理チップ対応を今回だけで確定したものではない。

SHA-256: `174d606f52a76957c6c15414705f2b66bf6a564a4c94f79878d9e4bc15c14a82`

次の回収は同じプログラムの行60を`60 S=0:A=8192`に変更し、
2000..2FFFを取得する。2300..23FFの既存256バイト（あの字形を含む）と
比較できる。保存先とコマンドは同じ。回収ファイル名の例は
`read-s0-2000-2fff.bin`。この次ブロックは未取得。

既存のselector 1、0100..01FFの256バイトと照合できる。
