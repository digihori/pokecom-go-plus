# PC-1360K 選択値2・3の一括回収

> この文書は個別実験の経過記録です。「未取得」「未実装」等は各記述時点の状態を示します。
> 現在のまとめは[PC-1360K 漢字ROM解析とStudio対応](../../machines/PC-1360K.md)、
> 吸い出し用BASICの使い方は[配布用手順書](../../../tools/pc1360k-rom-dump/README.md)を参照してください。

2026-10-18。実機の一括録音を受領し、選択値2・3の回収・照合を確認。
変換キー後の通常ROMの処理で3600への2・3の書込みが観測されたため、
既に回収した0・1と同じ手順で、それぞれの全16ビットDP範囲を取得する。
S/Tチップとの対応や、4つの範囲すべての物理的な独立性はまだ仮定しない。

## 操作

前回のread-all.basが実機に残っている場合、行60だけを変更する。

```basic
60 FOR K=&20 TO &3F
```

当時は`read-all-23.bas`（後の`pc1360k-kanji-dump-23.bas`）を新しいBASICとして転送する方法も使った。
現在の配布ソースは[ページ指定版](../../../tools/pc1360k-rom-dump/pc1360k-kanji-dump.bas)に統合している。
機械語DATA、使用RAM、CSAVE Mの範囲と識別形式は前回と同じ。

1. PC側で録音を開始する。
2. 実機でRUNする。
3. DONEが表示されたら録音を止め、WAVを丸ごと渡す。

途中のENTERや手動のCSAVE M操作は不要。読出し→再読比較→保存を32回行う。
再読不一致があれば保存前にERROR BLOCKとDを表示して停止する。
全0や全FFのデータでも、それだけで異常と決めつけて中断はしない。
転送量は前回と同じ128KiB＋識別ヘッダー。前回の実測は約64分39秒で、
同程度の長時間録音になる見込み。前の録音は保持し、別ファイルへ録音する。

| K（16進） | 選択値 | 読出し範囲 |
| --- | --- | --- |
| 20..2F | 2 | 各4KiB、0000..FFFFの全64KiB |
| 30..3F | 3 | 各4KiB、0000..FFFFの全64KiB |

使用領域はC000..C11B、C200..C21B、C220、CFF0..DFFF。
16バイト識別ヘッダーの番号は32..63となるが、形式バージョンは1のまま。
詳細は[前回の一括回収](READ_ALL.md)を参照。

## 抽出

WAVのまま渡せば解析側で処理する。自身で抽出する場合はpcwavでrawデコード後、
抽出ツールへ期待する選択値を明示する。

```sh
perl /path/to/pcwav-decode.pl raw kanji-23.wav kanji-23.raw
python3 docs/analysis/pc1360k/extract-batch.py --raw-s1 kanji-23.raw \
  --selectors 2 3 --output local-data/analysis/pc-1360k/batch23
```

実機で確認した端数＋FFの末尾チェックサムを既定で検証する。
選択値0・1の抽出は従来どおりで、既定の対象も0・1のまま。
`--selectors 0 1 2 3`で前後両方のrawを渡せば全4選択値を対象にできる。
取得済みのbatchとは別の出力ディレクトリを指定する。

32ブロックすべてそろうと、read-s2-0000-ffff.binとread-s3-0000-ffff.binを
生成する（各65536バイト）。欠番や不一致を隠してゼロ埋めしない。
復元後に0・1との全バイト比較、境界や変換処理が読むアドレスの値を確認する。
Studio側の2・3のROMマッピングは、この取得・照合前には拡張しない。

## 検証

ローカル標準ROMのBASICで、選択値0・1版と2・3版の各32周回・範囲・
保存ヘッダー・データを検証した。検証時のCSAVE Mは内容を取得するCALLで代替し、
READ結果は人工パターンで補っている。2番目のブロックの再読を変えると、
最初の1ブロックだけを保存して停止することも両版で確認。
この試験は実機の2・3の内容や動作を確認したものではない。

抽出側は選択値2・3の32番号、64KiB結合、誤った対象選択値の拒否、
末尾ブロックの欠落時に不完全な64KiBを生成しないこと、
範囲外の選択値・転送破損・矛盾する重複の拒否を自動テストで確認した。

```sh
python3 docs/analysis/pc1360k/test_extract_batch.py
PGP_ANALYZE_PC1360K_FAST=1 ./gradlew --gradle-user-home .gradle-local build
```

環境変数を変えてローカル試験を再実行するときはGradleのテストキャッシュに注意し、
必要なら対象desktopTestへ--rerun-tasksを指定する。ROM由来データはlocal-dataにのみ保存。

## 実機回収結果（2026-10-18）

kanji-all-23.wavは16kHz/8bit/モノラル、約64分32秒。
全32ブロック（番号32..63）、欠番なし、全D=0。
S1のヘッダー、120バイト単位、端数＋FFの末尾チェックサム、および
識別ヘッダーのデータ合計値がすべて一致した。

| selector | 回収サイズ | 合計 | SHA-256 |
| --- | ---: | ---: | --- |
| 2 | 65536 | 7107753 | `9add1283967e118e4b5b90830c96c9a9df280d145bb46f104398707ca6073635` |
| 3 | 65536 | 6170701 | `4f560a68c3c03d131a6df6cc646786c8db8461751dc6ae3f6052e0aa91ea6160` |

### 各64KiBの比較

| 比較する選択値 | 異なるバイト数（65536バイト中） |
| --- | ---: |
| 0 / 1 | 64501 |
| 0 / 2 | 65266 |
| 0 / 3 | 64803 |
| 1 / 2 | 65127 |
| 1 / 3 | 64891 |
| 2 / 3 | 64831 |

すべての組合せで内容が異なり、2・3が0・1の単純な64KiBの再現ではないことを
確認した。選択値0〜3の論理範囲、計256KiBの取得が完了。
S/Tの物理チップとの対応やゲートアレイのビット割当は引き続き未確定。
全64ブロックも一緒に検証し、batch-all以下へ4つの64KiBファイルを出力した。
0→1→2→3順の連結ファイルはread-selectors-0-3.bin（262144バイト）。
ROM本体、録音、raw、詳細manifest・由来情報はlocal-data以下にのみ保存。

取得直後のStudioでは2・3に対してFFを返していたが、その後4面対応を実装。
今回のデータを読み込むと、かな入力から漢字候補・切り替え・確定まで動作した。
詳細は[PC-1360K](../../machines/PC-1360K.md)を参照。
