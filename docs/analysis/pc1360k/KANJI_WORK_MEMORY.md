# PC-1360K：漢字が表示され、入力が確定するまで

2026-10-31開始。既存解析の確認と追加RAM解析の計画。
StudioのMCP接続で追加実験を進めている。各観測の実行済み事項と、後続コードからの予測を区別して記す。

漢字の混ざったBASICの行を表示することと、読みを入力して漢字へ変換することは、
最後には同じ字形表示へつながる。しかし、表示する文字を決めるまでの仕事は異なる。
この違いを入口に、追加RAM `0x2000〜0x27FF` の使われ方を調べる。

## 今回の解析で見えてきた使われ方

2026-10-31の実行観測では、「あ」のかな表示までは追加RAMへの書込みはなく、
変換を始めると管理位置の初期化、辞書読出し値の保持、検索結果の格納に使われた。
結果は `0x2053` から8バイト単位で並び、先頭フィールドがゼロの位置で終端する。
各結果はROM選択用情報、ROM内位置、項目位置を持ち、字形そのものは格納していない。
これは今回通過した変換経路の結果であり、2KiB全域の割当を確定したものではない。

管理位置 `0x237A〜0x237B` がROM内のバイト位置、`0x26D4〜0x26D5` が
別に加算・復元する項目位置を保持し、その値が結果レコードへコピーされる流れを確認した。
現時点のレコード形式は観測29に整理した。以下の経過には、後の観測で修正した仮説も残す。

## 吸い出し時に分かったこと

根拠は[現行の機種資料](../../reference/machines/PC-1360K.md)、
[検証履歴](PC-1360K_HISTORY.md)、[当時の経過](PC-1360K_ANALYSIS.md)。

- 実機から選択値0〜3の各64KiB、合計256KiBの論理イメージを取得した。
- 漢字ROMは通常のPEEKと別経路で読む。`0x3600` が選択値、DPが領域内アドレスとなり、
  READ/READMがデータを取得する。通常ROMバンクは別の `0x3400` で選択する。
- 「あ」のコード `0x2422` からselector 0の一覧表 `0x0156` を調べ、
  字形位置 `0x2378` を求める経路を実機データで確認した。
- この「あ」は30バイトを読み、各半分に空白列を加えて `0xFEB0〜0xFECF` の32バイトへ展開する。
  その後は通常ROMの大きい英字と共通のLCD転送処理へ合流する。
- 4領域を組み込んだエミュレータでは、かな入力、変換、候補切替、採用を確認した。
  変換時にはselector 2・3も読む。辞書形式や検索アルゴリズム全体は未解明である。
- 追加RAMの用途は未確定。過去の「書込みなし」は漢字ROMなしの限定的な入力区間の観測であり、
  実辞書を使った変換にも使わないという証拠ではない。

物理チップと選択値の対応、Fポート等の配線条件は、今回のソフトウェア解析とは別の未確定事項として残る。

## 二つの使い方から追う

| 系統 | 操作 | 解きたい問い |
| --- | --- | --- |
| 表示 | 保存済みの漢字混じりBASIC行をLIST・編集画面で表示 | ソースの符号化、字形取得、改行・再描画に追加RAMを使うか |
| 入力 | 漢字モード、ローマ字、かな、変換、候補切替、採用 | 読み、検索作業、候補、確定文字列をどこで保持するか |

表示の対照には漢字を含む文字列リテラルやコメントを使う。実際に受け付けられる構文と文字コードを先に確認する。
「同じ漢字を表示するが変換はしない」条件を作れば、辞書検索の仕事と字形を描く仕事を区別しやすい。
起動・初期化・CLEAR・モード解除も観測する。これは第三の主用途というより、領域の寿命を知るための対照である。

## まず行う観測

全4領域の実ROMを使い、初期化済み状態をそろえた独立セッションで比較する。
既存の [Pc1360kKanjiLocalTest](../../../core/src/desktopTest/kotlin/com/digihori/pgp/core/integration/Pc1360kKanjiLocalTest.kt)
には起動、WIDTH,2、かな入力、変換、次候補、採用とメモリアクセス取得の土台がある。
この実験を参考に専用の任意実行ハーネスを用意し、製品の動作は変えずに観測する。

| 順番 | 操作条件 | 主な比較 |
| --- | --- | --- |
| 1 | 起動からRAM初期化、待機、WIDTH,2、漢字モードへ | 初期化書込みと入力処理の書込み |
| 2 | 英字A／かな「あ」／子音Kのみ／KA | 字形表示と未完成ローマ字の保持 |
| 3 | 「あ」入力、変換、次候補、採用 | 読み・候補・検索状態の変化 |
| 4 | KANJIで「かんじ」を入力し同様に操作 | 長さに応じた領域の増減 |
| 5 | 同じ漢字を含む保存済み行を再表示 | 変換なしの表示で同じ領域を使うか |
| 6 | 削除、CLEAR、モード解除、再入力 | ポインターの巻戻し、再利用、残留内容 |

各キーは押下と解放を分け、十分な処理時間を取り、画面と処理区間を確認する。
固定サイクル待ちだけで完了と決めず、待機中の対照区間も取り、必要ならROM内の待機位置を調べる。
長い読み・文節操作・境界条件は、短い入力で基礎構造が分かってから追加する。

## メモリの差分だけでは見えないもの

操作前後の2KiBのダンプに加え、命令ごとの読出し・書込みを記録する。
同じ値の再書込みや、一時的に使って元に戻した場所は、前後の差分だけでは消えてしまう。
起動時のゼロクリアだけを見て「変換用」と決めることもできない。

記録する項目は操作名、命令数または累積サイクル、実行前PC、通常ROMバンク、
アクセス種別、アドレス、値、漢字ROM選択値、READ/READM時のDP。
通常のRAM読出しと漢字ROM読出しは経路も記録する。
漢字ROMのDPが `0x2000〜0x27FF` に入っただけの読出しを、追加RAMアクセスに数えない。
観測用ダンプを読むホスト側操作もCPUアクセス集計に混ぜない。

追加RAMだけでなく `0x303C`、`0x3400`、`0x3600`、`0xFD07`、`0xFD08`、
`0xFEB0〜0xFECF` とLCDの観測を結び付ける。
最初は全領域の読み書き回数とPC別集計を取り、実際に触る範囲を絞って詳細ログを読む。
字形ごとの一時バッファと、文字列全体や検索状態を保持する領域は分けて考える。

## 用途を確定する手順

1. 最初の書込み元を通常ROMの「バンク＋PC」で特定する。同じPCでもバンクが違えば別の命令である。
2. その値を後で読む命令へつなぎ、生成元と利用先を追う。必要な範囲だけ逆アセンブルする。
3. 一文字ずつ伸ばした入力で変化する位置を比べ、長さ・文字列・ポインター等の仮説を立てる。
4. 同じ読みの再変換、別の読み、候補切替で、検索中だけの値か保持される値かを確かめる。
5. 必要な場合だけエミュレータの複製セッションで値を一つ変更し、影響を再現して因果関係を調べる。
   通常実行での観測と変更実験は別の記録にする。
6. エミュレータ依存の疑いが残る重要な結論は、対象を絞った実機観測と照合する。

RAM内容が偶然文字コードやアドレスに見えるだけでは、用途を確定しない。
「同じ入力で再現する」「入力変更に追随する」「読出し側の処理と整合する」を根拠とする。
一度の試行でアクセスがなかった場合は、その操作・観測区間に限った結果として記す。

## 読み物としての完成形

本文は「保存済みの漢字を描く」「読みを漢字に変える」「2KiBに何が残るか」の順にする。
各場面で文字コード、辞書、字形、作業領域を結び付け、操作の例から内部の動きへ進む。
アドレス表には、範囲、用途、生成元と利用先のバンク＋PC、寿命、根拠となる実験を添える。
確定事項、観測、仮説を区別し、未解明部分を埋めたように書かない。

詳細な手順・条件・集計は本ディレクトリに残し、安定した説明は機種資料から案内する。
ROMイメージ、逆アセンブルの大量出力、辞書・字形データ、メモリダンプ・LCD画像は
追跡対象へ追加せず、既存方針に従って無視対象の `local-data/analysis/pc-1360k/` 以下へ保存する。

## 観測1：接続時の停止状態（2026-10-31）

MCPでPC-1360Kの停止状態を取得した。これは現在のセッションの途中状態であり、
コールドブート直後と確認したものではない。起動・初期化の経過は遡って判断できない。

| 項目 | 観測値 |
| --- | --- |
| 次のPC | `0x0148`（内部ROM）、通常ROMの選択バンク0 |
| 累積実行サイクル | 205652630 |
| `0x303C` | `0x08` |
| `0xFD07` / `0xFD08` | `0x18` / `0x04`（24文字 / WIDTH 4） |
| `0x2000〜0x27FF` | `0x26DF` の `0xA5` を除きすべて `0x00` |
| `0xFEB0〜0xFECF` | すべて `0x00` |
| Breakpoint / Watch | 登録なし |
| Trace / メモリアクセス履歴 | 無効 |

`0x26DF=0xA5` の生成元・用途は不明。領域内の非ゼロ値が一つという事実から、
この領域が未使用、初期化済み、あるいは特定の構造体であるとは判断しない。
過去のアクセス履歴が無効なので、この停止状態から書込み元を特定することもできない。
生のコンテキストは無視対象の `local-data/analysis/pc-1360k/work-memory/01-paused-baseline.json` に保存した。

次に `0x2000〜0x27FF` 全域へのwrite Watchを提案した。
changeではなくwriteとし、同じ値の書込みも捕まえる。設定はStudioのローカル承認待ちであり、
まだ登録・有効化されたとは扱わない。承認後にTraceを準備し、WIDTH設定・漢字モード・入力の順に進む。
MCPにはキー入力・Reset操作がないため、これらの操作はStudio側で行う必要がある。

## 観測2：WIDTH,2と漢字モードへの移行（2026-10-31）

書込みWatchの承認成功を確認後、ユーザーがContinue、無入力での待機、
`WIDTH,2`＋ENTER、漢字キーの順に操作し、自動停止せず手動Pauseした。
停止時にも全域write Watchが有効であることをMCPで再確認した。

| 項目 | 観測1 → 観測2 |
| --- | --- |
| `0x303C` | `0x08` → `0xA8` |
| `0xFD07` / `0xFD08` | `0x18` / `0x04` → `0x12` / `0x02` |
| 追加RAM全2048バイト | 変化なし。`0x26DF=0xA5`、その他ゼロ |
| `0xFEB0〜0xFECF` | 全ゼロのまま |
| 停止時の次PC | 内部ROM `0x0102` |
| 累積実行サイクル | 215344556 |

今回の操作区間では追加RAMへの書込みWatchは発火しなかった。
漢字モードへの移行だけでは追加RAMへ書かない、という観測となった。
読み出したかどうか、起動時にどう使ったかは、このwrite Watchからは判断できない。

Traceは4096件で有効だったが、1837008命令が実行されており、残っているのは
停止前の4096命令だけである。モード切替全体の命令列を保存できたとは扱わない。
メモリアクセス履歴は引き続き無効・空だった。現在のソース実装ではアクセスWatchのための
CPUアクセス取得と履歴保存の有効化は別であり、履歴が空であること自体をアクセスなしの根拠にはしない。
生データは `local-data/analysis/pc-1360k/work-memory/02-kanji-mode.json` に保存した。

次は同じWatchを保ったままAを一度押し、かな「あ」の表示を確認する。
自動停止すればその最初の書込みを解析し、停止しなければ手動Pauseして
モード・字形バッファ・追加RAMを比較する。変換キーはその後の独立した観測にする。

## 観測3：「あ」のかな表示（2026-10-31）

前の手順でAを一度押した後、ユーザーが手動Pauseした状態を取得した。
同じセッションで全域write Watchが引き続き有効、停止理由はなしだった。

| 項目 | 観測結果 |
| --- | --- |
| `0x303C` | `0xA8` のまま |
| `0xFD07` / `0xFD08` | `0x12` / `0x02` のまま |
| `0x2000〜0x27FF` | 全バイトが前回と同じ。`0x26DF=0xA5`、その他ゼロ |
| `0xFEB0〜0xFECF` | ゼロから字形データへ変化 |
| 字形の照合 | 吸い出し時の「あ」の30バイトに各半分の空白列を足した32バイトと全バイト一致 |
| `0x3600` | 停止時は `0x00` |
| 次PC / 累積サイクル | 内部ROM `0x00EB` / 218647845 |

少なくとも今回の一文字のかな表示では、追加RAMへ書き込まずに
既知の「あ」の字形を通常RAMの `0xFEB0〜0xFECF` に用意できた。
これは表示用の32バイトバッファと追加2KiBを別に考える根拠になる。
ただし追加RAMの読出し有無、別の文字や表示方法、辞書検索での利用はまだ確認していない。
停止時のselector値だけから、処理中の全切替を復元することはできない。

Traceは有効だが末尾4096命令のみで、履歴は依然無効だった。
したがって今回も、字形取得の全命令経路を直接取得したとは扱わない。
生データは `local-data/analysis/pc-1360k/work-memory/03-hiragana-a.json` に保存した。
次は変換キーを一回だけ押し、辞書検索に入って最初に追加RAMへ書く位置を捕まえる。

## 観測4：変換開始で最初の追加RAM書込み（2026-10-31）

変換キーを一回押すと自動停止した、というユーザー報告を受け、同じセッションを取得した。
最終TraceとCPU状態が、通常ROM bank 6の `0x5B5A` で実行した
`ANID 0x00` を示した。直前の `0x5B57` はDPへ `0x26FF` を設定している。
この命令は通常メモリのDP先と即値のAND結果を書き戻すため、`0x26FF` をゼロにする。
停止時の次PCは `0x5B5C`、その命令はRTNだった。

| 項目 | 結果 |
| --- | --- |
| 最初に捕まえた書込み先 | `0x26FF` |
| 書込み元 | 通常ROM bank 6、`0x5B5A` |
| 書込み | `0x00` → `0x00`（同値の書込み） |
| 追加RAMの前後差分 | なし。`0x26DF=0xA5`も変化なし |
| 字形バッファ | 「あ」のまま |
| 累積実行サイクル | 219341391 |

前後ダンプが一致しても、実際には書込みがある例を捕まえた。
write Watchを選んだ意義がここにあり、change Watchや前後差分だけではこの処理を見落とす。
MCPのstop項目自体はnullだったので、停止理由の詳細がAPIから得られたとは扱わない。
自動停止の報告、設定済みwrite Watch、最終命令とDPを合わせた判断である。

Traceにはbank 7側から内部ROMのバンク間呼出し処理を経て、bank 6の
`0x4001` → `0x4004` → `0x5B57` へ入る流れが残った。
したがって今回最初に見えた仕事は、字形を追加RAMに置くことではなく、
変換開始時に `0x26FF` の状態をクリアする短い処理である。
このバイトが具体的に何を表すか（フラグ、件数等）は、後続の書込み・読出しを調べるまで未確定とする。

近傍の未実行コードには `0x2378`、`0x26D6`、`0x26D7` を通常メモリとして扱う命令がある。
これは次に調べる候補であり、今回通過した証拠ではない。
特に通常RAMの `0x2378` と、以前「あ」の字形を読んだ漢字ROM selector 0のDP `0x2378` は、
数値が一致していても異なるアドレス空間である。

生コンテキストと限定逆アセンブルは無視対象のwork-memoryディレクトリに
`04-conversion-first-write.json` と `04-conversion-disassembly.json` として保存した。
次はキーを追加で押さずContinueし、同じ変換処理内で次に書く場所を観測する。

## 観測5：同じクリア処理への二度目の到達（2026-10-31）

Continue直後に再び自動停止した。前回から128命令、1216サイクル後で、
書込み元は再びbank 6の `0x5B5A`、書込み先は `0x26FF`、値は `0x00` のままだった。
追加RAMの非ゼロ値も依然 `0x26DF=0xA5` 一つだけである。

Traceを前回の最終sequence 2595581から区切ると、最初のクリアから戻った後、
bank 6の共通入口でCASE分岐し、`0x40A1` → `0x7853` へ進んだ。
この短い処理はCPU内部RAMのXへ `0xFB00` を設定し、復帰側 `0x405B` を経てbank 7へ戻った。
続いてbank 7の `0x5382〜0x5399` 付近で `0xFDB4` から読み始めた2バイト単位のデータを
`0xFB00` 側と交換する経路が記録され、その後 `0x530F` → `0x637E` → `0x6380` から
もう一度bank 6の共通入口へ入り、今回のクリアで止まった。
ここで扱われたデータの符号化・意味の確定は後続とする。

これにより、`0x26FF` のクリアはbank 6の `0x4004` に入るたびに呼ばれる共通前処理と分かった。
前節の「変換開始時のクリア」は今回の観測場面を表したもので、
変換専用の初期化であることまでは意味しない。このバイトを変換フラグと命名するのは早い。
また、二度の停止は同じ命令から進めずに止まり直したものではなく、
一度別の処理から復帰し、再呼出しされた結果である。

共通入口のCASE命令の後ろには分岐表がある。線形逆アセンブルでは表データまで命令として表示するため、
その部分の表示を実行命令とみなさず、Traceで実際の遷移先を確認する。
生データは `05-conversion-second-write.json`、入口の限定逆アセンブルは
`05-bank6-entry.json` に保存した。
次も同じWatchでContinueし、共通前処理の先で別アドレスへ書くかを確認する。

## 観測6：辞書側の選択と0x26FAへの初期値（2026-10-31）

次のContinueから33命令・426サイクルで、今度は異なる書込みに到達した。
通常ROM bank 6の `0x40D1` が `0x26FA` へ `0x01` を書き、次PC `0x40D2` で停止した。
追加RAMに初めて前後差分が現れ、非ゼロ値は `0x26DF=0xA5` と `0x26FA=0x01` になった。

直前の実行Traceでは、共通入口のCASE分岐から `0x406F` → `0x40C9` に入り、
`0x6A07` → `0x6A20` → `0x6A3E` を通って `0x3600` へ `0x02` を書いていた。
この時点では辞書側の領域を選択したところまで確認できたが、
今回の33命令にはREAD/READMはなく、まだ辞書を読んだとはいえない。

## 観測61：LISTも追加RAMの読書きなしで表示（2026-10-31）

### 次に絞って追う場所

1. `0x2381` からの別表と `0xFBDC〜0xFBE1` の三組。検索結果が何の中間データへ変換されるか。
2. `0x2573` 周辺と `0x26E5` 以降。読みの区切り、選択成分、候補列との対応。
3. `0x2040〜0x2049`。表示の候補数、総量、残数、選択位置を生成する命令と更新関係。
4. 起動・CLEAR・採用・再変換時の有効／無効判定。残存内容と有効状態を区別する管理値。

ここからは同じ既知ループの全書込みで停止するより、処理段階の入口・出口へBreakpointを置き、
短い区間に絞ってデータの生成元と利用先をつなぐ。
読み物には確定した説明を反映し、本記録には予測と観測の差も残す。
