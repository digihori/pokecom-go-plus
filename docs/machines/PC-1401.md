## 2. CPU / ROM / RAM

- CPUはSC61860A08。既存の`Sc61860Cpu`、命令decoder / assembler / debuggerを共用する。
  CPU専用命令の追加が必要という根拠は今回見つかっていない。
- 内部ROMは8 KiB、`0000..1fff`。外部ROMは32 KiB、`8000..ffff`。計40 KiB、bankなし。
- 旧`pc1401mem.bin`は64 KiBのアドレス空間image。ROM component importerは
  上記2領域のみ抽出し、RAM / LCD / holeの内容は破棄する。PC-1261 / 1350と同じROM layoutを使えるが、
  `MachineId("pc-1401")`は独立させ、他機種のROMをサイズ一致だけで同一視しない。
- 回路図には固定2 KiB RAMに加え、PC-1401用2 KiB / PC-1402用8 KiB RAMが示される。
  外部RAM総量は1401が4 KiB、1402が10 KiB。CPU内部RAM、LCD register RAM、
  BASICで利用可能な容量をこの総量へ混ぜない。製品表記の4.2 / 10.2 KBとの換算も別途確認する。
- MAMEの配置を物理busの第一候補とする。

| Range | PC-1401候補 | PC-1402参照との差 |
|---|---|---|
| `0000..1fff` | 内部ROM、読出し専用 | 同じ窓 |
| `2000..37ff` | 未実装領域、RAMとして公開しない | 1402では追加RAM |
| `3800..47ff` | 4 KiB RAM | 1402と共通の窓 |
| `4800..5fff` | 未実装領域 | MAMEでは同じ |
| `6000..67ff` | LCD register aperture | MAMEでは同じ |
| `6800..6fff` | 未実装領域 | MAMEでは同じ |
| `7000..77ff` | LCD aperture mirror候補 | MAMEでは同じ |
| `7800..7fff` | 未実装領域 | MAMEでは同じ |
| `8000..ffff` | 外部ROM、読出し専用 | 同じ窓、内容共通とは未確定 |

MAMEのLCD read/writeは`offset & 0xff`で256-byte registerへ正規化する。
aperture内の繰返し、`7000`側mirror、未接続領域の読出し値は実ROM / 回路図のdecodeで検証する。
Pokecom GOは`2000..7fff`を広くRAMとして扱い、LCDも特定アドレスだけ更新する。
この24 KiB書込み窓を実機RAM仕様として移植しない。解析用書込みを許可する場合も、
物理busとは別の明示的なhost機能として判断する。

発振クロック576 kHzを3 clocks/cycleで換算し、192,000 cycles/sを基準とする。
2026-10-11の全機種監査でPockEmulの576,000/3定義と照合した。
CPUの公称2 ms / 500 ms dividerは384 / 96,000 cycles、ブザーも192,000 cycles/sで換算する。
以前の288,000という仮説は撤回。出典と残るハードウェアタイマー検証はPORTING_NOTESを参照。

## 3. LCD

16文字 × 1行、各文字5×7 dots、論理80×7。文字間gapは1列。
LCD driverはSC43536。Pokecom GOとMAMEは以下の配置で一致する。

- 左8文字: `6000..6027`を順方向。
- 右8文字: `6067..6040`を逆方向。
- `603c` bit 3: STAT。
- `603d` bits 0..6: BUSY, DEF, SHIFT, HYP, PRO, RUN, CAL。
- `607c` bits 0..6: E, M, 括弧, RAD, G, DE, PRINT。
- OUTC bit 0によるdisplay enableは既存のI/O境界を使う。

`Pc1245Display`とは文字数と表示後半の並び方が異なる。Snapshotとdots変換の設計は共用し、
物理register配置とsymbol mapは`Pc1401Display`へ置く。
`DisplaySymbol`にCAL / HYP / STAT / M / 括弧の状態を追加し、E表示の意味・既存ERRORとの対応を確認する。
Studio / Player双方でsymbol labelと表示順を確認する。RUN/PROをhost状態から合成して
ROMのCAL表示と矛盾させない。

## 4. キーマトリクスとモード

Pokecom GOは14 groups × 8 bits。IBの下位7bit用前半7 groupsの最後は空、
IAの下位7bit用後半7 groupsを持つ。MAMEでは空groupを除いた13 groups。
通常の1bit選択のキー配置は一致するが、読取りアルゴリズムは異なる。

- Pokecom GO: IAが0ならIB、IAが非0ならIA側を優先し、最下位選択bitのgroupだけ返す。
  INBは常に0。
- MAME: IA自身を基礎にし、IA / IBの全選択groupをORする。INBはIB latchとpower状態を返す。
  初回起動ではC-CE押下を一時的に模擬する。
- 回路図のIA / IB接続を根拠に専用`Pc1401Keyboard` / Ioを実装し、単bit、複数bit、
  IA/IB同時、同時押し、BREAK/KON、power-upを検証する。起動専用C-CE模擬は必要性確認前に追加しない。

選択とキー配置（列内はbit 0から7、`-`は空）:

| Select | Keys |
|---|---|
| IB0 | +/- 8 2 5 CAL Q A Z |
| IB1 | . 9 3 6 BASIC W S X |
| IB2 | + / - * DEF E D C |
| IB3 | ) ( x² √ y^x EXP X→M = |
| IB4 | STAT切替 1/x LOG LN DEG HEX - M+ |
| IB5 | C-CE F↔E TAN COS SIN HYP SHIFT RM |
| IB6 | - - - - - - - - |
| IA0 | - 7 1 4 DOWN R F V |
| IA1 | - - , P UP T G B |
| IA2 | - - - O LEFT Y H N |
| IA3 | - - - - RIGHT U J M |
| IA4 | - - - - - I K SPACE |
| IA5 | - - - - - - L ENTER |
| IA6 | - - - - - - - 0 |

CAL / RUN / PROの3状態を扱う設計とする。CAL / BASICはマトリクス内の物理キーであり、
既存機種のmode switch RAM値を流用しない。BASICのRUN/PRO遷移とcold / warm reset時の状態は
ROMと取扱説明書で確認する。RESERVEは対応させない。STATは別の`OperatingMode`に増やさず、
ROMが制御する電卓内状態とLCDシンボルとして扱う。

`PocketKey`へCAL / BASICと不足する関数キーを意味単位で追加する。
既存LEFT_PAREN / RIGHT_PARENなどは共用可能。関数は文字列やAndroid resource IDでcoreへ渡さない。
`OperatingMode.CALCULATOR`を追加し、PC-1401の`setOperatingMode`はLCDから状態を判定して
cycleベースのCAL / BASICキー入力を要求する設計を検討する。ROMワークRAMへ値を直書きしない。
入力sequenceの実行は既存host queueが担い、coreはthreadや時刻を所有しない。
実行待ち・遷移失敗の表現は既存Unit APIの限界を確認して最小の追加APIで扱う。

## 5. ブザー

音声はOUTCの変化と経過cycleを入力とする既存設計を共用する。
PC-1401ではcycle rateを設定可能にし、ROM内BEEP入口を捕捉して2 kHzを固定長で鳴らす
Pokecom GOのhookは採用しない。MAMEはMACHINE_NO_SOUNDで、音声照合先として使わない。
BEEPの回数 / 音高 / 無音区間、OUTC oscillator mode、TEST dividerの時間を確認する。
スピーカー出力とPCM再生はhost側に残す。

## 6. BASICと保存形式

OLDのPC-1245 / 1251とは異なるS1系。PC-1261 / 1350とRAM内の行フレームを共用できる。

`FF [line-hi line-lo length body... 0D]* FF`

行番号はbig endian、lengthは行末0Dを含む1 byte。文字はASCII系、keywordは1 byte。
OLDの3桁packed decimalや独自英数字コードを使わない。S2のFE keyword prefixも使わない。
特殊文字の`FB..FE`（参照表のPI / SQR / INS / BX）はROM出力で確認し、
PC-1261 tokenizerのFE半角カナ経路を無条件に有効にしない。

PC-1401 / 1402の参照token tableは一致。
PC-1261にない`81..90`のREC, POL, ROT, DEC, HEX, TEN, RCP, SQU, CUR,
HSN, HCS, HTN, AHS, AHC, AHT, FACが必要。
逆にPC-1261のCLS / CURSOR (`CE/CF`)はPC-1401参照表にない。
PCWAVの表にあるOPEN / SAVE / LOADやgraphics命令もPC-1401へ持ち込まない。
`Pc1401BasicTokenizer`は専用語彙を持たせ、共通S1行処理を明示的な設定へ抽出する。
PC-1350名のresult型を新規機種へ拡散させるかは整理範囲を小さく判断する。

Pokecom GOのRAM管理候補:

- program default start `3800`。
- start pointer low/high `46e1/46e2`。
- end pointer low/high `46e3/46e4`。
- PC-1402のActivityもdefault `3800`を使う。追加RAMをBASICでどう利用するかの証拠にはならない。

`Pc1401BasicProgramMemory`はROMでNEWした直後・1行入力後・削除後のpointer、
開始/終了FFを含む範囲、変数/配列との衝突を確認してからload / extractを確定する。
容量を単純に`46e1 - 3800`で決めない。S1 transfer payloadのtrailer FFとRAM program envelope、
PGP project artifact、`.dmp`のaddress付き形式はそれぞれ分離する。
WAVのS1 codecはPGPではまだ仕様調査段階であり、PC-1401追加と同時に完成させる前提は置かない。

## 7. PC-1402を容量違いだけと扱わない理由

| Item | Pokecom GO 1401 | Pokecom GO 1402 |
|---|---|---|
| CLOAD hook | `9e25` | `9e0c` |
| CSAVE hook | `9d20` | `9d00` |
| BEEP hook | `c014` | `c08e` |
| Keyboard / tokens / LCD | 共通 | 共通 |
| RAM write guard | `2000..7fff` | 同じ広い窓 |

MAMEは`rom_pc1402 = rom_pc1401`とし、RAM mapだけを変える。
Pokecom GOの別ROMファイル / hook差と不一致なので、機種差・ROM版差・参照実装の誤りを
今回だけでは判定できない。1402を1401のRAM設定として公開せず、追加時には独立MachineId、
実ROM版、NEW/MEM、program開始位置、管理pointer、cold/warm resetを個別に検証する。
将来共通化するとしてもRAM decodeとROM identityを別の属性にする。

## 8. PGP統合と実装順序

1. **機種Coreと起動**: `pc1401/`へRomDefinition / importers、MemoryBus、Display、Keyboard、
   Io、Machineを追加。`MachineFamily.PC_1401` / keyboard layout / Catalog / Factoryへ登録。
   ROM layoutは既存8K+32K、generationと基本byte形式はS1。RAM容量設定は初版で公開しない。
   memory trace / physical ROM provenance / checkpointにも対応。synthetic ROM単体テスト後、実ROM起動で未確定事項を解消。
2. **BASICと入力**: PC-1401専用語彙、program memory、CharacterInput / ROM入力列を実装。
   S1共通フレームとPC-1401特殊文字を分離。LCD状態を基準にmode遷移を扱う。
3. **Studio**: ROM library / loader / component converter / locator、機種選択、Project machine ID、
   BASIC compiler / import / export、addressed machine-code loaderへ追加。
   `DesktopKeyboardInput`とlayout、Main.ktのmode / symbol / ROM登録分岐を更新。
   関数キーを省略したPC-1251 layoutへのfallbackはしない。
4. **Player**: `playerShared`の`PlayerKeyboardCatalog`, `PlayerSkinCatalog`, Session / display状態、
   Android ROM登録 / 起動、`controllerUi`のLCD・mode描画を確認して追加。
   Studio export成果物がmachine ID付きでPlayerへ渡る経路を検証。
   既存gamepadのPocketKey mappingを維持し、新しい機種キーの保存・読込みも確認。

共有するのはCPU、ROM component形式、snapshot / session境界、S1の行構造、
project / addressed image / host input / audio出力経路。
専用実装はmemory decode、LCD symbolと並び、キーmatrix / 刻印 / character sequence、
mode遷移、BASIC語彙 / pointerと容量判定。大きなFactory再編はPC-1401追加の前提にしない。

## 8a. 初版の画面レイアウトとPlayer後続検討

2026-10-11、ユーザーとの協議によりPC-1401初版は縦配置を採用する。
LCD → 関数キー6列×3行 → 主キー（英字・数字・矢印・操作キー）の順とする。
現在の幅基準のサイズ追従を維持し、LCDは縦横比を保つ。
LCD右側への関数キー配置や、広幅／狭幅による配置切替は初版では実装しない。
右側配置を後から追加する場合は、上段の基準寸法と共通倍率、最小キーサイズを別途設計する。

関数キーと主キーは別のgridとして定義し、キーIDと通常・SHIFT・BASIC刻印は共通定義を参照する。
配置と表示状態はCoreへ置かず、StudioとPlayerから参照できるpresentation層で所有する。
既存のpress/release経路を使い、CALでも英字キーを自動非表示にしない。
CAL/BASIC・SHIFT・C-CEなどへのアクセスを維持する。
Playerの既存SkinDefinitionは任意rectangle配置が可能だが、画像skinは初版の必須条件にはしない。

### Playerの拡張キー領域（後続検討、今回未実装）

PC-1470Uなど、キー数が多くLCDも24桁×2行となる機種では、全キーの常設により
モバイル画面上のLCDとキーが小さくなる問題がある。
後続案は通常表示をLCD＋主キーとし、関数キー等を拡張領域として必要時に表示する方式。
ユーザーからの例は、トリガーで上からスライド表示し、キーを押すと引っ込む動作。
これは検討候補であり、トリガー、表示位置、自動収納条件は未確定とする。

後続検討ではSHIFT＋関数、長押し、連続入力を妨げない表示・収納タイミング、
LCDを隠す範囲、キーrelease前の収納による押下状態の残留、表示中のサイズ追従を確認する。
初版では関数キーと主キーの定義を分離するところまでとし、拡張領域の仕組みは実装しない。

## 9. 検証計画と今回実施した確認

commit可能なテストは自作synthetic ROMと仕様由来のvectorだけを使う。
ROM、ROMから採取したtrace / RAM snapshot / screenshot / golden dataはcommitしない。

- ROM: componentサイズ、machine ID、所有権コピー、flatからROM領域だけ抽出、ROM書込み禁止。
- Bus: RAM両端、hole、LCD alias、ROM不変、cold resetとprogram保持warm resetの区別。
- LCD: 全80 columns、逆順境界、7 rows、symbol各bit、enable、revision、snapshot不変性。
- Keys: 全物理キー、select各bit、同時押し、IA/IB複数選択、BREAK/KON、mode sequence。
- BASIC: 機種固有関数 / 非対応語彙、文字列 / REM / DATA、line length境界、特殊文字、
  空program、末尾FF、pointer範囲、容量超過時の部分書込み防止、load→LIST→extract。
- 実ROM: cold boot→CAL、CAL/BASIC→RUN/PRO、四則と関数、短いBASIC RUN、
  ROMキー入力と直接loadの一致、NEW/MEM、BEEP / WAIT / TESTの時間、reset時のprogram保持。
  Pokecom GOとは同じROM・同じキーイベント・同じ命令境界で照合し、違いを実機不正と即断しない。
- UI: Studio standalone / Project、ROM登録2形式、外部編集→reload、Player export / launch、
  mode / symbols / 関数キー、既存機種選択とgamepad回帰。

今回実施: baselineとclean tree確認、参照実装・回路図比較。
`local-data/roms/pc-1401/`には8 KiB / 32 KiBのcomponentと64 KiB flat imageがあり、
flatのROM領域がcomponentと一致することだけを確認した。gitignore対象。
PC-1401のエミュレータ実行や実機照合はまだ行っていない。
取扱説明書全体の確認、RAM decodeの厳密なalias、ROM版差、program capacity、
mode遷移 / reset / 時間系は実装初段の検証項目として残る。

指定JDK 21 (`jbr-21.0.11`)で`./gradlew --gradle-user-home .gradle-local build :core:desktopTest`
は成功（既存testは多くがUP-TO-DATE）。`git diff --check`も成功。
変更は調査文書とPORTING_NOTESだけであり、このbuild成功はPC-1401の動作検証を意味しない。


## 10. 初版実装の到達点 (2026-10-11)

第9節の「今回実施」は調査時点の記録。現在はCore、BASIC、Studio、Playerの初版統合を実装し、
ローカル実ROMの起動・モード遷移・科学関数を含むBASIC実行・BEEP PCM生成・
ROM入力と直接ロードの一致を確認した。JDK 21の全体buildとCore回帰テストは成功。
詳細な移植判断と検証範囲は `docs/PORTING_NOTES.md` の「PC-1401初版実装」に記録した。

自動入力は実ROMで欠落が出ない保持40,000 / 間隔20,000 cyclesを採用。
192,000 cycles/sを基準とし、実機時間・音程との比較、最大容量と変数領域、
NEW/MEM、warm reset、Android実機の表示と操作感の確認は残る。
PC-1402対応およびPlayerの拡張領域は含まない。
