# 既存プログラムをAIで解析する

開発版はPC-1245とPC-1251に対応します。
Projectに登録していないプログラムも、利用者が選んで公開した解析用コピーをMCPから読めます。
元ファイルや実行中メモリを自動変更する機能ではありません。

## 取り込みと公開

1. Studioの`プログラム` → `プログラム解析を開く…`を開きます。ROM・Projectは不要です。
2. BASIC、ASSEMBLY、DMP、RAWから入力形式を選び、ファイルを選択します。
3. RAWでは配置先を16進で指定します。機械語の入口が分かる場合だけ入口を入力します。
   省略すると入口は不明のままです。既知情報や調べたいことをメモできます。
4. 「公開内容を確認」で対象名・形式・サイズ・hash・内容の抜粋を確認します。
5. 「解析用コピーをMCPへ公開」を押すと、そのコピーを認証済みMCPクライアントから取得できます。
6. 解析を終えたら「公開を解除」で取得を停止します。画面を閉じるだけでは解除しません。

取り込み・公開はStudioのローカル画面だけで行います。AIへ任意パスを渡してファイルを読ませるAPIはありません。
ファイル選択時の内容を保持し、公開時やMCP読取り時に元ファイルを再読込みしません。
元ファイルを更新した場合は選び直して確認・公開してください。保持するのは最後に公開した1件で、
アプリ再起動で消えます。公開内容は外部AIへ渡り得るので、必要なファイルだけを選んでください。

## 入力の範囲

- BASIC／AssemblyはUTF-8。BOM除去・改行正規化後のソースを読み取ります。
  構文不正なプログラムの調査にも使えるよう、取り込み時のBuildは行いません。
- DMPは既存のPGP DMP parserを使い、配置アドレスを保持します。
- Raw Binaryは明示した配置先とバイト列から解析します。拡張子だけで種類を自動推定しません。
- ファイルは最大64 KiB、ソース1行は最大8192文字、バイナリは合計4096バイトです。
  PC-1245とPC-1251の両方で、UTF-8のBASIC・アセンブリ、アドレス付きDMP、生の機械語を選べます。
- バイナリは選んだ機種の標準RAMとそのミラーに限定します。PC-1245の標準RAMは
  `0xC000..0xC7FF`、PC-1251は `0xB800..0xC7FF` です。取り込んだアドレスは逆アセンブルにそのまま使います。
  ROM・LCD・未割当領域や、ミラーの境界をまたいで物理アドレスが連続しないセグメントは拒否します。
  解析対象の機種は実行中のエミュレーターとは独立します。

## AIへの依頼

MCPサーバーを起動・接続し、次のように依頼します。

> Studioで公開した解析対象を、pgp_get_analysis_contextのmetadataから確認してください。
> ソースまたは取り込んだバイトの逆アセンブルと、PGPの機種知識を使って解析してください。
> 確認できた事実は対象ID・revisionと行番号／アドレスを根拠に示し、推定・未確認事項と分けてください。
> ファイルの直接参照、変更、Load、実行は不要です。

metadataは引数なしで取得できます。本文取得には返されたtargetIdとrevisionを指定します。
変更前のIDを再利用せず、`STALE_ANALYSIS_TARGET`ならmetadataを取り直します。
古いIDから以前の公開対象を取得することはできません。

ソースは物理行番号付きでページ取得します。物理行1がBASICの`10 ...`である場合もあり、
BASIC行番号と区別してください。逆アセンブルは指定アドレスから線形に行い、空白区間を読まず、
末尾の不完全な命令はDBで返します。データが命令に見える場合もあるため、実行コードと断定しません。

## 実行観測を追加する場合

解析用コピーの公開自体はエミュレーターへLoadしません。入口の指定も実行済みを意味しません。
metadataの`importLoadsEmulator=false`はこの取り込み操作の性質であり、現在のSessionが未ロードであることを意味しません。
実際のLoad・実行状態はこのAPIでは追跡しないため、`runtimeCorrespondence=notTracked`を返します。
TraceやDebug Contextを使う場合は、利用者が適切な機種・Load・起動操作・停止条件を用意し、
取り込んだバイト列と停止中のMemory等を照合してから関連付けます。現在の実行メモリとの一致は自動判定しません。
観測したSession ID・revision・アドレスを別の根拠として記録してください。

Continueは現在PCからの再開であり、RUN／CALL入力ではありません。
無限ループを終了として待ち続けず、Breakpointや明示的Pauseを使います。
最終Memory値だけから途中の書込み順を断定しないでください。

### 最小機械語で再現する手順

[検証用DMP](../../test-data/analysis/pc1245-loop/README.md)を作業用フォルダーへコピーして使います。
この例は`0xC100`を書き換え、無限ループするため、既存データのない検証用Sessionを用意します。

1. `loop.dmp`を解析画面でDMPとして選び、入口`C000`を指定して確認・公開します。
2. PC-1245を一時停止し、`プログラム` → `マシン語をロード…`で同じDMPをLoadします。
3. 停止中の`pgp_get_debug_context`で`0xC000`から14 byte、`0xC020`から4 byteを取得し、
   公開対象の逆アセンブルに含まれる18 byteとすべて一致するか確認します。
   この例の空白区間や観測用`0xC100`はimage hashの対象外です。
4. デバッガーで入口`0xC000`のBreakpointと命令Traceを有効にします。
   MCPから設定する場合は`pgp_propose_debug_action`を使い、Studioで内容を確認して承認します。
5. 実行を再開し、RUNモードのBASICで`CALL 49152`を入力します。
   入口で止まったことを画面・CPUのPC・停止理由で確認します。ContinueはCALL入力の代用ではありません。
6. 3命令StepしてPC=`0xC006`で`0xC100=0x41`、さらに3命令Stepして
   PC=`0xC023`で`0xC100=0x42`を、別々の停止中Contextとして取得します。
7. 1命令StepしてRTN後のPC=`0xC009`を確認し、さらに2命令Stepすると
   PC=`0xC000`、A=`0x09`、`0xC100=0x42`になります。ここで停止したままにします。

9命令のTrace順は`C000 → C003 → C005 → C006 → C020 → C022 → C023 → C009 → C00B`。
Traceは命令履歴であり、各書込みの値そのものを記録する履歴ではありません。
上の手順では2つのSTD直後のMemory取得を併用して、途中の`0x41`とその後の`0x42`を実測します。
各取得のSession IDが同じこと、revisionが観測順に進むこと、実行後も対象バイトが一致することを確認します。
Traceがtruncatedの場合、取得できた末尾の範囲だけを根拠にし、起動前からの全履歴とは扱いません。

AIには次のように追加依頼できます。

> 公開対象のmetadataとdisassemblyを取り直し、停止中のDebug Contextと照合してください。
> memoryRangesは[{startAddress:49152,length:14},{startAddress:49184,length:4},
> {startAddress:49408,length:1}]、traceLimitは9です。
> 静的な推定、現在のMemory値、命令Traceで観測できた順序を分けて説明してください。
> 追加の操作提案・Load・実行は不要です。

結果には次の区別を残します。

| 区分 | 記載する内容 |
| --- | --- |
| 確認できた事実 | 対象ID／revision、取得したソース行やバイト・アドレス、実際に行った観測 |
| 推定 | 処理目的、コード／データ区別等の解釈と、その根拠 |
| 未確認 | ROM ABI、入力条件、外部コード、実行される分岐、未取得領域、実機動作等 |

機種知識は[カタログ](../reference/knowledge/README.md)、MCP接続は[接続ガイド](AI_CONNECTION_GUIDE.md)を参照。
