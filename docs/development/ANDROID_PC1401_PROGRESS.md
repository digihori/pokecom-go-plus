## 手順2の実装

- 既存の1280×548画像を座標系とし、共有Playerの`Pc1401KeyboardLayout`にある
  メイン58キーと関数18キーの領域を定義した。

## ROM不要の確認画面

Debugビルド限定の`Pc1401SkinProbeActivity`を追加した。
通常のホームからは遷移せず、Releaseには含めない。
ROM Library・設定・プログラムファイルを読み書きしない。
画面確認用の独自に生成したCPU命令でLCDの交互ドットと全状態表示を点灯するため、
実機ROMの起動表示やモード状態を再現するものではない。
キー操作は画面内で押下・解放を記録し、実ROMへの入力確認とは分ける。

```sh
adb shell am start -n com.digihori.pgp.player/com.digihori.pgp.player.android.Pc1401SkinProbeActivity
```

起動時に`--ez regions true`を付けると領域枠、`--ez lcd true`でLCD拡大表示、
`--ez systemBars true`でシステムバー表示を確認できる。
別条件で開き直す際は、メニューを閉じてAndroidの戻るで確認画面を終了してから起動する。

```sh
adb shell dumpsys activity com.digihori.pgp.player.android.Pc1401SkinProbeActivity --skin-probe
```

このDebug専用dumpは、確認画面内のキー押下・解放の集合と表示中のキー中心座標を出力する。
外部キーボード入力や実際のPlayerセッションの入力内容は収集しない。

## 手順3：機種選択・ROM管理・Session切替

### 実装

- ホームの機種一覧はPC-1245とPC-1401。登録状態は現在のSessionとは別に、ROM Libraryから機種ごとに取得する。
  PC-1401には「対応確認中」を表示し、機種対応完了とは案内しない。PC-1350は追加しない。
- 同じ機種でPlayerとホームを往復する場合はSessionとRAMを維持し、従来の実行・停止意図を維持する。
  別機種への切替はRAMとロード済みプログラムの破棄を確認した後、新Sessionを生成してCPUを自動実行する。
  新Sessionでは表示を全体表示に戻す。
- ホームからの切替確認はキャンセル／Androidの戻るでホームへ、ROM管理からの操作は一覧へ戻す。
  ファイル選択のキャンセルも呼出元へ戻す。選択機種と呼出元はActivityのsaved stateにも保持する。
- ROM管理は登録・復元・置換・削除・使用機種選択の既存基盤を利用する。保存後にホームの登録状態を更新する。
  保存／読込失敗やキャンセルでは、確認前のROMとSessionを保持する。
- pgromはmanifestの機種と選択機種の一致を要求する。
  legacyは選択機種のインポータを使用し、64KiBのサイズだけで機種を推測しない。
- メニューの「動作モード」はPC-1245／1251／1261系だけに表示する。
  PC-1401など他機種は本体スキンのキーで切り替え、動作モードのメニュー項目を表示しない。
- PC-1401はROM本来のCALで起動し、CPUの自動実行とは分ける。
  共有Playerの起動・Reset時のモードfallbackもCALとし、PC-1245のRUNを維持する。
- アプリ再起動時は選択機種と保存済みROMを復元し、ホームで待機する。
  RAM・ロード済みプログラム・実行状態はプロセス終了後に復元しない。

### 自動検証

生成したByteArrayと一時ディレクトリを使用し、実際のROM LibraryやROM由来fixtureを使用しない。

- 64KiB legacyの選択機種別解釈、pgrom機種不一致・対象外機種・不正サイズ・破損アーカイブの拒否。
- PC-1245とPC-1401の共存、保存先からの復元・選択、PC-1401の置換・削除とPC-1245の保持。
- PC-1401の置換失敗時に旧ROMとPC-1245の選択を復元すること。
- PC-1401 Session間のRAM分離、同一Sessionの一時停止でのRAM維持、ResetでのRAM初期化とCAL fallback。
- iOSのpgrom受付は引き続きPC-1245限定。共有カタログへの追加でiOSの機種対応を広げないこと。
- JDK 21の全体build、Core desktop tests、共有Player desktop／iOS Simulator、Android unit testsが成功。
  最終結果はAndroid unit 26件、共有Player desktop 24件、iOS Simulator 28件、Core desktop 435件（失敗なし）。
  Coreの実ROM条件付きテストの件数を、Androidでの実ROM確認件数とは扱わない。

### Androidエミュレータ確認

- PC-1245の既存登録を保持したままPC-1401の未登録行が表示されること。
- ホームからのファイル選択キャンセル、配置済みPC-1401 pgromの登録、登録後のホーム更新。
- PC-1401のプレイで実ROMがCAL表示になり、CPUが自動実行されること。
- CALの確認用入力「1」を保持した同機種のホーム往復と自動再開、明示PAUSEの維持。
- 切替確認のAndroid戻る／キャンセルでPC-1401の選択とSessionを維持すること。
- PC-1245への切替とCPU自動実行、PC-1401へ戻ると新SessionのCAL「0」になること。
- 背景からの通常復帰はPAUSED、プロセス再起動後はPC-1401の選択と両機種のROM登録を復元すること。
- 設定→ROM管理の両機種表示、使用中ROMの削除警告とキャンセル、置換pickerキャンセルの一覧復帰。
- PC-1401の置換にPC-1245 pgromを指定すると拒否し、両機種の登録を保持すること。

エミュレータでは既存のPC-1245 ROMを削除・置換せず、PC-1401を追加登録した。
実ROMの削除・置換確定は行っておらず、そのデータ操作は一時領域の自動テストで確認した。
Android実機、PC-1401の全入力・モード遷移・入出力・ゲームパッドは後続の確認とする。


## 手順4：シンボル配置・入力・モード・実行操作

### 実装

- 利用者提示のLCD配置図に合わせ、上段左にBUSY／DEF、中央寄りにSHIFT／HYP、
  右寄りにDE・G・RAD、右端に( )・M・E、下段左にCAL／RUN／PRO、右にSTAT／PRINTを置く。
  表示枠とドット領域は共有スキン座標で管理する。PC-1401のシンボルは太字とする。
- 状態はCoreのLCD snapshotから取得する。モードのメニューや独立切替ボタンはPC-1401には追加しない。
  本体のCAL／BASICキーを使用するため、UIからの非同期モード要求APIは追加しない。
- Physical入力の短押し保持と解放間隔に、既存MachineDefinitionの40,000／20,000 cyclesを適用する。
  PC-1245の11,520／19,200 cyclesと入力所有権・フォーカス処理は維持する。
- F2をCAL、F3をBASICへ対応づける。テンキーの括弧キーは本体の括弧へ直接対応づける。
  SHIFT＋数字を文字へ変換する処理は追加しない。対応しない機種では既存の許可キー判定で拒否する。
- Debugのオンデマンドdumpに機種・現在モード・LCDシンボル・押下中キー数を加える。
  キー内容やROM／プログラムデータを記録・永続化せず、Releaseではこのdumpを使用しない。

### 自動検証

- 上段・下段のシンボルの順番、ドットとの分離、角度単位の連続配置、左右のグループを確認。
- PC-1401の短いCAL／BASIC入力を実行CPUサイクル数だけ保持し、解放間隔を挟むこと。
- 停止・機種変更時に短押し保持と未入力キューを破棄すること、PC-1245のタイミングへ切り替えられること。
- JDK 21の全体build・Core desktop tests・共有PlayerのiOS Simulator testsが成功。
  Android unit 28件、共有Player desktop 25件、iOS Simulator 29件、Core desktop 435件が失敗なし。
  Coreの条件付き実ROMテストの件数は、以下のAndroidエミュレータ確認とは区別する。

### Androidエミュレータでの確認

実ROMは既存の登録済みPC-1401 pgromを使用した。タッチはADBの画面操作、外部入力はkeyboardソースの
KeyEvent注入で行い、USB／Bluetoothキーボードや実機での指の操作感とは区別する。

- 実ROMのCAL起動とCPU自動実行、本体BASICキーのCAL→RUN→PRO→RUN、CALキーでの復帰。
- F2／F3の短押しでも同じモード遷移となり、実際のLCDシンボルが変わること。
  PC-1401には動作モードのメニューを追加していない。
- SHIFT／DEFの単独入力とLCD表示、短い連続入力A〜Zの表示と入力キュー消化。
- 小数計算12.5＋2.5＝15、√9＝3、テンキー括弧による(1＋2)×3＝9。
- M・HYP・括弧・ゼロ除算時のEと解除、DRGによる角度表示の3状態の切替。
- キー入力した確認用の`10 GOTO 10`をRUNし、Esc／BRKで「BREAK IN 10」へ戻ること。
  このループ中の観測はLCD消灯で、BUSYの実ROM点灯を確認したものとは扱わない。CPUはBRK後もRUNNING。
- タイトルバーのPAUSE→ホーム→同機種プレイはPAUSEDを維持し、RUN操作で復帰すること。
  メニューのResetでCALへ戻り、CPUが自動実行されること。
- 物理SHIFTを1.8秒保持したままPAUSE・メニュー・背景へ移ると、入力所有権が解放されること。
  メニューを閉じると入力フォーカスが戻り、背景復帰時はPAUSEDを維持すること。
- 画面上のSHIFTキーを押したまま背景へ移っても押下を解放し、復帰・Reset後に残らないこと。
- PC-1245のPhysical入力、RUN／PRO、RUN／PAUSEの回帰確認と、PC-1401専用F2／F3の許可キー判定。
- ROM不要の表示確認画面で15シンボルを全点灯し、通常表示とLCD拡大表示で図の配置を確認。

## 手順5：BASIC／DMPのロード・セーブ

### 実装

- Androidの既存OpenDocument／CreateDocumentと共有Playerの入出力を再利用する。
  CoreのS1 BASIC変換・管理ポインタ更新、RAM判定、型付きエラーを変更していない。
- セーブのアドレス例を機種別の`MachineMemoryLayout.assemblyStartAddress`から取得する。
  PC-1401は4400／44FF、PC-1245は従来のC500／C5FFを表示する。
- 同梱ヘルプにPC-1401のS1形式、保存時の空白正規化、RAM 3800〜47FF、
  DMPによるBASIC・管理情報の上書き、ロード中止時の停止を記載した。
  他アプリへの共有は追加していない。

### 自動検証

JDK 21で全体buildとCore desktop testsを実行し成功。
Android unit 28件、共有Player desktop 29件、iOS Simulator 33件、Core desktop 435件が失敗なし。
PC-1245の既存入出力テストとiOSの対象機種制限も維持する。

追加したPC-1401の共有Playerテスト4件は、独自作成のNOPW命令列とテキストを使用する。
実ROMやROM由来fixtureは使用・追加しない。

- BOM／CRLFを含むBASICの解析、S1への配置、3800の開始マーカーと46E1のポインタ、
  テキストへの正規化と別Sessionへの往復。事前checkがRAMを書き換えないこと。
- 容量超過（標準開始位置の容量3808 bytes）・機種不一致時に既存RAMが変わらないこと。
- 不連続DMPと3800／47FFの境界、範囲外・ROM・LCDを含むロードの全体拒否とRAM保持、
  セーブ範囲の検証。DMPによるBASIC・管理ポインタの明示的上書きも確認する。
- 実行中の共有API呼出しの拒否、不正テキストの解析失敗。

### Androidエミュレータでの確認

既存登録のPC-1401実ROMを使用し、独自作成の短いBASICとDMPを専用の検証フォルダへ配置した。
ファイル選択・保存はAndroidのDocuments UIをADBで操作した。実機のタッチや外部document providerとは区別する。

- `10 PRINT "STEP5"`／`20 END`のロード成功後にCPUが自動再開する。
  RUNコマンドをキー入力するとLCDにSTEP5を表示する。ロード時のRUN自動入力は行わない。
- BASICをファイルへセーブし、正規化された内容を比較。保存済みBASICの再ロードでも
  PAUSEDからCPUが自動再開する。
- DMPのロード後にCPUが自動再開し、4400〜4403をセーブすると独自の4バイトと一致する。
  保存したDMPの再ロードでもPAUSEDからCPUが自動再開する。
- 47FFから2バイトを指定したDMPは、4800の利用者向けエラーで拒否され、CPUは停止する。
  エラー時のRAM不変は上記の自動テストで別途検証する。
- セーブダイアログのキャンセル、保存先選択のキャンセルとも、開始時RUNNINGなら再開する。
  明示的なPAUSEで開いた場合は、保存完了・完了表示を閉じた後・保存先選択のキャンセルの
  いずれもPAUSEDを維持する。
- ロード選択のキャンセルはPAUSEDで復帰する。CPU状態だけでなく、Player画面への復帰と
  モーダル解除を確認した。ファイル選択画面内の上位フォルダへの移動やIMEを閉じる操作は、
  選択キャンセルとは区別する。

### 後続と未確認

Android実機、他のdocument provider、Activity／プロセスがファイル選択中に破棄される場合は未確認。
ゲームパッド等は次の手順6で扱う。PC-1350、サウンドは対象外。
保存済みROM・登録セット・既存のプログラムファイルは変更しない。
検証用テキストとBASIC／DMP往復用セーブ先はDownload内の専用フォルダを使う。
PAUSE中の保存確認も別名の検証用ファイルを新規作成し、既存ファイルを上書きしない。

## 手順6：ゲームパッド・入力所有権・回帰

### 実装

- PC-1401の共有`GamepadKeys`と既存Androidアダプターを再利用する。
  メイン58キーと関数18キー、計76キーを割当可能とし、Coreのキー受付まで確認する。
- 設定の入口はホームの「設定」→「コントローラ設定」。対象キーの機種名と、
  割当が全機種共通の1セットであることを表示する。機種別保存は追加しない。
  PC-1401固有キーはPC-1245へ切り替えても保存したまま、PC-1245への送出だけ抑止する。
- Androidの入力受信条件にActivityのresumed状態を明示する。既存のCPU状態・フォーカス・
  ホーム・メニュー・設定・入出力ダイアログによる抑止、所有者別解放とニュートラル待ちは再利用する。
- 同梱ヘルプに接続・割当・機種非対応キー・復帰後の押し直し・対象外入力を記載した。
  OSで認識済みの1台を使い、アプリ内ペアリングや新しい権限・通信は追加しない。

### 自動検証

JDK 21の全体buildとCore desktop testsが成功。
Android unit 28件、共有Player desktop 32件、iOS Simulator 36件、hostInput desktop 10件、
Core desktop 435件が失敗なし。iOSのゲームパッド機能拡張は行っていない。

追加の共有Playerテスト3件は、独自のNOPW命令列によるSessionを使用する。

- 全76キーをゲームパッド割当→HostKeyState→Coreへ送信し、受付・解放・重複down抑止を確認。
- 同じキーをタッチ・外部キーボード・複数パッドボタンで保持し、最後の所有者まで保持すること。
  SHIFTと他キーの同時押しを独立して解放すること。
- 受信停止／モーダル相当・Reset・切断／再接続・機種切替の解放とニュートラル待ち。
  PC-1401のBASIC割当をPC-1245では送らず、保存した割当をPC-1401で再利用できること。

### Androidエミュレータ：ROM不要のアダプター検証

Debug限定の`GamepadProbeActivity`とAndroid標準uinputで一時的な仮想ゲームパッドを使用した。
ProbeのSessionは生成した命令列だけで構成し、ROM Libraryを読み込まない。
設定保存は専用名前空間に隔離し、通常の`gamepad`設定が前後で変わらないことを照合した。
仮想パッドは検証終了時に切断する。ReleaseにはProbeのActivity・manifestを含めない。

```sh
adb shell am start -n com.digihori.pgp.player/com.digihori.pgp.player.android.GamepadProbeActivity
adb shell dumpsys activity com.digihori.pgp.player.android.GamepadProbeActivity --gamepad-probe
```

- AndroidのGAMEPAD／JOYSTICK機器としての認識・1台の選択、KeyEventの押下・解放・リピート抑止。
- 同じNUM_4への2ボタン割当とSHIFT同時押し、所有者ごとの解放。
- キー型十字キー、HAT型十字キーと斜め入力、スティック軸をキー入力にしないこと。
  キー型とHAT型は別の仮想機器構成で確認した。
- モーダル相当の受信抑止、有効解除、Reset、割当変更による解放とニュートラル待ち。
- CAL割当のPC-1245での抑止とPC-1401への復帰、機種切替時の押下解放。
- Activityを背景へ移すと解放し、復帰時に保持中ボタンを再送せず、離して押し直すと入力できること。
- 2台目の入力を無視し、選択中の機器を押下中に切断すると解放すること。
  接続済みの2台目へ勝手に入力元を切り替えないこと。

### Player本体のエミュレータ回帰確認

仮想パッドを切断してから、既存登録の実ROMでPlayer本体を確認した。

- ホームの設定からコントローラ設定へ進み、「対象キー：PC-1401」と共通割当の説明が表示される。
  通常設定は編集せず、戻る操作でホームへ復帰する。
- PC-1401のCAL起動、Physical F3でのRUN切替と数字入力、CPUのRUN／PAUSE、
  明示的PAUSEを保ったホーム往復と再開。
- PC-1245への機種切替・CPU自動実行・Physical数字入力、PC-1401への切替復帰とCAL起動。

### 検証の限界

上記の仮想パッド検証はAndroidアダプターと共有Core受付の確認であり、実ROMを動かしたゲームでの
全ボタン操作確認ではない。その後、実機のゲームコントローラー基本動作についてユーザーからOKの報告を受けた。
接続方式や各操作の詳細は未特定のため、USB／Bluetooth両方式、機器別の印字・配列・不足ボタン、
自然な短押し、切断・再接続のタイミング差を網羅したとは扱わない。
ゲームパッドの短押しは直接押下・解放であり、Physicalキーボードの最小保持補正は適用しない。
PC-1350、音声、RAM拡張等は追加しない。

## 実機レビュー：旧Androidのステータスバー領域

2026-10-15、実機のゲームコントローラー動作はユーザー確認済み。
併せてHUAWEI P20 lite・3ボタンで、タイトルバー上にステータスバーが残るとの報告を受けた。
接続端末はAndroid 9（API 28）。端末固有の識別子は本書へ記録しない。

修正前の実機では、ステータスバーの非表示を要求するViewフラグは設定されていたが、
WindowのFULLSCREEN指定がなく、タイトルバー上にステータスバー相当の空白が残っていた。
Android 10以前ではWindowの`FLAG_FULLSCREEN`も併用し、`onResume`でも非表示設定を再適用する。
Android 11以降は従来のWindowInsetsControllerによる制御を維持する。
3ボタンのナビゲーションバーとノッチの安全領域は維持し、端末側のナビゲーション設定は変更しない。

全体build・Core desktop testsが成功。HUAWEI実機で修正版をデータ保持で更新し、
上部の空白がなくなることを実表示で確認した。実機・新Androidのエミュレータともに、
メニューを閉じた後と背景復帰後も余白が戻らず、PAUSEDを維持することを確認した。
本修正はCore・iOS・Studioを変更せず、ROM登録・保存済みプログラム・通常の設定を変更しない。
