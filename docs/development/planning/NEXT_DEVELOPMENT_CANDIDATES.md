## 複数Projectを束ねる作業セット案（2026-10-30見直し）

コンパイラを利用するゲームが複数あるため、コンパイラ本体を各ゲームProjectへ複製する構成を見直します。
ゲームとコンパイラは独立したProjectとし、上位の作業セット（仮）がProjectの場所を参照する案を第一候補とします。
既存のAssembly Workspaceと名称が混同しないよう、UI上の呼称は別途決めます。

```text
作業セットA                 作業セットB
├── ゲームA Project         ├── ゲームB Project
└── コンパイラProject ──────┴── 同じコンパイラProjectを参照
```

- Projectはソース・Build成果物等の単独管理単位として維持する。
- 作業セットはProjectへの参照を持ち、コンパイラのファイル本体をコピーしない。
- 複数Projectを開き、選択中のProjectに対してBuild／Loadする。選択変更だけではROM切替・Reset・Loadを行わない。
- 一つのEmulator Sessionで補助Projectと作成対象Projectを扱い、ロード済み領域と状態をProjectごとに管理する。
  別々のEmulatorを起動する機能とは区別する。
- 最初は各Projectの明示ロードを基本とする。依存関係に沿った自動Build／ロード順・起動操作の一括実行は後続で検討する。
- 同じコンパイラProjectを更新すると参照するゲームにも影響する。将来必要なら版固定・参照先切替を検討する。
- 参照パス、移動後の再指定、同じProjectの重複登録、作業セット未使用での従来Project単独利用を設計する。

### サブプロジェクト方式との比較

親Projectが子Projectを外部参照する方式でも共有は可能です。ただし、ゲームがコンパイラを
所有するのか、依存するのか、ロードするだけなのかを整理し、自動Buildや依存の循環も設計する必要があります。
当面の目的は独立Projectを同時に扱うことなので、作業セットによる並列管理を第一候補とし、
外部参照型のサブプロジェクト／依存関係は比較候補として保持します。詳細仕様は未確定です。

## 先行案：Project内のプログラムグループ（比較・履歴）

現在のProjectは全ソースを一つのBuild／Load単位として扱い、BASICソースもProject全体で1件に制限しています。
コンパイラ本体と作成対象を同時に登録すると、不要な一括ロードやBASIC数の制限が問題になります。
単なるファイルツリーの分類だけでなく、独立したBuild／Load単位が必要です。以下は見直し前の構成例です。

仮の構成例：

```text
Project
├── 作成対象
│   └── ゲームのソース等
├── 補助ツール
│   └── ポケコンパイラ／LC-3本体等
└── 生成物
    └── Emulator上で生成されたマシン語の保存先等
```

「メイン／サブ」は仮称です。表示名は任意にできるグループを基本候補とし、
コンパイラ専用の固定2カテゴリにするか、複数の任意グループにするかは今後決めます。
生成物は入力グループと区別し、Project更新で自動的に入力へ混ざらないようにします。

### 最初に改善したい操作

1. 補助ツールのグループを選択してロードする。
2. 作成対象のソースをロードする。同居可能なコンパイラ本体を毎回ロードし直さずに済むようにする。
3. ポケコン側でコンパイラを起動して変換する。
4. 生成されたマシン語を指定範囲からDMP等へ保存し、実行・デバッグする。
5. 作成対象だけを修正・再ロードし、繰返し確認する。

Buildでホスト側の内蔵／外部Assemblerを実行する操作と、Emulator上のコンパイラを動かす操作は別です。
最初はグループ単位のロードを中心に設計し、起動キー列・CALL等の自動実行や一括手順は後続候補とします。

### 設計時に確認する事項

- グループごとのソース一覧、Build／Load状態、既定グループ、任意名と選択操作。
- BASICの1件制約をグループ内の単位へ移す。ただし実機に複数の独立したBASIC領域があるとはみなさない。
  BASICの再ロードによる置換・末尾クリアが補助プログラムを壊さないか確認する。
- 補助プログラム・入力ソース・生成マシン語・ワーク領域の配置と、保存すべき領域を明示する。
  他グループとの重複を検査し、意図した上書きや同居不能のケースを区別する。
- Reset、機種／ROM／RAM設定切替、手動ロード・メモリ編集で、各グループのロード済み表示を無効化する条件。
- 生成マシン語の保存範囲・開始アドレスを記録する方式。任意RAMの全保存やセーブステートとは区別する。
- 旧Manifestの読み込みと、従来の単一Build／Loadの移行方針。
- Projectツリー、Assembly Workspace、Debuggerのソース対応、MCPのグループ指定・承認・Build成果物管理との整合。
- ポケコンパイラとLC-3それぞれの実際の操作順・配置・起動方法で受入れを行う。第三者アプリ本体は同梱しない。
