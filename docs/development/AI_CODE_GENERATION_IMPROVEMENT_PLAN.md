# AIコード生成の品質・承認回数の改善計画

記録日 2026-11-19。新しいチャットで再開するための合意事項と作業状態。

## 目的

初めて使うユーザーが、公開用の自然文プロンプトから、構成が読みやすく変更しやすい
プログラムを生成できるようにする。コード品質は生成側の基本要件とし、ユーザーに
ループ化・共通化・メンテナンス性を毎回指示させない。
MCPの情報取得と、変更・ビルド提案の往復を減らし、承認負担も改善する。
実装改善後のAIクライアントでの再試験は後日実施する。

## PC-1350先行課題の評価基準

ロケットと音階の各試行で、生成ソース、Build診断、Studioの実行結果を根拠として
各項目を「合格／要修正／未確認」で記録する。該当しない項目には理由を添える。

| 項目 | 判定に使う根拠 |
| --- | --- |
| 画像データと共通描画 | 画像をデータとして定義し、転送ループを複数コマで使う。画像定義と転送処理をソースで確認する |
| 位置更新 | 座標をループで更新し、端やVRAMブロック境界での移動と旧位置の消去をLCDで確認する |
| 時間と音階 | 機種クロック、ループ回数、命令サイクルからコマ間隔・音程・音の長さを計算し、実行時の観測値と照合する |
| メモリ範囲 | Build成果物の配置と実行時の書込み先を機種のRAM・VRAM仕様に照らし、BASIC領域との重複と画面外への書込みがないことを確認する |
| 復帰 | 変更するレジスター・I/O状態のうち復帰に必要なものを保存・復元し、通常経路の最後でBASICへ戻ることを確認する |
| MCP操作回数 | 検索・個別取得・変更提案・Buildの呼出しと、クライアント側／Studio側で表示された承認を別々に数える |

## 承認回数を増やさない工夫

- 検索結果と本文・構造化データをまとめて取得し、作業に必要な範囲だけを返す。
- 同じ機種・カタログの取得済み知識をチャット内で再利用する。不足項目のみ追加取得する。
- BASICとAssemblyを準備してからProject作成を提案し、同一ソースの関連変更を集約する。
- Build前に構文、配置、時間、保存・復元を確認する。失敗時は診断を取得して原因を特定する。
- 同じ失敗が続く場合は方針を見直し、必要なら小さな描画から確認する。
- operationの完了後に不要な再取得を繰り返さない。途中状態の確認には適切な間隔を設ける。
- 書込み・Build・Load・実行に必要なStudio承認は保つ。
  クライアント側の読み取り承認とStudio側の操作承認をそれぞれ記録する。

承認数を固定値で保証せず、同じ課題の試行で取得回数、変更提案数、ビルド回数とともに実測する。

- Claudeは253行で、タイトルとロケットを機械語で描画し、画面幅を使って移動した。BASICの最終ソースは `CALL &6000`。利用者は `pgp_get_knowledge` の承認が多いと報告した。11月19日の添付ログのStudio向け呼出しは重複を除いて39件で、ツール名、知識ID、承認件数は特定できなかった。
