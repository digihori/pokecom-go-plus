# Pokecom GO Studioとpc-1251 emulatorの連携について

こんなことを妄想しています。

Pokecom GO Studio（以下Studio）で開発したプログラムを、pc-1251 emulator（以下1251emu）へボタンひとつで転送する。1251emuの実機に近いスキンやキー操作で動かし、気になる動作があったらStudioのデバッガーで中身を調べる。そんなふうに、二つを並べて使えたら楽しそうです。

まずは方向性をご相談するための構想です。APIの細かな仕様や実装範囲は、実現しやすい形を一緒に考えられればと思っています。

## ざっくりとした世界観

**Studioを開発・解析の作業場、1251emuを実機感覚で動かす本体として使う**イメージです。

```text
Pokecom GO Studio                         pc-1251 emulator
┌─────────────────────┐                 ┌─────────────────────┐
│ プロジェクト・ビルド  │ ── 転送 ──────→ │ BASIC・マシン語を実行 │
│ ソース・ラベル表示    │                 │ スキン上でキーを操作  │
│ デバッガー・逆アセンブル│ ←─ 状態取得 ─── │ CPU・メモリ・LCD      │
│                     │ ── 停止・ステップ→ │                     │
└─────────────────────┘                 └─────────────────────┘
```

Studioには「1251emuへ転送」のようなボタンを設け、BASICや、アセンブル済みのマシン語・データを送り込みます。転送後は1251emuの画面で、普段どおりに操作して動かします。

さらに、1251emuで動いているCPUの状態やメモリをStudioから参照でき、可能であれば停止・再開・ステップ実行もできるようにしたいです。外部接続中のStudioのデバッガーは、1251emu側を操作対象にします。Studioでステップを進めた結果が、1251emuのLCDにも反映されるイメージです。

デバッグ機能を両者で完全に揃える必要はありません。**外部連携で使える機能はStudio内蔵デバッガーの一部でよく、1251emuが提供できる情報・操作だけを使う**方針です。取得した情報を逆アセンブルやソース・ラベル表示と組み合わせ、開発に役立つ形にする部分をStudioが担当します。

## こんな使い方ができたら

### 1. 作ったプログラムを、実機のような画面ですぐ試す

1. 外部エディターでソースを編集し、Studioでプロジェクトをビルドする。
2. 「1251emuへ転送」を押し、BASICとマシン語・データをまとめて送る。
3. 1251emuのキーで`RUN`や`CALL`を入力し、表示や操作感を確かめる。
4. 修正して再ビルド・再転送し、動作確認を繰り返す。

ファイルを個別に選んで読み込む手間を減らし、開発から動作確認までをつなげます。

### 2. 動作中のプログラムを止めて、中身を調べる

1. 1251emuでゲームなどを動かす。
2. 気になる場面で、1251emu側またはStudio側からCPUを一時停止する。
3. Studioでレジスター、メモリ、現在位置の逆アセンブルを確認する。
4. Studioで1命令ずつ進め、レジスターやメモリ、1251emuのLCDの変化を見る。
5. 調査が済んだら実行を再開する。

ここでいう一時停止は、ポケコンのBRKキーによる中断とは別の、CPUを命令の境界で止めるデバッグ用の停止です。

### 3. 転送したコードを、ラベルやソースと照らして追う

1. Studioでアセンブルしたプログラムを1251emuへ転送する。
2. 停止時のPC（プログラムカウンター）を取得し、Studioが保持するラベルやソース行との対応を表示する。
3. ブレークポイントにも対応できれば、調べたいルーチンの入口で止めて処理を追う。

1251emuにはCPUの状態や停止機能を提供してもらい、ビルド結果との照合や見せ方はStudio側で担当する想定です。ソースとの対応は、転送したビルドと実行中のコードが一致していると確認できる場合に表示します。

## API実装のイメージ

同じPC上で動く二つのアプリを、ローカルAPIで接続する形を考えています。例えばHTTP＋JSONであれば、Pythonの1251emuとKotlin/JVMのStudioの間でも連携できます。通信方式は、1251emu側に組み込みやすい方法をご相談できればと思います。

通常の実行は1251emu内で完結し、転送やデバッグ操作のときだけ通信します。CPUの1命令ごとに常時通信する構成は想定していません。

| APIの役割 | 内容のイメージ |
|---|---|
| 接続情報・対応機能 | 現在の機種、RAM構成、APIのバージョン、利用可能な操作を取得する |
| プログラム転送 | BASICテキストと、番地付きバイナリの複数セグメントをまとめて読み込む |
| 実行状態の取得 | 実行中／停止中、停止理由などを取得する |
| CPU・メモリの参照 | 提供可能なレジスター、内部RAM、指定範囲のメモリなどを取得する |
| 実行制御 | CPUの一時停止、再開、1命令ステップを行う |
| ブレークポイント（追加候補） | 指定番地の命令を実行する直前に停止する |

BASICはテキストを渡して1251emu側で機種に応じて読み込み、マシン語はStudioでアセンブルしたバイト列を渡す案です。1251emu側にStudioのプロジェクト形式やアセンブラーを実装していただく必要はありません。

APIが返す対応機能に応じて、Studioの操作を有効・無効にします。例えば、メモリ参照だけに対応する段階でも利用でき、後からステップ実行やブレークポイントを追加できる形にしたいです。

## 役割分担と、最初の一歩

| Studio側で担当すること | 1251emu側にご相談したいこと |
|---|---|
| 接続設定と転送ボタン | ローカルAPIの窓口 |
| ビルド、転送データの準備 | 対象機種・容量などの検証と読み込み |
| デバッガー画面、逆アセンブル、ソース・ラベルとの対応表示 | CPU状態・メモリの取得と、可能な範囲の実行制御 |
| 未対応機能の表示、通信エラーの案内 | CPU実行ループと安全に連携する処理 |

最初から全機能を揃えず、まずPC-1251で次の流れを試せたらと思っています。

**Studioでビルド → 1251emuへ転送 → 1251emuで実行 → 停止 → Studioで状態を確認 → 可能なら1命令ステップ → 再開**

その後、共通の仕組みでPC-1245／1261／1350などにも広げられれば理想的です。

文字コード・特殊文字の表記、ロード失敗時の復元、停止中の状態取得、左右の画面から操作した場合の調整、接続先の識別などは、具体化するときに別途相談したいです。BASICの行単位ステップや、高度なTrace・履歴機能も後続の検討で十分と考えています。

1251emuの実機らしい操作感と、Studioの制作・解析機能を組み合わせて、ポケコンのプログラムを作って試す楽しさを広げられたら、という提案です。
