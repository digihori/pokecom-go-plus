# PC-1360K：読みを漢字に変える2KiBの仕事

2026-11-24更新。実機から回収したROMをStudioと独立Coreで実行し、
読みを候補に変える手順と、文字コードから画面を描く手順を追った。
ROM・ワークRAM・文字確定・字形表示の関係は[1ページの概説](../../analysis/pc1360k/ANALYSIS_OVERVIEW.md)、
個別の実測条件は[ワークメモリの観測記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)を参照。

## 字形を描く仕事と、描く文字を決める仕事

「あ」を入力すると、文字コードから漢字ROMの一覧表を調べ、字形の位置を求める。
以前の吸い出し解析では、selector 0の `0x2378` から30バイトを読み、
各半分に空白列を加えて通常RAM `0xFEB0〜0xFECF` の32バイトへ展開する経路を確認した。
今回の入力実験でも、同じバッファの内容が回収済みの「あ」と全バイト一致した。

その間、追加RAM `0x2000〜0x27FF` への書込みはWatchで捕まらず、内容も変わらなかった。
追加2KiBを字形全体の一時置場と考える説明は、少なくともこの一文字表示には当てはまらない。
ただし読出しを含めて一切使わないと確認したわけではない。

変換キーを押すと、違う仕事が始まる。
通常ROM bank 7からbank 6の処理を呼び、読みを検索用の表現へ用意し、
追加RAMと通常RAMの管理位置を初期化して、漢字ROMの辞書側データを調べる。
調べた結果を8バイト単位の表に残し、その後に候補の選択・表示へ進む。

```text
かなのコード → 字形の位置を調べる → 字形を展開 → LCDへ転送

入力の読み → 検索用の表現 → 辞書を走査 → 追加RAMの結果表
                                              ↓
                                    候補の選択状態 → 文字の表示
```

8バイトの結果表から5バイトの別表を作り、後続の読みを照合して候補ワークを確定する。
候補選択はワークが指す辞書項目を取り出し、必要な仮名を補って表示へ渡す。

## 同じアドレスでも、読んでいるものが違う

通常のメモリ読出しと、漢字ROMのREAD/READMは別の経路である。
たとえば通常RAMの `0x2378` と、selector 0のDP `0x2378` は別の場所になる。
通常ROMバンクは `0x3400`、漢字ROMの論理領域は `0x3600` で選ぶ。
命令を特定するときも、PCだけでなく通常ROMのbank番号を併記する必要がある。

今回の「あ」の辞書検索では、selector 3の `0x760A〜0x760B` から読んだ値を
通常RAM `0x26D5`、`0x26D4` に保存するところを捕まえた。
その後selector 2へ切り替え、追加RAMに保持した位置をXへロードし、
DP `0x0000` から別の辞書データを読み始めた。
追加RAMは、ROMを参照する位置や走査中の状態を置く役割を持っている。

## 辞書のバイト位置と、項目の位置

`0x237A〜0x237B` は下位・上位順の16ビット値で、漢字ROM内の読出し位置として使われた。
一方 `0x26D4〜0x26D5` は、ROMの表から初期値を得て加算し、
作業レコードへ保存して後で復元する別の16ビット値だった。

「あ」の走査では、最初のROM項目から次へ進むとき、
バイト位置は `0x0000 → 0x0005`、後者の値は `0x0000 → 0x0001` となった。
次はバイト位置が `0x0005 → 0x0009` へ進み、項目位置が2になった。
ROM項目の長さはヘッダー由来の値で変わるが、項目を進む数は1ずつ増える。
二つの位置を分けて保持する理由が、ここに見える。
候補表示では、ワークが指す表から辞書の参照位置を取り出し、項目内の選択位置に従って表記を読む。表示順と辞書内の順の対応は、後述の履歴で変わる。

## 8バイトの結果表

今回の経路では、結果表は `0x2053` から並んだ。
新しい結果を置くと、前のゼロ終端をレコード先頭で上書きし、8バイト先に新しいゼロを置く。
二件目・三件目でも同じ構造を確認した。

| レコード内の位置 | 実測で分かった内容 |
| --- | --- |
| +0 | 元表側の読み消費量。「あ」は1、「かんじ」では1・2・3 |
| +1 | 枠内の辞書項目数。新規時1。継続項目を加えると増える |
| +2 | ROM由来の属性値。現在のレコードと比較して、統合か新規かを分ける |
| +3 | ROM領域を選ぶための情報。`0x3600` へ書く値そのものとは限らない |
| +4〜+5 | ROM内位置、上位→下位 |
| +6〜+7 | 項目位置、上位→下位 |

管理位置の16ビット値と、レコード内の直列化ではバイト順が逆になっている。
表全体に一つのバイト順を当てはめると取り違える。

「あ」では8項目分が7レコードへまとまった。ROMヘッダーの上位3ビットが7の
継続項目を、直前に採用した枠へ加えたためである。コードには、現在枠の属性と
新しい項目の属性が一致した場合にも項目数を増やす分岐がある。
観測202で分類7の経路を実測し、属性一致の経路は静的に確認した。
「かんじ」では29レコード・39項目分となり、先頭フィールド別には次のように分かれた。

| 先頭フィールド | レコード数 | まとめた項目数 |
| --- | ---: | ---: |
| 1 | 17 | 19 |
| 2 | 9 | 15 |
| 3 | 3 | 5 |

この段階の1・2・3は「か」「かん」「かんじ」に対応する読み消費量。画面側の候補数は、別表の絞込みとワーク生成を経てから計算する。

## 管理位置から見える作業の分担

| 通常RAMの位置 | 今回の経路で確認した使い方 |
| --- | --- |
| `0x2372〜0x2373` | 結果表の終端＋1を保持し、新規レコードで8ずつ進む |
| `0x2374〜0x2377` | 検索表の基点を保持するポインタの組。後段検索は2374/75を参照する |
| `0x237A〜0x237B` | 漢字ROM内のバイト位置 |
| `0x237C〜0x237D` | 結果表の位置をYへ取得して書込み・検査に使う |
| `0x2380` | 新規レコード格納前に1減らす枠の制御値。統合時は減らない |
| `0x26D4〜0x26D5` | ROM走査時の項目位置。加算・保存・復元する |
| `0x26D6` | 漢字ROM領域の選択に使う情報 |
| `0x2573〜0x2577` | 別の5バイト作業状態。末尾2バイトにROM位置を上位→下位で保存する経路を確認 |
| `0x2578〜0x2579` | 通常RAMへの書込み先ポインターとして使う |

追加RAM以外にも `0xFB00` 側の入力、`0xFB29` 側の検索用表現、
`0xFBA7` 側の中間レコードなどがある。変換状態が2KiBだけで完結するわけではない。

## 「感じ」から「幹事」へ

「かんじ」を変換すると、ユーザーの目視で「感じ」と「候補6」の表示を確認した。
その時点で `0x2040=6`、`0x2041=6`、`0x2043=0` だった。
変換キーをもう一度押すと、`0x2043` が0から1へ進み、
表示は「幹事」と「候補5」、`0x2041` も5となった。

したがって画面上の6→5と、内部の選択位置0→1は別に扱う必要がある。
この経路では `0x2042` を上限側として比較し、同値なら選択位置をゼロへ戻す。
「あ」では上限側が1だったため、再押下してもゼロへ戻って「亜」のままだった。
「かんじ」では上限側が4で、最初の再押下はゼロへ戻らず1へ進んだ。

候補送りは群の中でも進む。複数成分があるワークでは、まず特殊成分、次に後段、
前段の順に項目位置を繰り上げ、そのワークを一巡すると次の群へ移る。

## 採用と、RAMに残る状態

候補を採用すると編集入力に戻る。「感じの」の実測では採用直後に入力欄とカーソルが表示された。
BASICのプログラム行を保存する場合は、編集した行をENTERで登録する。

「亜」と「幹事」をそれぞれ採用した後も、追加RAMの2048バイトは前後で同じだった。
結果表が残っていても、その内容を有効な変換状態として使い続けているとは限らない。
採用を、領域全体のゼロクリアで見分けることはできなかった。

字形バッファも同様に、待機時の内容だけでは表示の成否を判断できない。
候補の「亜」「感じ」「幹事」が表示されていても、確認した待機時には全ゼロだった。
一方、採用後には非ゼロの字形が残る場合があった。
描画時の一時バッファとLCDに残る表示、変換中の有効状態とRAMに残る値を区別して追う必要がある。

候補を覚える履歴にも、値がRAMに残っていても参照されない状態がある。
その有効範囲と、通常のCLEARで初期化する領域は後述する。


## 5バイト表で読みと候補を結び付ける

追加RAMの2381から始まる5バイト表は、元の8バイト表を番号で参照する。
各枠は読み消費量、元表番号、項目数、属性、追加参照符号の順。先頭00で終わる。

元表の属性が27未満なら、そのまま別表の属性に使う。27以上なら、
漢字ROM selector 3の間接表から3バイトの組を読み、入力の残りと照合する。
この照合は読み消費量を0〜2バイト延ばす。同じ消費量・元表番号で次の組も一致すると、
既存の枠の追加参照符号を更新する。観測68の「かんじ」では元表29件と読みから
別表18件を再構成でき、順序と全バイトが一致した。消費量1→2と2→3は保存データで確認した。
独立Coreの観測196では、KANJIYOなど4入力で別表の消費量が2→4に延びた。
KANJIREでは別表の延長後、後段の終端判定で不採用になった。

### 読みの続きを照合する

5126は5バイト表の属性と追加参照符号を、漢字ROM selector 3の
16バイト境界の参照位置へ変換する。追加参照符号FFは第2参照を省略する。
例えばA9はCA90を指す。後続の読みから選んだROMの2バイト記述子は、
参照へのオフセット、ビットマスク、次の参照符号を作る。
参照位置へオフセットを加えて読んだ値とマスクのANDが非ゼロなら、
その組を次の参照位置の再構成に採用する。

5126が入力終端に着いたときは、その時点の有効参照の先頭バイトを使う。
いずれかのbit 7が立っていれば終端を許可する。読みが残っていればビットマスクで
後続を照合し、成功した組が指す参照へ置き換えてから終端を判定する。
「かんじの」ではC077のAFとマスク04が一致し、次の符号76からC760へ進み、
「の」を1バイト消費した。この後続消費量はワーク+10に入り、
別表生成時の延長分は別表+0に入る。

追加参照が終端と後続照合の両方を変える例もある。「きれ」は
別表に属性15・追加参照FFの枠と、属性15・追加参照1Dの枠を作った。
C150だけを調べる前者は終端を許可せず、「ば」を受け入れる。
C1D0も調べる後者は、C1D0の先頭bit 7によって終端を許可し、
C1D0の別のビットによって「と」も受け入れた。両方とも「の」は不成立だった。
他の語でも同じ属性・追加参照と同じ残りの読みなら同じ結果になることを、
観測197・198の独立Core再現で確認した。

### 表を再利用し、確定したワークを選ぶ

ワーク生成時は別表の消費量を降順に試し、同じ消費量の候補は表の順に試す。
「かんじの」の最終ワークは、元の消費量3、別表番号15・16・17、
項目数3・1・1、追加消費量1を持つ3件だった。

その変換で、起点1の別表には先頭00の後ろに非ゼロ値が残った。
独立Coreで再現すると、先に「の」側の後続検索が表を作り、
次に「ん」側の起点1の検索が表先頭を00へ戻して辞書の索引判定で復帰した。
後続の値や終端後ポインタは先行検索から残り、先頭00で走査が止まる。

確定したワークは257Fから17バイト刻みで並び、先頭FFの枠で終わる。
共通のフィールドと、後段成分の展開先は以下のとおり。オフセットは10進。

| ワーク位置 | 内容 | 表示管理領域 |
| --- | --- | --- |
| +0 | 入力バッファ内の起点 | 2044周辺の起点側成分の判定に使う |
| +1〜+3 | 先頭側の読み消費量、別表番号、項目数 | 2046〜2048 |
| +4〜+6 | 後段別表側の読み消費量、別表番号、項目数 | 2049〜204B |
| +7〜+9 | 符号7側の読み消費量、6バイト要素番号、項目数 | 204C〜204E |
| +10 | 後続照合で消費した量 | ワーク確定時にFC2Fから保存 |

KANJIHENKANでは先頭側が3バイト、後段別表側が4バイトを消費した。
後段成分の項目数は2で、候補送りで204Aが0→1と進む。
上限に達すると204Aが0へ戻り、先頭側の項目位置2047が進む。
符号7の成分が有効な場合、項目位置204Dがそれらより先に進む。
画面側の通し番号2041は候補送りごとに減り、1の次に項目数の総計2040へ戻る。
生成と選択の命令、再現で取得した値は観測181〜191に記録した。

### ワークから候補数を計算する

5384は有効なワークごとに、使える各成分の項目数を掛け、全ワークの積を2040へ加える。
例えばKANJIHENKANは先頭側の項目数が3・1・1で、いずれも後段側が2項目なので、
3×2 + 1×2 + 1×2で10候補になる。後段側の項目数は後段別表から再集計する。
算出は描画前に行われるため、同じ表記に到達する異なるワークも別々に数える。
「きれ」では候補番号が2→1に変わり、両方とも「切れ」と表示された。
ワーク内の積と2040への加算はそれぞれ1バイトで折り返す。
通常入力KIKANKOUSEISHIでは、先頭ワークの6×9×9=486が230となり、
残り2件の81ずつを加えた392も折り返して2040は136になった（観測210）。
候補送りは通し番号と別に項目位置を進める。この入力では136回目で番号が戻っても
項目位置は進み、ワークと項目位置の全648組を一巡した（観測211）。
KIKANTAISEIKOUでは合計256が0に折り返す。最初の候補は描画され、
以降の変換キーによる候補送りは2041=0で終了する（観測212）。
最初の候補はPROモードのPRINT文に文字列として登録できる（観測213）。

### 辞書の表記と入力から補う仮名

5A68は別表が指す元表を選び、辞書項目の表記を候補バッファFB7C側へ出す。
元表枠の中で何件目かを指定すると、5CBDは各ROMヘッダーの下位5ビットに1を
足した分だけ進む。継続項目のヘッダーでは次のバイトから表記を読む。
「かんじの」の同じ元表枠ではROM位置4839、483E、4842から
「幹事の」「漢字の」「監事の」の順に選んだ。
5A10は入力の読みを仮名として補う。別表が元表より長く読みを消費する場合は
その差を補い、最後の呼出しでまだ残る読みを終端まで補う。
観測199・200では候補バッファの書込み元を追い、次の内訳を確認した。

| 表示候補 | 辞書側の表記 | 別表で延ばした分 | 最後に補った分 |
| --- | --- | --- | --- |
| 切れば／着れば | 切／着 | れ | ば |
| 食べれば | 食べ | れ | ば |
| 食べよ | 食べ | よ | なし |
| 感じれば | 感 | じれ | ば |
| 幹事返還 | 幹事、返還 | なし | なし |

「食べれば」と「食べよ」は同じ8バイトの元表枠を選び、別表属性は
それぞれ15と21に分かれた。「きれ」では異なる元表枠から同じ「切れ」が
2候補出たため、内部の候補数には同じ表示文字列が含まれることがある。
これらは取得した項目・表記の対応であり、属性全体の言語的分類は未確定。
具体的なアドレス、再現条件、選択箇所は[詳細記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)の
観測196〜203にまとめた。

## 保存済みの文字コードから画面を描く

`10 PRINT "A幹事B"` のLISTでは、プログラムRAMから読んだ
「幹」の保存コード `8A B2` を内部ROM `0x02A5` の処理でJIS
`0x3434` へ変換し、通常ROM bank 1の `0x5013` へ渡した。
「事」もJIS `0x3B76` で同じ入口へ進んだ。

字形索引で格納位置を求め、selector 0から「幹」は25バイト、
「事」は19バイトをREADMでCPU内部RAMへ取得した。
どちらも `0xFEB0` 側の32バイトの字形バッファへ展開し、LCDへ送る。
混在行の英字は通常ROMから字形を取り出してLCD転送へ進む。

この行のLISTとPRINTでは、追加ワークRAM `0x2000〜0x27FF` への
読書きWatchは発火せず、前後の内容も変わらなかった。読み変換で使う
候補表は、保存済み文字を描くこの経路では使われなかった。

## 選んだ候補を覚えて、次の変換で先頭に出す

「かんじの」を変換すると、履歴のない状態では先頭に「幹事の」が現れた。
そこで「漢字の」へ候補を切り替え、採用してから同じ読みを再入力すると、
次の変換では先頭に「漢字の」が現れた。画面の候補番号は5、内部の表示位置は0のままである。
この変化を、追加RAMへの保存から辞書項目の取出しまで追跡できた。

### 通常の読み変換では辞書項目を参照する4バイトを残す

通常の読み変換では、末尾の `0x2700〜0x27FF` に辞書を参照する4バイトを保存する。
今回の「漢字の」の候補変更では `01 48 39 01` が書かれた。

| バイト位置 | 意味 | この例 |
| --- | --- | --- |
| +0 | 一次表に保存されたROM選択符号 | 01 |
| +1/+2 | ROM内位置（上位・下位） | 4839 |
| +3 | 辞書項目内の位置 | 1 |

選択符号をそのままハードウェアのROMセレクタ値とは解釈しない。
候補送りで6074に入ると、対象の辞書項目を履歴に保存する。
PROモードのPRINT文では、閉じ引用符とENTERによる行登録で履歴は増えず、
対照入力の履歴が2枠進んだのは行登録前に候補を送った時点だった（観測213）。
同じ読みの次の変換では、先頭3バイトの一致判定を通り、末尾の項目位置1が読み込まれた。

### 保存情報から表示候補までの経路

履歴の照合は、現在の候補群に対応する辞書位置を使って行う。
同じ符号・ROM位置に対する記録が複数ある実験では、後方の記録の位置2が優先された。
この結果は次の領域を通って表示側へ届く。

| 段階 | 領域・処理 | 確認した内容 |
| --- | --- | --- |
| 記録 | 2700〜27FF | 辞書参照3バイトと項目位置1バイト |
| 照合 | 6475のルーチン | 3バイト一致後に項目位置を取込む |
| 集約 | 26E2/26E3 | 一致した記録の走査順と、候補群を通算した項目位置 |
| ワーク保存 | 17バイトレコードの+11/+12（10進） | 上の2値を保存 |
| 表示側へ展開 | 2050 | ワーク+12の値を受け取る |
| 項目番号変換 | 59B0のルーチン | 表示位置から実際の辞書内位置を求める |

保存位置1を持つ3項目群では、取出し番号は次のようになった。

| 内部の表示位置 | 履歴なしの辞書内位置 | 保存位置1がある場合 |
| --- | --- | --- |
| 0 | 0 | 1 |
| 1 | 1 | 0 |
| 2 | 2 | 2 |

右列は全3項目で実測した。保存した項目を先頭へ移し、残りの項目の順序を保つ。
辞書本体の並びを変更せず、取出し番号を変える仕組みである。
一般の保存位置h・表示位置kについてコードを読むと、k=0ならh、
1≦k≦hならk−1、それより後ろならkを使う。ただし全てのhと項目数を実験したわけではない。
複数履歴から選ばれた位置2についても、表示位置0から辞書位置2への変換を確認した。

先頭側に加えて、後段別表と符号7の項目位置も同じ番号変換を使う。
独立Coreでは、KANJIHENKANの後段別表の位置1が2051へ、
KANJITAIの符号7の位置3が2052へ再展開され、次回の表示位置0で選ばれた。
1回の候補送りで先頭側と後段側の記録を2枠へ保存する例も確認した。

### 履歴は候補群の並びにも使う

通常の読み変換では、418Dがワーク列に終端を書き、6314が各ワークの履歴を照合する。
候補群を作る走査では、入力起点が0のワークは+11を比較値に使う。
起点が非ゼロなら、+11と起点側の履歴順位26F9の大きい方を使う。
まず比較値が非ゼロのワークを降順に並べ、次に比較値がゼロのワークを
読み消費量の降順に並べる。同順位の一部では、後続成分の符号7の照合結果
（ワーク+15）を比較し、リスト内の隣接要素を入れ替える。

リストは26E4から始まり、0始まりのワーク番号を並べてFFで終わる。
群位置2043からリストの番号を読み、257Fから17バイト刻みのワークを選ぶ。
KANJIYAKUの独立Core再現では、符号7のFC06側を選んで保存すると、
次の変換でリストが 00 01 02 03 04 05 FF から 01 00 03 02 05 04 FF に変わった。
物理ワーク列の先頭11バイトは各ワークで一致し、表示リスト上の3組が入れ替わって
FC06側が先頭に移った。書込み先を採取した5回は、すべてその走査の開始位置以降だった。

55B3の書込み先が現走査の開始位置より前になるには、その走査の最初の採用で
比較値が0のまま特殊入替えが成立する必要がある。さらに物理的に隣接するワークの
前件が特殊要素0、後件が非ゼロ要素で、前件だけが走査の対象から外れる必要がある。
通常入力1,620通りでこの要素順の隣接対を433組確認した。全組で起点・読み消費量・
前段別表番号・項目数が一致し、両件が別の走査に分かれる条件は見つからなかった。
複製元の先頭と不採用要素の処理を含む根拠は[履歴仕様](../../analysis/pc1360k/HISTORY_SPEC_STATUS.md)の
観測214〜218にまとめた。前の走査をまたぐ上書きの実入力例は未確認。

### ▲▼キーで選ぶ変換では文字コードを保存する

WIDTH,2で漢字キーの後に▲▼を2回押すと、FF03の下位2ビットが2になる。
この状態で変換すると、bank 6の6952が履歴を新しい記録から逆順に調べ、
先頭がFFの記録の文字コードを候補表2200と照合する。
一致した候補を2100の先頭側へ移し、残りを元の順で続ける。
周回後も有効範囲を逆順に読み、同じ候補を重複して先頭側に追加しない。
2形式を混在させた独立Coreの境界試験で、有効4枠だけを読むことを確認した（観測223）。

同じ独立Coreで `KANJI` を変換したとき、候補表の先頭は
`25 34 / 26 34 / 27 34` だった。数字2で選ぶと
`FF 26 34 00` が履歴に入り、同じ読みの再変換では
`26 34 / 25 34 / 27 34` に変わった。数字1で先頭を選んだ対照では
履歴を追加しなかった。再現手順は[履歴仕様](../../analysis/pc1360k/HISTORY_SPEC_STATUS.md)の観測219〜222に記録した。

どちらの変換も、61FCで同じ履歴リングの枠を確保する。

| 変換 | 履歴レコード | 照合と表示 |
| --- | --- | --- |
| 通常の読み変換 | 辞書参照の符号・ROM位置2バイト・辞書内位置 | 6475で辞書参照を照合し、ワークと26E4の群リストから表示 |
| ▲▼を2回押して選ぶ変換 | FF・候補の文字コード2バイト・00 | 6952で文字コードを照合し、候補表2100の先頭側へ移動 |

### 履歴を蓄積する位置と、選び直す範囲を管理する位置

| アドレス | この経路での役割 |
| --- | --- |
| 26DF | 起動時の復帰経路が確認する印。履歴初期化時にA5を書く |
| 26FA | 初回保存と、同じ変換内の再保存の切替え。開始時1、保存後0 |
| 26FB | 有効な履歴を走査する開始位置 |
| 26FC | 次の保存位置／有効な履歴の終端 |
| 26FD | 現在の変換の保存開始位置。再保存時に戻る位置 |

開始・終端の管理値は2刻みで、実アドレスは2700+2×管理値になる。
管理値を7Fでマスクして周回し、64枠のうち1枠を空けて最大63件を保持する。
満杯のときは空き枠に記録を入れ、開始位置を1枠進める。
追加した形式にかかわらず、最古の記録は有効範囲から外れ、その内容が残った枠が次の空きになる。
観測224では最古枠に追加側と異なる形式の記録を置き、両方向の押し出しを確認した。
開始と終端が等しい空状態では、記録を読む前に終了することを実測した。

通常の読み変換では、変換開始の40D1が26FAを1にする。最初の保存では60A2が
書込み位置26FCを26FDへ退避し、保存後の61F9が26FAを0にする。
その後の候補変更では26FDを26FCへ戻して、同じ保存部分を書き直す。
例えば、記録 `01 48 39 00` が `01 48 39 01` へ更新されても、終端26FCは6のままだった。
同じ変換中に候補を選び直すたび、履歴件数を増やすことを避けている。

▲▼側の番号選択では61FCで枠を確保し、26FAと26FDは参照しない。
先にFF形式を1件保存して通常側へ切り替えた試行では、60A2が次の枠の位置02を
26FDへ書いた。その後の候補送りは608Cで26FCを02へ戻し、
先行するFF形式の記録を保持した（観測225〜226）。

満杯で再保存する場合も戻すのは終端26FCだけで、開始位置26FBは進んだ値を保つ。
この保存側の動作は、境界を設定した観測192と、通常のキー操作のみで65回保存した観測204で確認した。

### 周回後に古い記録が候補へ反映される場合

通常の読み変換の6475では、終端が開始より小さいと、有効範囲を読み、範囲外の枠を一巡してから
有効範囲をもう一度読む。実アドレスだけを周回させるため、管理値が示す件数より
64件多く調べる。有効63件では127回、有効2件でも66回になる。

照合は最後の一致を採用する。同じキーの記録が有効範囲にもあれば、
最後の有効範囲の走査で見つけた記録が優先される。範囲外にだけ一致があると、
古い項目が先頭に出たり、候補群の順序が変わったりする。
観測193では先頭の辞書項目が0→2に変わる例と、先頭候補群が0→1に変わる例を確認した。
観測194では通常の候補送りで最古記録を押し出し、同じキーの有効記録の有無で
再変換結果が変わることを確認した。両観測とも履歴の初期状態は独立Coreに直接設定した。

観測224では、FF形式の追加で押し出した辞書参照も6475で候補に反映された。
通常の辞書参照の追加で押し出したFF記録については、6952の有効範囲の逆順走査に
含まれず、候補表2100の先頭に移らなかった。満杯状態は直接設定し、保存後の
リングを別の独立Coreへ移して、それぞれの照合を確認した。

### CLEARと起動時の履歴

通常のCLEARキーは入力・表示の作業領域を初期化する。独立Coreの観測189〜191では、
CLEAR後も履歴ポインタと有効な2件の記録を保持した。
ROMの履歴初期化は26DFへA5を書き、26FBと26FCをゼロにする。
記録バイトはRAMに残り、開始と終端が一致するため照合対象から外れる。
起動時に初期化を選ぶ分岐と、復帰時の26DF検査でA5が見つからない分岐がこの処理を呼ぶ。
追跡した復帰分岐ではA5があれば履歴を保持する。エミュレータのcoldResetはRAMを先に
ゼロにするため、記録バイトも消える。観測204では独立Coreで起動時に初期化経路を通ることと、coldResetで履歴領域がゼロになることを確認した。実機の電源・リセット操作ごとの分岐は未確認。

履歴の保存・照合・表示に関する実測は[観測記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)の
観測140〜165・189〜194・204、生成条件・初期化・周回時の詳細は[履歴仕様](../../analysis/pc1360k/HISTORY_SPEC_STATUS.md)の
観測167〜195にまとめた。
