# PC-1360K：読みを漢字に変える2KiBの仕事

2026-10-31、解析途中のまとめ。
実機から回収したROMをStudioで実行し、MCP経由で命令とメモリを追った結果を整理する。
実機上のRAMアクセスを直接測定した結果ではない。
[漢字ROMの回収とアクセス方式](PC-1360K.md)を前提とし、
手順・観測ごとの根拠は[ワークメモリの解析記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)に残した。

## 字形を描く仕事と、描く文字を決める仕事

「あ」を入力すると、文字コードから漢字ROMの一覧表を調べ、字形の位置を求める。
以前の吸い出し解析では、selector 0の `0x2378` から30バイトを読み、
各半分に空白列を加えて通常RAM `0xFEB0〜0xFECF` の32バイトへ展開する経路を確認した。
今回の入力実験でも、同じバッファの内容が回収済みの「あ」と全バイト一致した。

その間、追加RAM `0x2000〜0x27FF` への書込みはWatchで捕まらず、内容も変わらなかった。
追加2KiBを字形全体の一時置場と考える説明は、少なくともこの一文字表示には当てはまらない。
ただし読出しを含めて一切使わないと確認したわけではない。

変換キーを押すと、違う仕事が始まる。
通常ROM bank 7からbank 6の処理を呼び、読みを検索用の表現へ用意し、
追加RAMと通常RAMの管理位置を初期化して、漢字ROMの辞書側データを調べる。
調べた結果を8バイト単位の表に残し、その後に候補の選択・表示へ進む。

```text
かなのコード → 字形の位置を調べる → 字形を展開 → LCDへ転送

入力の読み → 検索用の表現 → 辞書を走査 → 追加RAMの結果表
                                              ↓
                                    候補の選択状態 → 文字の表示
```

結果表を使って候補の文字コードを得る後段には、まだ未解明の部分がある。
この図は処理段階の整理であり、その間のすべての呼出しを確定した図ではない。

## 同じアドレスでも、読んでいるものが違う

通常のメモリ読出しと、漢字ROMのREAD/READMは別の経路である。
たとえば通常RAMの `0x2378` と、selector 0のDP `0x2378` は別の場所になる。
通常ROMバンクは `0x3400`、漢字ROMの論理領域は `0x3600` で選ぶ。
命令を特定するときも、PCだけでなく通常ROMのbank番号を併記する必要がある。

今回の「あ」の辞書検索では、selector 3の `0x760A〜0x760B` から読んだ値を
通常RAM `0x26D5`、`0x26D4` に保存するところを捕まえた。
その後selector 2へ切り替え、追加RAMに保持した位置をXへロードし、
DP `0x0000` から別の辞書データを読み始めた。
追加RAMは、ROMを参照する位置や走査中の状態を置く役割を持っている。

## 辞書のバイト位置と、項目の位置

`0x237A〜0x237B` は下位・上位順の16ビット値で、漢字ROM内の読出し位置として使われた。
一方 `0x26D4〜0x26D5` は、ROMの表から初期値を得て加算し、
作業レコードへ保存して後で復元する別の16ビット値だった。

「あ」の走査では、最初のROM項目から次へ進むとき、
バイト位置は `0x0000 → 0x0005`、後者の値は `0x0000 → 0x0001` となった。
次はバイト位置が `0x0005 → 0x0009` へ進み、項目位置が2になった。
ROM項目の長さはヘッダー由来の値で変わるが、項目を進む数は1ずつ増える。
二つの位置を分けて保持する理由が、ここに見える。
この項目位置の辞書全体での意味と、候補表示時の使い方は引き続き調べている。

## 8バイトの結果表

今回の経路では、結果表は `0x2053` から並んだ。
新しい結果を置くと、前のゼロ終端をレコード先頭で上書きし、8バイト先に新しいゼロを置く。
二件目・三件目でも同じ構造を確認した。

| レコード内の位置 | 実測で分かった内容 |
| --- | --- |
| +0 | 入力との比較時の状態。「あ」は1、「かんじ」では1・2・3。一致した読みの長さという仮説 |
| +1 | まとめた項目数。新規時1、同属性の継続時に増える |
| +2 | ROM由来の属性値。現在のレコードと比較して、統合か新規かを分ける |
| +3 | ROM領域を選ぶための情報。`0x3600` へ書く値そのものとは限らない |
| +4〜+5 | ROM内位置、上位→下位 |
| +6〜+7 | 項目位置、上位→下位 |

管理位置の16ビット値と、レコード内の直列化ではバイト順が逆になっている。
表全体に一つのバイト順を当てはめると取り違える。

「あ」では8項目分が7レコードへまとまった。同じ属性の連続する2項目が一組になったためである。
一度離れて現れた同じ属性は別レコードとして残り、全表から同属性を探してまとめる動作ではなかった。
「かんじ」では29レコード・39項目分となり、先頭フィールド別には次のように分かれた。

| 先頭フィールド | レコード数 | まとめた項目数 |
| --- | ---: | ---: |
| 1 | 17 | 19 |
| 2 | 9 | 15 |
| 3 | 3 | 5 |

この1・2・3が「か」「かん」「かんじ」のような一致長に対応する可能性がある。
ただし、この結果表の項目数を、そのまま画面の候補数と呼ぶことはできない。

## 管理位置から見える作業の分担

| 通常RAMの位置 | 今回の経路で確認した使い方 |
| --- | --- |
| `0x2372〜0x2373` | 結果表の終端＋1を保持し、新規レコードで8ずつ進む |
| `0x2374〜0x2377` | 検索から戻った後、前の組を第二・第三組へ複製する。使い分けは未解明 |
| `0x237A〜0x237B` | 漢字ROM内のバイト位置 |
| `0x237C〜0x237D` | 結果表の位置をYへ取得して書込み・検査に使う |
| `0x2380` | 新規レコード格納前に1減らす枠の制御値。統合時は減らない |
| `0x26D4〜0x26D5` | ROM走査時の項目位置。加算・保存・復元する |
| `0x26D6` | 漢字ROM領域の選択に使う情報 |
| `0x2573〜0x2577` | 別の5バイト作業状態。末尾2バイトにROM位置を上位→下位で保存する経路を確認 |
| `0x2578〜0x2579` | 通常RAMへの書込み先ポインターとして使う |

追加RAM以外にも `0xFB00` 側の入力、`0xFB29` 側の検索用表現、
`0xFBA7` 側の中間レコードなどがある。変換状態が2KiBだけで完結するわけではない。

## 「感じ」から「幹事」へ

「かんじ」を変換すると、ユーザーの目視で「感じ」と「候補6」の表示を確認した。
その時点で `0x2040=6`、`0x2041=6`、`0x2043=0` だった。
変換キーをもう一度押すと、`0x2043` が0から1へ進み、
表示は「幹事」と「候補5」、`0x2041` も5となった。

したがって画面上の6→5と、内部の選択位置0→1は別に扱う必要がある。
この経路では `0x2042` を上限側として比較し、同値なら選択位置をゼロへ戻す。
「あ」では上限側が1だったため、再押下してもゼロへ戻って「亜」のままだった。
「かんじ」では上限側が4で、最初の再押下はゼロへ戻らず1へ進んだ。

ただし別の管理値にも下位から繰り上げるような処理があり、
画面に表示する候補数と単一の選択位置だけで全選択状態を説明する段階にはない。
表示用の値をどの命令で作るか、各成分が文節等の何に対応するかは未解明である。

## 残る内容と、有効な内容

「亜」と「幹事」をそれぞれ採用した後も、追加RAMの2048バイトは前後で同じだった。
結果表が残っていても、その内容を有効な変換状態として使い続けているとは限らない。
採用を、領域全体のゼロクリアで見分けることはできなかった。

字形バッファも同様に、待機時の内容だけでは表示の成否を判断できない。
候補の「亜」「感じ」「幹事」が表示されていても、確認した待機時には全ゼロだった。
一方、採用後には非ゼロの字形が残る場合があった。
描画時の一時バッファとLCDに残る表示、変換中の有効状態とRAMに残る値を区別して追う必要がある。

今後は、結果表から表示文字列を得る処理、複数文字の採用時の状態遷移、
別表 `0x2381` 以降の形式や、候補列と選択成分の対応を追う。
本稿で未確認の領域を含め、2KiB全域の割当表はまだ完成していない。


## 保存済みソースは別の文字表現から始まる

比較用に `10 PRINT "A幹事B"`、`20 END` をロードし、プログラムRAMを確認した。
保存された文字列はASCIIのA・Bと、CP932の2バイト文字である。
「幹」は `0x8A,0xB2`、「事」は `0x8E,0x96` となっていた。
入力ワークで見たJISコードの下位・上位順の並びとは異なる。
LIST時の解析では、この保存表現をどう判別し、字形取得へ渡すかが入口となる。
WIDTH 2を維持して英数入力・PROモードへ移り、LISTを表示した区間では、
追加RAM全域への書込みWatchは発火せず、2048バイトの内容も変わらなかった。
保存済みソース表示と、結果表を作る入力・変換の違いがここでも現れた。
同じソースをRUNし、PRINTで文字列を出した場合も、追加RAMの書込みWatchは発火せず、
2048バイトの内容は変わらなかった。さらに全域read/write WatchでRUNを繰り返しても
停止せず、今回のPRINTは追加RAMの読出しも必要とせずに進んだ。
LIST 10も全域read/write Watchで繰り返して停止せず、内容は不変だった。
今回の保存済み混在行では、LISTもPRINTも追加RAMの読書きを必要としなかった。


LISTの最初の漢字「幹」で、通常ROM bank 1の字形取得入口を捕まえた。
ソースの `0x8A,0xB2` は内部ROM `0x02A5` の変換処理を通り、
字形取得時のXはJISコード `0x3434` となっていた。
その後は、以前「あ」で追ったbank 1 `0x5013` からの字形取得処理へ合流した。
保存ソース表示は、既に決まった文字をコード変換して描く経路として追える。
入力変換時のように結果表を作って描く文字を選ぶ仕事とは区別できる。


二文字目「事」もJIS `0x3B76` で同じ入口へ到達した。
その手前で「幹」が表示されるまでの全命令がTraceに残り、
「幹」はselector 0の25バイトをREADMでCPU内部RAMへ読み、
圧縮側の展開処理から字形バッファへ書く経路を通っていた。
「あ」の無圧縮30バイトとは異なる経路でも、追加2KiBへの書込みはなかった。
字形展開で使うCPU内部RAMと、日本語処理用の追加RAMを区別する必要がある。


「事」の取得直後・LCD転送前でも停止できた。selector 0の19バイトを
CPU内部RAMへ読み、同じ32バイトの字形バッファへ展開していた。
「幹」の25バイトとは取得量が違うが、展開後の形式は揃う。
そのバッファは「幹事」の採用後に残っていたものとも一致し、
文字単位でバッファを再利用する流れを裏付けた。


同じ混在行のBでは、漢字の字形バッファを上書きせず、
通常ROMの字形位置をXへ返す経路に切り替わった。
Bの最初の読出し位置は `0x4733` となる形で、WIDTH 2のAから16バイト後に当たる。
保存文字列を表示するときも、通常ROMの英字と漢字ROMから展開した字形を
同じ表示呼出しの中で扱い分けている。


## 二つの使い方を比べて

今回の試験では、保存済みソースをLISTする場合も、PRINTで文字列を出す場合も、
追加2KiBへの読書きWatchは発火しなかった。
一方、読みから漢字を選ぶときには、ROM内位置、項目位置、8バイトの結果表、
選択位置などがこの領域に置かれた。
追加RAMの仕事を考える入口として、「漢字を描く」と「描く漢字を決める」を
分けることが有効だった。

まだ分かっていないのは、結果表から候補列を作る別表の形式や、
選択状態の各成分、文節操作、採用時の有効状態の切替である。
調査対象の2KiB全域へ、確定した名前を付け終えたわけではない。


## 結果表を参照する、もう一つの5バイト表

`0x2381` からは別形式のレコードを作る処理も捕まえた。
「かんじ」の最初の結果に対しては、読みの消費量、元の結果レコード番号、
まとめた項目数、属性、追加情報の5バイトを置き、次の先頭をゼロにする。
ROM内位置は元の8バイト表に保持し、別表はその番号で関係付ける二段構造になっている。

今回の最初のレコードは、属性によって直接格納する分岐だった。
別の属性ではさらにROM表を調べるコードがあるため、
すべての5バイトレコードが単純コピーでできるとはまだ確認していない。
最後の追加情報が `0xFF` になる意味や、この表から候補を選ぶ後段は引き続き解析する。


二件目は元表の番号4から作られ、間の番号1〜3は別表に入らなかった。
また元表の属性 `0x2C` は、selector 3の別のROM表を引いて属性6へ変わっていた。
つまりこの5バイト表は、元表の参照番号を保ちながら、
条件に合うものを選び、後段で使う属性へ変換した表である。
元の項目数2は引き継がれるが、全レコードが単純な複製ではない。


「かんじ」の別表が完成すると、元の29レコードから18レコードになった。
一部は読みの消費量も1から2、2から3へ増えていた。
元の一致位置の先を調べる処理が、単純な絞込みに加わっている。
追加情報のバイトも後から `0xFF` 以外へ更新されるため、
その意味と更新条件は次の解析対象になる。

2026-10-31はこの別表完成時点で一旦中断した。
停止位置と次に追う場所は[中断・再開メモ](../../analysis/pc1360k/WORK_MEMORY_CHECKPOINT.md)に残した。
