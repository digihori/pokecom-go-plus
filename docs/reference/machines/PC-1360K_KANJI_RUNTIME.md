# PC-1360K：読みを漢字に変える2KiBの仕事

2026-10-31、解析途中のまとめ。
実機から回収したROMをStudioで実行し、MCP経由で命令とメモリを追った結果を整理する。
実機上のRAMアクセスを直接測定した結果ではない。
[漢字ROMの回収とアクセス方式](PC-1360K.md)を前提とし、
手順・観測ごとの根拠は[ワークメモリの解析記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)に残した。

## 字形を描く仕事と、描く文字を決める仕事

「あ」を入力すると、文字コードから漢字ROMの一覧表を調べ、字形の位置を求める。
以前の吸い出し解析では、selector 0の `0x2378` から30バイトを読み、
各半分に空白列を加えて通常RAM `0xFEB0〜0xFECF` の32バイトへ展開する経路を確認した。
今回の入力実験でも、同じバッファの内容が回収済みの「あ」と全バイト一致した。

その間、追加RAM `0x2000〜0x27FF` への書込みはWatchで捕まらず、内容も変わらなかった。
追加2KiBを字形全体の一時置場と考える説明は、少なくともこの一文字表示には当てはまらない。
ただし読出しを含めて一切使わないと確認したわけではない。

変換キーを押すと、違う仕事が始まる。
通常ROM bank 7からbank 6の処理を呼び、読みを検索用の表現へ用意し、
追加RAMと通常RAMの管理位置を初期化して、漢字ROMの辞書側データを調べる。
調べた結果を8バイト単位の表に残し、その後に候補の選択・表示へ進む。

```text
かなのコード → 字形の位置を調べる → 字形を展開 → LCDへ転送

入力の読み → 検索用の表現 → 辞書を走査 → 追加RAMの結果表
                                              ↓
                                    候補の選択状態 → 文字の表示
```

結果表を使って候補の文字コードを得る後段には、まだ未解明の部分がある。
この図は処理段階の整理であり、その間のすべての呼出しを確定した図ではない。

## 同じアドレスでも、読んでいるものが違う

通常のメモリ読出しと、漢字ROMのREAD/READMは別の経路である。
たとえば通常RAMの `0x2378` と、selector 0のDP `0x2378` は別の場所になる。
通常ROMバンクは `0x3400`、漢字ROMの論理領域は `0x3600` で選ぶ。
命令を特定するときも、PCだけでなく通常ROMのbank番号を併記する必要がある。

今回の「あ」の辞書検索では、selector 3の `0x760A〜0x760B` から読んだ値を
通常RAM `0x26D5`、`0x26D4` に保存するところを捕まえた。
その後selector 2へ切り替え、追加RAMに保持した位置をXへロードし、
DP `0x0000` から別の辞書データを読み始めた。
追加RAMは、ROMを参照する位置や走査中の状態を置く役割を持っている。

## 辞書のバイト位置と、項目の位置

`0x237A〜0x237B` は下位・上位順の16ビット値で、漢字ROM内の読出し位置として使われた。
一方 `0x26D4〜0x26D5` は、ROMの表から初期値を得て加算し、
作業レコードへ保存して後で復元する別の16ビット値だった。

「あ」の走査では、最初のROM項目から次へ進むとき、
バイト位置は `0x0000 → 0x0005`、後者の値は `0x0000 → 0x0001` となった。
次はバイト位置が `0x0005 → 0x0009` へ進み、項目位置が2になった。
ROM項目の長さはヘッダー由来の値で変わるが、項目を進む数は1ずつ増える。
二つの位置を分けて保持する理由が、ここに見える。
この項目位置の辞書全体での意味と、候補表示時の使い方は引き続き調べている。

## 8バイトの結果表

今回の経路では、結果表は `0x2053` から並んだ。
新しい結果を置くと、前のゼロ終端をレコード先頭で上書きし、8バイト先に新しいゼロを置く。
二件目・三件目でも同じ構造を確認した。

| レコード内の位置 | 実測で分かった内容 |
| --- | --- |
| +0 | 入力との比較時の状態。「あ」は1、「かんじ」では1・2・3。一致した読みの長さという仮説 |
| +1 | まとめた項目数。新規時1、同属性の継続時に増える |
| +2 | ROM由来の属性値。現在のレコードと比較して、統合か新規かを分ける |
| +3 | ROM領域を選ぶための情報。`0x3600` へ書く値そのものとは限らない |
| +4〜+5 | ROM内位置、上位→下位 |
| +6〜+7 | 項目位置、上位→下位 |

管理位置の16ビット値と、レコード内の直列化ではバイト順が逆になっている。
表全体に一つのバイト順を当てはめると取り違える。

「あ」では8項目分が7レコードへまとまった。同じ属性の連続する2項目が一組になったためである。
一度離れて現れた同じ属性は別レコードとして残り、全表から同属性を探してまとめる動作ではなかった。
「かんじ」では29レコード・39項目分となり、先頭フィールド別には次のように分かれた。

| 先頭フィールド | レコード数 | まとめた項目数 |
| --- | ---: | ---: |
| 1 | 17 | 19 |
| 2 | 9 | 15 |
| 3 | 3 | 5 |

この1・2・3が「か」「かん」「かんじ」のような一致長に対応する可能性がある。
ただし、この結果表の項目数を、そのまま画面の候補数と呼ぶことはできない。

## 管理位置から見える作業の分担

| 通常RAMの位置 | 今回の経路で確認した使い方 |
| --- | --- |
| `0x2372〜0x2373` | 結果表の終端＋1を保持し、新規レコードで8ずつ進む |
| `0x2374〜0x2377` | 検索から戻った後、前の組を第二・第三組へ複製する。使い分けは未解明 |
| `0x237A〜0x237B` | 漢字ROM内のバイト位置 |
| `0x237C〜0x237D` | 結果表の位置をYへ取得して書込み・検査に使う |
| `0x2380` | 新規レコード格納前に1減らす枠の制御値。統合時は減らない |
| `0x26D4〜0x26D5` | ROM走査時の項目位置。加算・保存・復元する |
| `0x26D6` | 漢字ROM領域の選択に使う情報 |
| `0x2573〜0x2577` | 別の5バイト作業状態。末尾2バイトにROM位置を上位→下位で保存する経路を確認 |
| `0x2578〜0x2579` | 通常RAMへの書込み先ポインターとして使う |

追加RAM以外にも `0xFB00` 側の入力、`0xFB29` 側の検索用表現、
`0xFBA7` 側の中間レコードなどがある。変換状態が2KiBだけで完結するわけではない。

## 「感じ」から「幹事」へ

「かんじ」を変換すると、ユーザーの目視で「感じ」と「候補6」の表示を確認した。
その時点で `0x2040=6`、`0x2041=6`、`0x2043=0` だった。
変換キーをもう一度押すと、`0x2043` が0から1へ進み、
表示は「幹事」と「候補5」、`0x2041` も5となった。

したがって画面上の6→5と、内部の選択位置0→1は別に扱う必要がある。
この経路では `0x2042` を上限側として比較し、同値なら選択位置をゼロへ戻す。
「あ」では上限側が1だったため、再押下してもゼロへ戻って「亜」のままだった。
「かんじ」では上限側が4で、最初の再押下はゼロへ戻らず1へ進んだ。

ただし別の管理値にも下位から繰り上げるような処理があり、
画面に表示する候補数と単一の選択位置だけで全選択状態を説明する段階にはない。
表示用の値をどの命令で作るか、各成分が文節等の何に対応するかは未解明である。

## 残る内容と、有効な内容

「亜」と「幹事」をそれぞれ採用した後も、追加RAMの2048バイトは前後で同じだった。
結果表が残っていても、その内容を有効な変換状態として使い続けているとは限らない。
採用を、領域全体のゼロクリアで見分けることはできなかった。

字形バッファも同様に、待機時の内容だけでは表示の成否を判断できない。
候補の「亜」「感じ」「幹事」が表示されていても、確認した待機時には全ゼロだった。
一方、採用後には非ゼロの字形が残る場合があった。
描画時の一時バッファとLCDに残る表示、変換中の有効状態とRAMに残る値を区別して追う必要がある。

候補を覚える履歴にも、値がRAMに残っていても参照されない状態がある。
その有効範囲と、通常のCLEARで初期化する領域は後述する。


## 保存済みソースは別の文字表現から始まる

比較用に `10 PRINT "A幹事B"`、`20 END` をロードし、プログラムRAMを確認した。
保存された文字列はASCIIのA・Bと、CP932の2バイト文字である。
「幹」は `0x8A,0xB2`、「事」は `0x8E,0x96` となっていた。
入力ワークで見たJISコードの下位・上位順の並びとは異なる。
LIST時の解析では、この保存表現をどう判別し、字形取得へ渡すかが入口となる。
WIDTH 2を維持して英数入力・PROモードへ移り、LISTを表示した区間では、
追加RAM全域への書込みWatchは発火せず、2048バイトの内容も変わらなかった。
保存済みソース表示と、結果表を作る入力・変換の違いがここでも現れた。
同じソースをRUNし、PRINTで文字列を出した場合も、追加RAMの書込みWatchは発火せず、
2048バイトの内容は変わらなかった。さらに全域read/write WatchでRUNを繰り返しても
停止せず、今回のPRINTは追加RAMの読出しも必要とせずに進んだ。
LIST 10も全域read/write Watchで繰り返して停止せず、内容は不変だった。
今回の保存済み混在行では、LISTもPRINTも追加RAMの読書きを必要としなかった。


LISTの最初の漢字「幹」で、通常ROM bank 1の字形取得入口を捕まえた。
ソースの `0x8A,0xB2` は内部ROM `0x02A5` の変換処理を通り、
字形取得時のXはJISコード `0x3434` となっていた。
その後は、以前「あ」で追ったbank 1 `0x5013` からの字形取得処理へ合流した。
保存ソース表示は、既に決まった文字をコード変換して描く経路として追える。
入力変換時のように結果表を作って描く文字を選ぶ仕事とは区別できる。


二文字目「事」もJIS `0x3B76` で同じ入口へ到達した。
その手前で「幹」が表示されるまでの全命令がTraceに残り、
「幹」はselector 0の25バイトをREADMでCPU内部RAMへ読み、
圧縮側の展開処理から字形バッファへ書く経路を通っていた。
「あ」の無圧縮30バイトとは異なる経路でも、追加2KiBへの書込みはなかった。
字形展開で使うCPU内部RAMと、日本語処理用の追加RAMを区別する必要がある。


「事」の取得直後・LCD転送前でも停止できた。selector 0の19バイトを
CPU内部RAMへ読み、同じ32バイトの字形バッファへ展開していた。
「幹」の25バイトとは取得量が違うが、展開後の形式は揃う。
そのバッファは「幹事」の採用後に残っていたものとも一致し、
文字単位でバッファを再利用する流れを裏付けた。


同じ混在行のBでは、漢字の字形バッファを上書きせず、
通常ROMの字形位置をXへ返す経路に切り替わった。
Bの最初の読出し位置は `0x4733` となる形で、WIDTH 2のAから16バイト後に当たる。
保存文字列を表示するときも、通常ROMの英字と漢字ROMから展開した字形を
同じ表示呼出しの中で扱い分けている。


## 二つの使い方を比べて

今回の試験では、保存済みソースをLISTする場合も、PRINTで文字列を出す場合も、
追加2KiBへの読書きWatchは発火しなかった。
一方、読みから漢字を選ぶときには、ROM内位置、項目位置、8バイトの結果表、
選択位置などがこの領域に置かれた。
追加RAMの仕事を考える入口として、「漢字を描く」と「描く漢字を決める」を
分けることが有効だった。

まだ分かっていないのは、結果表から候補列を作る別表の形式や、
選択状態の各成分、文節操作、採用時の有効状態の切替である。
調査対象の2KiB全域へ、確定した名前を付け終えたわけではない。


## 結果表を参照する、もう一つの5バイト表

`0x2381` からは別形式のレコードを作る処理も捕まえた。
「かんじ」の最初の結果に対しては、読みの消費量、元の結果レコード番号、
まとめた項目数、属性、追加情報の5バイトを置き、次の先頭をゼロにする。
ROM内位置は元の8バイト表に保持し、別表はその番号で関係付ける二段構造になっている。

今回の最初のレコードは、属性によって直接格納する分岐だった。
別の属性ではさらにROM表を調べるコードがあるため、
すべての5バイトレコードが単純コピーでできるとはまだ確認していない。
最後の追加情報が `0xFF` になる意味や、この表から候補を選ぶ後段は引き続き解析する。


二件目は元表の番号4から作られ、間の番号1〜3は別表に入らなかった。
また元表の属性 `0x2C` は、selector 3の別のROM表を引いて属性6へ変わっていた。
つまりこの5バイト表は、元表の参照番号を保ちながら、
条件に合うものを選び、後段で使う属性へ変換した表である。
元の項目数2は引き継がれるが、全レコードが単純な複製ではない。


「かんじ」の別表が完成すると、元の29レコードから18レコードになった。
一部は読みの消費量も1から2、2から3へ増えていた。
元の一致位置の先を調べる処理が、単純な絞込みに加わっている。
追加情報のバイトも後から `0xFF` 以外へ更新されるため、
その意味と更新条件は次の解析対象になる。

2026-10-31はこの別表完成時点で一旦中断した。
停止位置と次に追う場所は[中断・再開メモ](../../analysis/pc1360k/WORK_MEMORY_CHECKPOINT.md)に残した。


2026-11-21の再現では、二件目のレコードの追加情報を更新する直前で停止できた。
bank 6 `0x4E8E` のIYSは、selector 3の `0xE3BB` から得た `0xA9` を
既存レコードの+4（`0x238A`）へ格納する。更新前の値は `0xFF` だった。
同じ消費量・元レコード番号の結果へ、別のROM表由来の情報を追加する経路である。
この情報を後段でどう解釈するかは、読出し側の解析を続ける。


利用側では `0xFF` を特別扱いし、今回の `0xA9` は上下4ビットから
selector 3内の参照位置 `0xCA90` へ変換された。
追加情報は、この経路で16バイト境界のROM位置を表す短い参照符号として使われる。
参照先の内容が候補・文節処理で何を意味するかは、さらに追跡する必要がある。


### 追加情報は後段のROM表への参照符号だった

5バイト表の最後の追加情報は、後段では属性と同じ変換ルーチンへ渡される。
実行で `0xA9` からselector 3の `0xCA90` を参照し、先頭バイト
`0x80` を読むことを確認した。`0xFF` は参照変換を飛ばす分岐になっている。
属性と追加情報から作る参照位置は、通常RAM `0xFC18` 以降へ
上位・下位の順で保存される。

さらに後段には、参照位置にオフセットを加えて読んだROMの値と、
作業表のマスクをビットANDで照合する処理がある。
照合成功項目から別の参照符号を取り出すコードも見つかった。
このため追加情報を単なる表示用フラグとして扱うことはできない。
ただし、照合が品詞や語の接続など何を表すのかは、まだ確定していない。
詳細な実測と未確認部分は観測78〜89に分けて記録している。

比較入力を「かんじ」から「かんじの」へ延ばすと、照合成功側を捕捉できた。
作業項目 `07 04 76` の先頭が `87` に変わり、その成功印を使って
第3バイト `0x76` から新しい参照位置 `0xC760` を作るところまで確認した。
参照位置の格納先は先頭から書き直されるため、後段では元の属性参照を
そのまま使い続けるだけでなく、照合結果に応じて参照の組を作り直している。
この挙動は読みの続きを扱う仕組みを考える手掛かりになるが、
言語上の分類名や最終候補との対応付けは今後の解析に残る。

この再構成に成功した後、処理は後続の読みの消費量を累積する。
「かんじの」の実験では追加分が1となり、処理位置も後続の「の」に対応する位置の
次、入力終端を指した。参照の再構成はROM表を引くだけで完結する処理ではなく、
読みの続きを照合して消費する流れにつながっている。
この追加分を最終的な候補や文節へ反映する呼出し元は、引き続き追跡する。

後続読みの追加消費量は、さらに追加RAMの作業レコードへ保存される。
今回の実測では `0x2578` のポインタが示す `0x257F` の+10、
すなわち `0x2589` へ1が書かれ、ポインタは17バイト先の `0x2590` へ進んだ。
これにより、ROM表の照合から追加RAM上の候補処理用状態へ至る経路が確認できた。
作業レコード全体のフィールドと候補文字列との対応は、引き続き解析する。

保存後には17バイトの領域を次の作業位置へコピーし、次の領域の追加消費量を0へ戻す。
今回、元の `0x257F` のレコードは追加分1を保持し、次の `0x2590` は
共通の内容を引き継いだうえで追加分0となり、管理値 `0x257E` は1に増えた。
追加RAMには候補の検索結果だけでなく、読みの続きを処理した結果を残す領域と、
次の処理に使う作業領域があることが分かってきた。

この17バイトレコードには、5バイト表のどの結果を使ったかも残る。
今回の値と保存コードでは、+1が元の読み消費量、+2が5バイト表の番号、
+3がその項目数、+10が後続の追加消費量と対応した。
「かんじの」では、元の読み長3を持つ3レコードが追加分1を保持して並んだ。
元の結果と後続の照合結果を組にして保存する領域だと捉えられる。

今回の生成ルーチンが上位へ戻った時点でも、保存済みレコードは3件だった。
それぞれ5バイト表の番号15・16・17に対応し、読み長3と後続追加分1を持つ。
これは処理結果レコードの数であり、画面の候補数や異なる文字列の数とはまだ対応付けていない。
レコード内の項目数は3・1・1なので、同じ粒度の数として数えないことが大切である。

作業レコードの+0には、入力バッファ内の起点オフセットが入ることも確認できた。
起点を0から1へ進めた準備処理では、保存済みの3レコードを保ったまま、
次の作業レコードの+0だけが1となり、入力位置はバッファ基点+1へ設定された。
これでレコードの一部は、起点・元の読み長・結果表番号・項目数・後続追加分という
入力位置と検索結果の組合せとして説明できる。

起点を変えた処理では、元の表の開始側を残しながら、新しい表の終端後位置を別の管理組へ保存する。
実測では一次表の `0x2374` の組が現在の終端後位置を受け取り、`0x2376` の組は開始側を保持した。
5バイト表でも `0xFBDE` と `0xFBE0` の組が同様に分かれていた。
表の内容だけでなく、どの起点の範囲を処理中かを管理位置で区別している経路が見えてきた。

生成側から戻った後は、現在の作業位置の先頭へ `0xFF` を書いて列を終端にする。
今回の実測では、保存済み3レコードを維持したまま、次の位置 `0x25B2` が終端となった。
入力起点として0も有効なので、この17バイト列の終端は、
8バイト表・5バイト表の先頭0による終端と同じ規則では扱えない。

この作業列を後段へ渡すと、「かんじの」の実験では選択状態 `0x2040`・`0x2041` が5、
`0x2042` が3になった。保存された3レコードの項目数3・1・1の合計5と対応する。
選択状態への累積コードも確認でき、検索結果のレコードと候補数の粒度の違いを
数値で追えるようになってきた。画面表示との対応は別途確認する。

その後の表示処理ではLCDに「文節 かんじの」が現れ、内部の5・5・3は維持された。
この画面には候補番号5が表示されていないため、項目数の合計5と最終的な表示候補数の
一致はまだ実測していない。内部の数値の生成と、画面上での使い方は分けて確認している。

文節画面で変換キーを押すと、保存済みレコードを変えずに、表示が「文節 漢字の」へ変わった。
このとき `0x2040` は5のまま、`0x2041` は5から4へ、`0x2047` は0から1へ変わった。
`0x2040` の5を実際に読む命令も捕捉でき、その利用側は2以上かを検査し、
後に `0x2041` と比較する。固定の件数側と選択によって動く状態側が分かれていることを示す。
各フィールドの全モードでの意味と循環時の規則は、さらに更新命令を追って確認する。

変換キーで動く `0x2041` は、今回5→4→3→2→1→5と循環した。
更新命令はbank 6 `0x56A7`。直前で1を減らし、0になった場合は件数側の
`0x2040` を読み直すため、この経路では1から上限へ戻る仕組みになっている。
循環後には「文節 幹事の」と番号5が表示され、内部の選択値5との対応も確認できた。
一方、レコード番号側の選択成分は別のタイミングで更新されるので、
内部値の書込直後と、画面が完成した状態を区別して追っている。

内部の項目位置 `0x2047` は、通し番号とは逆に0から1へ増える。
実際の更新はbank 6 `0x570F` で捕捉できた。
コード上は `0x2046` の上限と比較し、到達すると位置を0へ戻して、
より上位の成分へ繰り上がる構造である。
画面の番号を減らす処理と、候補を取り出す内部位置を進める処理は、別々に実装されている。

項目内の上限を越えた場合には、位置が0へ戻ったうえでグループ位置 `0x2043` が
0から1へ進む実行例も捕捉できた。次のコードは新しいグループ用の状態を作り直す。
作業レコード幅17とグループ位置を使う処理が見つかり、
保存済み3レコードと、選択側のグループ・項目内位置がつながりつつある。

3件の作業レコードと選択グループの対応も実測できた。
グループ位置0・1・2は、それぞれ `0x257F`・`0x2590`・`0x25A1` のレコードを選ぶ。
そのレコードから別表番号15・16・17と項目数3・1・1が選択状態へ設定される。
今回の5項目の巡回は、この3グループを、項目内位置を進めながら順にたどる仕組みとして説明できる。
候補文字列の取得先を追う際は、通し番号だけでなく、グループに対応する別表番号と項目内位置を見る必要がある。

## 選んだ候補を覚えて、次の変換で先頭に出す

「かんじの」を変換すると、履歴のない状態では先頭に「幹事の」が現れた。
そこで「漢字の」へ候補を切り替え、採用してから同じ読みを再入力すると、
次の変換では先頭に「漢字の」が現れた。画面の候補番号は5、内部の表示位置は0のままである。
この変化を、追加RAMへの保存から辞書項目の取出しまで追跡できた。

### 文字列ではなく、辞書項目を参照する4バイトを残す

末尾の `0x2700〜0x27FF` に保存されるのは、字形や候補文字列そのものではない。
今回の「漢字の」の候補変更では `01 48 39 01` が書かれた。

| バイト位置 | 意味 | この例 |
| --- | --- | --- |
| +0 | 一次表に保存されたROM選択符号 | 01 |
| +1/+2 | ROM内位置（上位・下位） | 4839 |
| +3 | 辞書項目内の位置 | 1 |

選択符号をそのままハードウェアのROMセレクタ値とは解釈しない。
保存は採用前の候補変更でも発生するので、「採用したときだけ覚える」とは説明できない。
同じ読みの次の変換では、先頭3バイトの一致判定を通り、末尾の項目位置1が読み込まれた。

### 保存情報から表示候補までの経路

履歴の照合は、現在の候補群に対応する辞書位置を使って行う。
同じ符号・ROM位置に対する記録が複数ある実験では、後方の記録の位置2が優先された。
この結果は次の領域を通って表示側へ届く。

| 段階 | 領域・処理 | 確認した内容 |
| --- | --- | --- |
| 記録 | 2700〜27FF | 辞書参照3バイトと項目位置1バイト |
| 照合 | 6475のルーチン | 3バイト一致後に項目位置を取込む |
| 集約 | 26E2/26E3 | 一致した記録の走査順と、候補群を通算した項目位置 |
| ワーク保存 | 17バイトレコードの+11/+12（10進） | 上の2値を保存 |
| 表示側へ展開 | 2050 | ワーク+12の値を受け取る |
| 項目番号変換 | 59B0のルーチン | 表示位置から実際の辞書内位置を求める |

保存位置1を持つ3項目群では、取出し番号は次のようになった。

| 内部の表示位置 | 履歴なしの辞書内位置 | 保存位置1がある場合 |
| --- | --- | --- |
| 0 | 0 | 1 |
| 1 | 1 | 0 |
| 2 | 2 | 2 |

右列は全3項目で実測した。保存した項目を先頭へ移し、残りの項目の順序を保つ。
辞書本体の並びを変更せず、取出し番号を変える仕組みである。
一般の保存位置h・表示位置kについてコードを読むと、k=0ならh、
1≦k≦hならk−1、それより後ろならkを使う。ただし全てのhと項目数を実験したわけではない。
複数履歴から選ばれた位置2についても、表示位置0から辞書位置2への変換を確認した。

### 履歴は候補群の並びにも使う

候補群を作る走査では、入力起点が0のワークは+11を比較値に使う。
起点が非ゼロなら、+11と起点側の履歴順位26F9の大きい方を使う。
まず比較値が非ゼロのワークを降順に並べ、次に比較値がゼロのワークを
読み消費量の降順に並べる。同順位の一部では、後続成分の符号7の照合結果
（ワーク+15）を比較し、リスト内の隣接要素を入れ替える。

リストは26E4から始まり、0始まりのワーク番号を並べてFFで終わる。
群位置2043からリストの番号を読み、257Fから17バイト刻みのワークを選ぶ。
この並びの生成規則はROMの静的解析による。群位置とワークの対応は観測124・127、
保存項目を群内の先頭へ移す動作は観測149〜157で実測した。
符号7による入替えの実入力での発生は未確認。

### 履歴を蓄積する位置と、選び直す範囲を管理する位置

| アドレス | この経路での役割 |
| --- | --- |
| 26DF | 起動時の復帰経路が確認する印。履歴初期化時にA5を書く |
| 26FA | 初回保存と、同じ変換内の再保存の切替え。開始時1、保存後0 |
| 26FB | 有効な履歴を走査する開始位置 |
| 26FC | 次の保存位置／有効な履歴の終端 |
| 26FD | 現在の変換の保存開始位置。再保存時に戻る位置 |

開始・終端の管理値は2刻みで、実アドレスは2700+2×管理値になる。
管理値を7Fでマスクして周回し、64枠のうち1枠を空けて最大63件を保持する。
満杯のときは空き枠に記録を入れ、開始位置を1枠進める。旧最古の記録は
照合対象から外れ、その内容が残った枠が次の空きになる。
開始と終端が等しい空状態では、記録を読む前に終了することを実測した。

変換開始の40D1は26FAを1にする。初回の保存では書込み位置26FCを26FDへ退避してから
記録を追加するコードがあり、保存後の61F9は26FAを0にする。
その後の候補変更では26FDを26FCへ戻して、同じ保存部分を書き直す。
例えば、記録 `01 48 39 00` が `01 48 39 01` へ更新されても、終端26FCは6のままだった。
同じ変換中に候補を選び直すたび、履歴件数を増やすことを避けている。

再起動後の実験でも、初回は巻戻しを省略し、次の候補変更は608Cの書戻しを実行して
保存開始位置0へ戻ることを確認した。26FCから26FDへ退避する命令自体は未捕捉だが、
値の変化と保存済みのコードは整合する。

満杯で再保存する場合も戻すのは終端26FCだけなので、すでに有効範囲から外れた
最古記録は復活しない。満杯・周回・複数枠の再保存は命令列と記号モデルで確認した。

### CLEARと起動時の履歴

通常のCLEARキーの分岐は入力・表示の作業領域を初期化し、履歴ポインタを保持する。
ROMの履歴初期化は26DFへA5を書き、26FBと26FCをゼロにする。
記録バイトはRAMに残り、開始と終端が一致するため照合対象から外れる。
起動時に初期化を選ぶ分岐と、復帰時の26DF検査でA5が見つからない分岐がこの処理を呼ぶ。
追跡した復帰分岐ではA5があれば履歴を保持する。エミュレータのcoldResetはRAMを先に
ゼロにするため、記録バイトも消える。以上はROMとCore実装の静的確認による。

履歴の保存・照合・表示に関する実測は[観測記録](../../analysis/pc1360k/KANJI_WORK_MEMORY.md)の
観測140〜165、生成条件・初期化・満杯時の詳細は[履歴仕様](../../analysis/pc1360k/HISTORY_SPEC_STATUS.md)の
観測167〜180にまとめた。
