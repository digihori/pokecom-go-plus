# PC-1360K 漢字ROM解析とStudio対応

文書区分：現行の機種情報と調査履歴を含む技術資料。2026-10-22整理。
利用操作は[導入ガイド](../../guides/GETTING_STARTED.md)・[Playerヘルプ](../../guides/PLAYER_HELP.md)、
実装・実機確認は各日付の記録として読み分けてください。

確認用初稿 / 2026-10-18

以前から私が調べていたPC-1360Kの情報に、今回行った実機での読出し実験、漢字ROMの回収、
Pokecom GO Studioへの組込みで分かったことを加えて整理した。
現在分かっているアクセス方法と、その根拠、まだ解明できていない点をここにまとめる。

アドレスとバイト値は原則として`0x`付きの16進数、容量はKiBで表す。
実機プログラムの`SUM`・`D`など、結果として返された数値は10進数のまま記載する。

## 1. 現在の到達点

実機から、漢字ROMの**選択値0〜3それぞれについて64KiB、合計256KiBの論理イメージ**を回収した。
これをStudioへ組み込み、変更していないPC-1360Kの通常ROMで、かな入力・漢字変換・候補切替・採用まで動作を確認した。
PC-1360KはStudioの通常の機種一覧とROM登録から選択でき、隠しモード用の環境変数は不要になった。

現在のアクセスモデルは次のとおり。

```text
通常の命令実行・PEEK等
    CPUアドレス → 通常のメモリ空間
                   0x4000〜0x7FFFは0x3400で通常ROMバンクを選択

漢字ROMのデータ読出し
    0x3600の値 → 読出し領域を選ぶ（確認済みは0〜3）
    DP         → 選んだ領域内の0x0000〜0xFFFFを指定
    READ(LDPC)  → 読出し値をAへ
    READM(MVMP) → 読出し値をCPU内部RAMの(P)へ
```

ここでいう「4領域」は実機から取得したデータを整理する単位である。
**選択値とSC6976S／SC6976Tの物理的な対応、A16・A17・Fポートの論理関係は未確定**であり、
回収した256KiBを、そのまま物理配線の解明完了という意味では使わない。

## 2. 情報の確かさと対象

本書では、次の根拠を区別する。

| 区分 | 意味 |
| --- | --- |
| 以前の調査 | これまでに私が基板・回路図・実機操作から調べていた内容 |
| 実機確認 | 読出しプログラムを手元の実機で実行し、数値・ファイル・録音を記録して確認した事項 |
| ローカルROM解析 | 実機から吸い出したROMをStudioのエミュレータで実行し、命令・メモリアクセス・表示を追った結果 |
| Studioの実装 | 確認した範囲を再現するために採用した動作。未測定の実機動作を保証するものではない |
| 未確定 | 今回の証拠だけでは判断していない事項 |

対象は手元の実機と、そこから吸い出したROMセットである。すべての製造時期・CPU改版・ROM版について同じと確認したわけではない。

## 3. 以前の調査で分かっていたハードウェアの違い

PC-1360KはPC-1360をベースに日本語対応した機種である。
以前から基板を調べていて、漢字ROMのSC6976S／SC6976Tと追加RAMが主な違いと考えていた。
追加RAMは**2KiB**で、対象アドレスは`0x2000〜0x27FF`である。

回路図からは、次のように読み取っていた。

| 信号 | 回路図から読み取った接続・観察 |
| --- | --- |
| CPUのA0〜A15 | 漢字ROMのアドレス線へ接続 |
| ゲートアレイ側A16 | 漢字ROMのA16へ接続 |
| ゲートアレイ側A17 | 漢字ROMのCEへ接続 |
| CPUのFポート出力 | 漢字ROMのCE系につながっている |
| AS1〜AS3 | 通常ROMの8バンク切替用。漢字ROMへは接続されていない |

この表は私が回路図から読み取った内容を整理したもので、CEの極性・合成条件まで確認した結線表ではない。
特に、ゲートアレイ側のA16／A17という名前だけでは、CPUのどの状態から各信号が作られるかは決まらない。

A0〜A16は17本なので、8ビット幅のROMが全アドレスを使う構成なら、1チップで128KiBを指定できる計算になる。
ただし、これは線数から得られる容量の見通しである。今回の4つの論理イメージを、
どのチップのどの半分へ割り当てるかは、この計算だけでは決められない。

### PC-1360とのROM比較

手元に保存していた両機種のダンプを今回比較すると、`0x0000〜0x1FFF`の内部ROM各8KiBは一致した。
一方、通常の外部ROMは8バンク中の複数バンクで異なっていた。

| 通常ROMバンク | 異なるバイト数（各16384バイト中） |
| --- | ---: |
| 0 | 34 |
| 1 | 316 |
| 2 | 1530 |
| 3 | 14322 |
| 4 | 9 |
| 5 | 0 |
| 6 | 0 |
| 7 | 5311 |

解析対象となったbank 1の`0x5013〜0x527D`の字形取得処理は、両方のダンプで一致していた。
同じ命令列があることと、外部バスの動作が同じであることは区別する必要がある。

なお、本書の「内部ROM 8KiB」と、READM(MVMP)の転送先である「CPU内部RAM」は別の領域である。
追加の2KiB RAMも、これらとは別に扱う。

## 4. 通常メモリと漢字ROMの対応

### 通常のCPUメモリ空間

今回のStudio実装では、PC-1360系の基本構成を次のように扱っている。

| CPUアドレス | 主な内容・用途 |
| --- | --- |
| `0x0000〜0x1FFF` | 内部ROM、8KiB |
| `0x2000〜0x27FF` | K機種の追加RAM、2KiB。漢字処理のワークという用途は調査対象 |
| `0x2800〜0x3FFF` | 制御・表示領域。以下の切替レジスタを含む |
| `0x4000〜0x7FFF` | 通常外部ROMの16KiB窓。8バンク、合計128KiB |
| `0x8000〜0xFFFF` | 基本実装のRAM領域。RAM構成設定等の詳細は機種定義に従う |

`0x3400`は通常ROMバンクの切替に使う。Studioは下位3ビットでbank 0〜7を選ぶ。
`0x3600`は、今回の実機読出しとStudio実装で漢字ROMの読出し元を選ぶ値として扱う。
この2つの切替は別系統である。

### 漢字ROMの論理読出し空間

漢字ROMは、今回確認したREAD(LDPC)／READM(MVMP)の経路では次の4つに整理できる。

| `0x3600`へ書く値 | DPの範囲 | 回収・保存する単位 | Studioのcomponent ID |
| --- | --- | ---: | --- |
| `0x00` | `0x0000〜0xFFFF` | 64KiB | `kanji-selector-0` |
| `0x01` | `0x0000〜0xFFFF` | 64KiB | `kanji-selector-1` |
| `0x02` | `0x0000〜0xFFFF` | 64KiB | `kanji-selector-2` |
| `0x03` | `0x0000〜0xFFFF` | 64KiB | `kanji-selector-3` |

理解のための式で書くと、読出し元は`漢字データ[選択値][DP]`となる。
たとえば選択値0、DP=`0x2378`でREAD(LDPC)すると、selector 0のイメージのオフセット`0x2378`を読む。
通常の`PEEK &2378`が同じ漢字ROMのバイトを返す、という意味ではない。

4イメージを0→1→2→3の順に連結すれば262144バイトになるが、そのファイル上の並び順は整理上の約束である。
これを実機の18ビット物理アドレスや、Sチップ→Tチップの順序と同一視しない。

## 6. 「あ」を表示するまでのデータの流れ

表示処理を追うと、文字の一覧表と字形データを区別して理解できる。
一覧表は「文字コードから、どの領域のどの位置にある字形を読むか」を求めるための情報である。
画面上の文字一覧を、そのまま並べたものという意味ではない。

### 6.1 一覧表の位置

通常ROM側の計算では、文字の行・列コードからselector 0内の一覧表の位置を求める。
今回の通常ROMについて、188件（重複1件を含む）の入力条件を読出し直前まで実行し、次の算術と一致することを確認した。

```text
r = 行コード - 0x21
rが0x0F以上なら r = r - 7
c = 列コード - 0x20
一覧表ブロックの先頭DP = r × 0x72 + (c >> 4) × 0x13
```

1ブロックは3バイトのヘッダーと16個の1バイト記述子からなる。
この確認は通常ROMの計算手順についてのもので、未定義の文字コードにも実在の字形があるという保証ではない。

「あ」の行・列コード`0x24／0x22`では、最初の一覧表DPは`0x0156`になる。
実機から取得した`0x0156〜0x015B`の値を使うと、次のように読める。

| 項目 | 値 |
| --- | --- |
| ヘッダー | `0x00` |
| 基準位置の上位・下位 | `0x23`、`0x5A` → `0x235A` |
| 先行する2文字の記述子 | `0x00`、`0x1D` |
| 「あ」の記述子 | `0x1D` |

この経路の字形読出し先の選択値は、ヘッダーのbit 2から`(ヘッダー & 0x04) >> 2`で求めている。
基準位置にはヘッダーのbit 0〜1を上位部分として加え、後続2バイトの値を足す。
先行記述子は、下位5ビットが0なら進み量0、そうでなければ下位5ビット+1として積み上げる。

「あ」では選択値0、基準位置`0x235A`、先行分`0 + 0x1E`なので、字形の先頭は`0x2378`になる。
実際にselector 0の`0x2378〜0x2395`を読み出し、期待した「あ」の字形になることを確認した。

したがって、選択値0を一覧表専用、選択値1を字形専用と固定するモデルは正しくない。
`0x3600`への書込みも、常に0と1を交互に切り替える決まりではない。
漢字ROMなしの初期解析で観測した0→1は、最初のREAD(LDPC)が次の命令の`0x34`を代わりに返し、
そのbit 2が1だったことでも生じていた。この初期の並びを、実機の固定的な切替規則の根拠には使わない。

### 6.2 字形の各ビットと画面上の位置

今回の「あ」は圧縮処理を通さない30バイトの経路だった。
最初の15バイトが上半分8ドット、次の15バイトが下半分8ドットで、1バイトが縦1列を表す。
各バイトはbit 0が上、bit 7が下に対応する。

左上を座標`(0, 0)`とし、字形データのバイト番号を`i`、ビット番号を`b`とすると、対応は次のようになる。

| データ内の位置 | 横位置x | 縦位置y |
| --- | --- | --- |
| バイト0〜14のbit b | i | b |
| バイト15〜29のbit b | i - 15 | 8 + b |

たとえば上半分の先頭バイトで`0x08`が立っていれば、左端の上から4番目、座標`(0, 3)`が点灯する。
同じ`0x08`が下半分の先頭バイトにあれば、座標`(0, 11)`が点灯する。

通常ROMは各15バイトの後ろへゼロ1バイトを加え、`0xFEB0〜0xFECF`の32バイトの一時バッファへ展開する。
これにより右端の空白列を含む16列×16ドットの形で、共通のLCD転送処理へ渡す。
この説明は実際に確認した「あ」の経路についてのもので、すべての字形が無圧縮30バイトという意味ではない。
記述子の他のビットを使う経路の全仕様は、引き続き調査対象である。

## 7. WIDTH、JAPAN設定、追加RAMの関係

### WIDTHと漢字入力は段階を分ける

以前の調査では、KS8のジャンパーはオープンでJAPAN、クローズで海外版となり、
手元の実機ではWIDTHコマンドの入口はJAPAN時のみ有効だった。
またPC-1360でも設定値を直接書き換えると、縦16ドットのアルファベット表示が働くことを確認していた。
ジャンパーの物理判定とコマンドの入口の全条件は、今回の実験では独立に確定していない。

ローカルROMでの基本操作と観測値は次のとおり。

| 操作段階 | `0x303C` | `0xFD07` CharMax | `0xFD08` WIDTH |
| --- | --- | ---: | ---: |
| 初期化後 | `0x08` | 24 | 4 |
| `WIDTH,2`＋ENTER | `0x08` | 18 | 2 |
| 漢字キー後 | `0xA8` | 18 | 2 |
| 続けてAを入力 | `0xA8` | 18 | 2 |

漢字キー後の左下の「文節」は、漢字ROMなしの解析状態でも表示された。
これだけでは漢字ROMの読出し成功を判断できない。Aを押した後のかな字形が、読出し経路を確かめる手掛かりになった。

漢字ROMなしのStudioでA入力後に見えたバーコード状の表示は、仮のREAD(LDPC)動作が後続命令の値を繰り返し返し、
それを字形として転送したことで生じた。実機で漢字ROMを取り外した場合の表示を確認したものではない。

### 大きいアルファベットとかなの取得元

ローカルROMでASCIIのAを比較すると、WIDTH=2のアルファベット字形は通常ROMのbank 1、
`0x4723〜0x4732`から取得され、PC-1360とPC-1360Kで一致した。
この経路ではREAD(LDPC)／READM(MVMP)も`0x3600`も使わず、`0xFEB0`への書込みもなかった。
通常表示の5列×8ドットの字形を単に拡大するのではなく、別の8列×16ドット字形を使っていた。

```text
通常ROMのWIDTH=2用アルファベット ─────────┐
                                         ├→ 共通のLCD転送処理
漢字ROM → 字形取得・展開 → 0xFEB0バッファ ──┘
```

したがって、`0xFEB0`をWIDTH=2の全表示に共通の字形取得場所とする説明は修正した。
今回確認したかな取得経路では使うが、大きいアルファベットの取得経路では使わない。

### 2KiBの追加RAM

`0x2000〜0x27FF`は追加RAMとして扱っているが、「漢字処理で読み出した内容をすべてここで処理する」とはまだ確認していない。
漢字ROMなしで比較したA入力の限定的な観測区間では、この領域へのCPU書込みはなかった。
その観測には初期設定の前段や、実際の辞書データを使う漢字変換の全体は含まれていない。
ワークの割当、辞書検索中の用途、常駐情報の内容は今後の解析対象とする。

## 9. Studioへの組込み

### 実装した動作

通常のPC-1360系のCPU・表示・キーボード・通常ROMバンクを土台に、PC-1360Kの識別、
追加RAMの区分、追加キー、漢字ROM読出しを組み込んだ。
CPUのREAD(LDPC)／READM(MVMP)からデータ取得を機種側のバスへ委譲し、
漢字ROMを持つPC-1360Kでは選択値とDPで読出す。
命令フェッチ、通常のメモリ読出し、`0x3400`の通常ROMバンク切替は別に保つ。

他機種のREAD(LDPC)／READM(MVMP)は、既存のPC+1読出し動作を維持する。
PC-1360Kで漢字ROMを一切登録しない場合も、従来の解析用動作との互換のため同じ動作を残している。
これは実機でチップが欠けた場合の電気的な値を再現したものではない。
漢字ROMを登録した状態で未登録・範囲外の選択値を使うと、Studioは`0xFF`を返す。
この値も未測定の実機動作を保証するものではない。

### `.pgrom`の形式

manifest v1をそのまま使い、機種IDを`pc-1360k`とする。
新しい物理アドレス指定の項目は追加していない。

| component ID | role | サイズ | 個数 |
| --- | --- | ---: | ---: |
| `internal` | `internal` | 8KiB | 1 |
| `bank-0`〜`bank-7` | `external` | 各16KiB | 8 |
| `kanji-selector-0`〜`kanji-selector-3` | `kanji` | 各64KiB | 4 |

4領域を含む完成セットは合計13コンポーネントとなる。
漢字ROMはパッケージ内の`rom/kanji-selector-0.bin`〜`rom/kanji-selector-3.bin`として保存し、SHA-256を検証する。
名前は観測した選択値を表し、S／Tの物理チップ名は割り当てていない。

解析途中のセットとの互換のため、漢字ROMなし、0・1のみ、0〜3すべての3構成を受け付ける。
途中に穴がある構成、3つだけの構成、サイズ・roleが違う構成、通常PC-1360への漢字ROM追加は拒否する。
かな漢字変換を使う場合は4つすべてを用意する。

### 登録と起動

1. `Create ROM Set…`でPC-1360Kを選ぶ。
2. 内部ROM 8KiB、bank 0〜7を順に連結した通常外部ROM 128KiBを指定する。
3. 漢字ROM欄に選択値0〜3の各64KiBを指定して`.pgrom`を作成する。
4. `Register in ROM Library`、または`Manage ROMs…`から登録し、PC-1360Kを選択する。

開発用の従来ファイル読込みも維持する。`local-data/roms/pc-1360k/`の
`pc1360kmem.bin`、`pc1360kbank.bin`、`kanji-selector-0.bin`〜`kanji-selector-3.bin`を使える。
同じ場所の`pc-1360k.pgrom`も通常の開発用検索で認識するが、登録済みの前回選択が優先される。

### 追加キー

画面キーは従来の実装で確認したスキャン位置を使う。グループ番号は0始まり。

| 表示 | 内部キー名 | スキャングループ | ビット |
| --- | --- | ---: | ---: |
| 漢字 | `KANJI` | 10 | 4 |
| 平/片 | `HIRA_KATA` | 11 | 5 |
| 採用 | `KANJI_FIX` | 0 | 2 |
| 変換 | `KANJI_CONVERT` | 0 | 3 |
| ▲と▼の上下2段 | `YJ` | 11 | 6 |

グループ0はメモリ側選択値1、グループ10・11はIAのbit 3・4を使う。
暫定表示FIX／CHG／YJは、実機の表記に合わせて上記のキーキャプションへ修正した。
▲▼キーの機能全体については、字形表示の修正と区別し、今回の完了確認に含めていない。
PC-1360Kの通常一覧への追加はStudio側の対応であり、Playerの対応機種追加とは別である。
