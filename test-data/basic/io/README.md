# BASIC入出力・通常系の受け入れテスト

独自に作成した再配布可能なBASIC。ROM・実機由来のプログラムは含まない。
WAV信号の再検証ではなく、Studioの通常のBASICロード／保存経路を対象にする。
手動は下記の **3ケース**。各ケース内で同じ手順を続けて行う。

| ケース | 機種 | データ |
| --- | --- | --- |
| BASIC-OLD | PC-1245 | [pc1245](pc1245/full.bas) |
| BASIC-S1 | PC-1401 | [pc1401](pc1401/full.bas) |
| BASIC-S2 | PC-1360K | [pc1360k](pc1360k/full.bas) |

## 準備

- 編集中のプログラムは先に別ファイルへ保存する。この確認ではプログラムを置換する。
- 対象機種と対応するROMを選択し、BASICのPROモードにする。
- 同じ機種の `full.bas`、`edited.bas`、`short.bas` を使う。
- 保存先はテスト用の別フォルダとし、配布データを上書きしない。
- 各機種フォルダ内の `saved*.bas` は手動保存のローカル成果物としてGit管理から除外する。
- `edited.bas` はキー編集後の期待値。最初からロードして編集工程を省略しない。

## 共通手順（各機種で1回）

| 段階 | 操作 | 合格条件 |
| --- | --- | --- |
| A ロード | `full.bas` を通常のBASICロードで読み、LISTで先頭・800〜900・910以降を確認 | 行順・行番号・文字列・REM・記号が保持される。エラーなし |
| B 実行 | RUNモードで `RUN` | `BASIC OK` と数値 `1` を表示して終了。`FAIL` や構文エラーなし |
| C 編集 | PROモードで `160 V=2`、`165 REM EDIT ADDED` を入力。`930` だけを入力してその行を削除 | LISTで変更・追加・削除が反映。RUNすると `BASIC OK` と `2` |
| D 保存 | BASICを `saved-edited.bas` に保存 | 下記の比較基準で同機種の `edited.bas` と一致 |
| E 再読込 | `NEW` で消去後、`saved-edited.bas` をロード。LISTとRUNを確認 | Cと同じ内容・実行結果。消去前のメモリに依存しない |
| F 短縮置換 | Eの長いプログラムが入ったまま `short.bas` をロード。LIST・RUN・保存・NEW・再読込 | 10・20行のみ。800以降を含む旧行が残らない。`SHORT OK` と表示。保存結果も `short.bas` と一致 |

Fでは上下キーによる行送りも確認する。「旧行が残らない」は有効なプログラムとして
参照されないという意味であり、旧領域がゼロで埋まっていることは合格条件にしない。

910以降は文字列・REMの保存専用で、通常のRUNでは実行しない。
PC-1245の指数は `\EX`、PC-1401/1360Kは `E` を使用する。
PC-1401には日本語を入れず、PC-1360Kのみ漢字・半角カナを確認する。
表示の数値前後の空白や、LISTの折り返し位置は判定対象外。

## 比較基準と対象範囲

ソースの完全な文字列一致は要求しない。保存時のキーワード周囲の空白、
行番号後の区切り、記号の正規表記への変換は許容する。
同じ機種でコンパイルした内部プログラムbyteの一致を基準とする。
ただし引用符内・REM内の文字と空白、行の追加・削除は保持が必要。

総合データは比較演算子6種、複文、負数・小数・指数、FOR/NEXT、GOSUB/RETURN、
行番号参照、文字列とREM内のキーワード・演算子・コロン、機種別記号と円記号をまとめて確認する。
異常ファイル・容量超過・キャンセル・WAV往復はこの手動3ケースには追加しない。
実機で行う場合は既に確認済みのWAV経路で転送し、B〜Cと保存後の内容確認を追加で行う。

自動テスト `BasicIoFixturesTest` は通常のDesktopBasicLoaderを使い、対応14機種で
全データのコンパイル→保存→再コンパイルのbyte一致、およびBOM有無・LF/CRLF/CRを検証する。
これは変換の確認であり、ROM上のRUNやメモリ置換の合格を意味しない。
トークン・記号の固定byte期待値は既存のcoreテストと併用する。

```sh
./gradlew :desktopApp:test --tests '*BasicIoFixturesTest'
```

保存したファイルは次のコマンドで照合できる（読取のみ）。機種と期待ファイルは対象に合わせて変更する。

```sh
./gradlew :desktopApp:verifyBasicIoSave -PbasicMachine=pc-1245 \
  -PbasicExpected=test-data/basic/io/pc1245/edited.bas \
  -PbasicSaved=/path/to/saved-edited.bas
```

### PC-1245ポインタ確認（2026-10-31）

ローカルROMを使った `Pc1245BasicNavigationTest` で、通常BASICロードと
結合program-imageロードの両経路を確認した。開始pointerはC6E1–C6E2、
終了pointerはC6E3–C6E4で、いずれも下位byteが先。

| データ | byte数 | 開始 | 終了（最後のFF） |
| --- | ---: | --- | --- |
| full.bas | 332 | C000 | C14B |
| edited.bas | 326 | C000 | C145 |
| short.bas | 20 | C000 | C013 |

短縮後の管理byteは `00 C0 13 C0`。ROMのキー入力でshort.basを作成した場合とも一致した。
各ロード直後とLIST後のpointer・本文・終端位置を検証済み。
LIST後の下・下・上・上では、ROM入力で作ったshortプログラムと表示も一致した。
LISTを挟む上記の手順では報告の旧行表示を再現できなかった。

追加の再現手順: リセット・起動 → full.basロード → RUN → CL → short.basロード
→ PRO切替 → 上・上・上 → CL → 上（途中でLISTを実行しない）。
この順序では最初の上キーで「00」を表示する症状を再現した。
開始・終了pointerは正しいが、ROMがRUN後の位置として保持するC6FE–C6FFが
旧位置C0C0のままで、上キーがC0BF以降の旧領域を逆向きに読んでいた。
CL後も同じ旧位置を再利用する。

ロード時にC6FE–C6FFも新終端C013へ更新する修正を追加。
回帰テストでは上キーで20行→10行→10行、CL後の上キーで20行を表示し、
旧領域C014–C14Bを読み取らないことを検証する。
ゼロクリア処理は変更していない。カーソル追加修正後にユーザーから動作OKの報告あり。
修正後の `build :core:desktopTest :desktopApp:createDistributable` は成功。

追加のカーソル不具合: 最初の上キーでENDのEが点滅し、CL→上では右側の空白で点滅する。
参照位置だけでなく、CPU内部RAM 0x15のbit 0x10に旧RUNからの編集復帰状態が残っていた。
BASIC置換成功時にこのbitも解除する。直接・結合ロードの両経路で確認し、失敗・BASICなしの操作では状態を保持する。
表示テストのカーソル除外を廃止し、ROMのNEW・キー入力で作った期待表示と、
上→上→上→CL→上の各表示をカーソル込みで複数の点滅位相にわたって比較する。
カーソル追加修正後も `build :core:desktopTest :desktopApp:createDistributable` が成功。

### PC-1401のカーソルとREM（2026-10-31）

PC-1401でも旧RUN後のカーソル残留を報告・再現。開始・終了pointerの不正ではなく、
内部RAM 0x35のbit 0x10が旧実行位置からの編集復帰を選ばせていた。
BASIC置換成功時にこのbitだけを解除する。PC-1401/1402のローカルROMで
直接・結合ロードの上→上→上→CL→上をカーソル込みで確認するテストを追加した。
2026-10-31、ユーザーから修正後のPC-1401はOKとの報告あり。手動ケースを合格として記録する。
PC-1360Kの結果は後述の確認記録を参照。

REMの後ろの余分な間隔は手入力でも現れる。ROM手入力の内部byteとファイル変換を比較すると、
`REM XXX`、`REM  XXX`、引用符・コロン・比較記号を含むREMはいずれも一致した。
保存・再読込を繰り返しても空白が増えないことを自動確認する。送信時の空白削除は不要。
PC-1401修正後の `build :core:desktopTest :desktopApp:createDistributable` は成功。

ユーザーによる追加確認: LIST上で `10 REM  ABC`（空白2個）と表示された行を保存すると、
ファイルでは `10 REM ABC`（空白1個）になった。空白増殖の報告ではなく懸念として挙げられたもの。
今回の経路では表示上の追加1個を保存時に持ち越さず、元のファイル表記へ戻るため、
REM区切りの仕様変更や送信前の空白削除は行わない。
